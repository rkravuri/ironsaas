# Iron.Architecture.Tests

The build checks of the repository, written as plain xUnit tests so that anyone can read them.

| Rule | Where | What it checks |
|---|---|---|
| Layers | `LayerRules`, `LayerBuildCheckTests` | Every project declares `<IronLayer>` in its own file: `Kernel`, `Business`, `Suite`, `Host`, `Test` or `Tool` (ADR-0029, ADR-0043). The layer agrees with the name and the folder: `Iron.Kernel*` under `src/Kernel/`, `Iron.Business.*` under `src/Business/`, `Iron.Suites.<Suite>.*` under `src/Suites/<Suite>/`, `Iron.Host.*` under `src/Hosts/`, tests under `tests/`, tools under `tools/`. A Suite project also declares `<IronSuite>`, which names that `<Suite>`; no other project declares one. The build's own target `IronCheckLayer` (in `Directory.Build.props`) stops a project without a valid layer with `IRON0001` or `IRON0002`, and a missing, misplaced or invalid suite with `IRON0003` or `IRON0004`; `LayerBuildCheckTests` proves it on fixture projects, and that a suite project carries its suite into its assembly. |
| Project references | `ModuleBoundaryRules` | Dependencies go downward only: a suite may use Business and Kernel, Business may use Kernel, Kernel uses only Kernel. A suite never references another suite, not even its Contracts, and the Foundation never references a suite (ADR-0043). The vocabulary `Iron.Kernel` references nothing. A kernel library references the vocabulary and kernel libraries only. A Contracts project references `Iron.Kernel` only. A module references the vocabulary, the kernel libraries and Contracts projects only, never another module. A host references projects of the three layers, never another host, a test or a tool. |
| Private namespaces | `AssemblyReferenceRules` | No compiled assembly refers to a type in another module's `Api`, `Services` or `Data` namespace, whatever the layer. The check reads the type references of each assembly, so it also sees uses inside method bodies. |
| System clock | `ForbiddenMemberRules` | No Foundation assembly reads `DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now` or `DateTimeOffset.UtcNow`. Time comes from an injected `TimeProvider` (ADR-0007). The check reads member references, so it sees every call site. |
| Model rules | `ModuleDbContextTests` | Every `ModuleDbContext` in a module assembly builds its model and passes `ModelCheck`: every entity derives from `Entity`; in the Business and Suite layers every entity is a `BusinessRecord` or marked `ITenantWide` (TF-220); in every layer a business record is tracked (ADR-0051) and its table has its tags' `text[]` column `visibility_tags` (ADR-0057). A context's schema starts with its layer's prefix, or a suite's short name: `kernel_`, `business_`, `procurement_`. |
| What a test proves | `ProvesBuildCheckTests` | Every test method names the requirement criteria or the decisions it proves, `[Proves("TF-033 AC2")]`, or is `[Untraced("why")]` (ADR-0044). The analyzer in `tests/Iron.Testing.Analyzers`, which `Directory.Build.props` puts into every test project, stops the build with `IRON0005` (neither), `IRON0006` (an identifier out of form) or `IRON0007` (both); the test builds a fixture test project and expects each. Whether an identifier exists is `make trace`'s check. |
| Layout | `RepositoryLayoutTests` | Every project sits in a folder with its own name; a Contracts project sits in `Contracts/` inside its module; every module has a Contracts project; project names are unique; projects under `src/` start with `Iron.`; `src/` holds `Kernel/`, `Business/`, `Suites/` and `Hosts/`, and `src/Suites/` one folder per suite with its README. |
| Image pins | `ImagePinRules`, `ImagePinRulesTests` | Every image a Dockerfile builds from (`FROM`, `COPY --from`) and every third-party image of a compose file is pinned by its version and its digest, `name:version@sha256:...`, and its folder is in a Dependabot entry of its ecosystem (ADR-0055, since V0). An earlier stage and an image built here, named through a variable, are the build's own. |
| Script modes | `ScriptModeRules`, `ScriptModeRulesTests` | Every shell script git's index holds (`*.sh`) has mode 100755, read with `git ls-files --stage`, so a script that lost its executable bit fails the build before anything runs it; the failure names the script and the command that gives the bit back (V2's review). |

Each failure names the project file or the assembly and the forbidden reference.

How the rules are organised: `ProjectCatalog` finds every project file in the repository (build output and packages left out) and describes it by its declared layer and its name (pure logic, unit tested with made-up paths in `Fixture`). `LayerRules`, `ModuleBoundaryRules`, `AssemblyReferenceRules` and `ForbiddenMemberRules` are pure functions over that data. The `*Tests` classes apply them to the real repository.

Adding a rule: write it as a pure function with its own unit tests, then add one test that applies it to the repository.

Try it: add `<ProjectReference Include="../Iron.Kernel.Identity/Iron.Kernel.Identity.csproj" />` to `src/Kernel/Iron.Kernel.Audit/Iron.Kernel.Audit.csproj`, or delete the `<IronLayer>` line of any project, and run `make check`. Undo it afterwards.
