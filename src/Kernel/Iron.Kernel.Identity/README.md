# Iron.Kernel.Identity

Kernel module (ADR-0029). Schema `kernel_identity`. Principals, passwords, sessions, invitations and access tokens (TF-010, TF-011, TF-018, TF-020, TF-021, TF-023, TF-029; ADR-0014, ADR-0015); the password policy, lockout, recovery links, a person's life cycle and security events (TF-012, TF-017, TF-019; ADR-0046).

| Folder | Holds |

| `Contracts/` | `IdentityPermissions` (`identity.users.read`, `identity.users.manage`), `IdentitySettings` (the session limits, an invitation's validity, the password policy and the lockout), `IdentityErrors` (with `identity.user.not_found`, the home unit's codes, one code per password rule, the lockout's, recovery's and the life cycle's), `IdentityAuditEvents` (login, logout, session, invitation, token, home unit, `identity.user_created`, and one per security event), `SecurityEventKinds` and `SecurityEventActors` |

Configuration (`Identity` section): `Session:CookieName` (`iron.session`), `Session:IdleMinutes` (60), `Session:AbsoluteHours` (12), `Session:TouchSeconds` (60), `Password:MaximumLength` (1024; the rest of the policy is the tenant's settings), `Argon2:MemoryKb` (65536), `Argon2:Iterations` (3), `Argon2:Parallelism` (1), `Invitation:ValidHours` (72). `Seed:Administrator:LoginId` and `Seed:Administrator:DisplayName` name the first administrator the `seed` command creates; `Seed:ServiceAccounts` (a list of `ClientId`, `Secret`, `Role`, `DisplayName`) the service accounts: the smoke client in a unit, the operator in the control plane. An account that exists keeps its secret when the seed is given the same one; given another, it takes the new secret and the seed writes `identity.service_account_secret_changed` in the same transaction, which is how a unit healed after a lost store (ADR-0028) gets its smoke client back. `Tokens` section: `AccessTokenMinutes` (15), `Audience` (`iron-api`), `Issuer` (default `https://<primary hostname>`), `SigningKeyPem` or `SigningKeyPath`.

Passwords (TF-012, TF-017, ADR-0046): one `PasswordPolicy` checks every password set, by an invitation, a recovery link or a change, against the tenant's settings: `identity.password.minimum_length` (12; 8 to 64), `identity.password.common_check` (always on), `identity.password.history_depth` (10; 0 to 24) and `identity.password.maximum_age_days` (0, off; or 30 to 365). There are no composition rules. A refusal answers 400 with one code per rule (`identity.password.too_short`, `too_long`, `is_login_id`, `common`, `reused`) and the rule as the field problem's code. `GET /auth/password-policy` answers the rules to anyone, for the forms of people without a session. `POST /api/v1/me/password` (`current_password`, `new_password`, `end_other_sessions`, true unless false) changes the password with the current one and ends the other sessions in the same step. A wrong current password answers `identity.password.current_wrong` on its field and counts against the login. A locked login answers 403, so the shell's session is not signed out. A right password past the maximum age answers the sign-in 401 `identity.password.expired` with `recovery_token`, the code of a recovery link, and no session. `/me` answers `password_expires_at` while the age is on.

Lockout (TF-012, ADR-0046): failed sign-ins count per login identifier, whether anyone has it or not, within `identity.lockout.window_minutes` (15). At `identity.lockout.threshold` (5) the identifier is locked for `identity.lockout.duration_minutes` (15), and even the correct password answers 401 `identity.login.locked` with one fixed message. The lock is checked before the account is looked up, so the answer says nothing about the account. The principal's status and sessions never change. The user record answers `locked_until`; `POST /api/v1/users/{id}/unlock` lifts it. Each lock and unlock is a security event of the person's, and a lock of an identifier nobody has is an audit event alone.

Links (ADR-0046): an invitation is `/invitations#<token>` and a recovery link `/recovery#<code>`, the code in the fragment, which no server receives; the shell posts it in the body. A link from the operator's path (the first administrator's invitation, the operator's recovery) is handed over through `IOperatorHandover` (Iron.Kernel), the one-time place the fleet gives the seed and `recover-admin`, and is never logged; a host run from source writes the dev administrator's link to the console.

Recovery links (TF-017, ADR-0046): a one-time code, valid 15 minutes, its SHA-256 on the principal. A newer link replaces the older one. `POST /auth/recovery` (`token`, `password`) sets a password under the policy, consumes the code, lifts a lock and ends every session; a used, replaced or expired code answers 404 `identity.recovery.invalid`, and a policy refusal leaves the link open. An administrator issues one with `POST /api/v1/users/{id}/recovery-link`, which answers `recovery_link` (`/recovery#<code>`) and `expires_at`, shown once. It needs `identity.users.manage` at the person's home unit and every permission the person holds (`identity.recovery.escalation`, 403). The operator issues one for a tenant's administrator through the control plane: the fleet runs the image's `recover-admin` command with the `Recovery` section (`LoginId`, `Operator`, `Reason`, all three required). The command issues the link only for an active tenant administrator of the whole tenant, records the operator and the reason in the tenant's audit trail and the person's security activity, and hands the link over through the job's place; without one it refuses (exit 1).

A person's life cycle (TF-010, ADR-0046): `POST /api/v1/users/{id}/deactivate` and `/reactivate` need `identity.users.manage` at the person's home unit. A deactivated person (status Disabled) cannot sign in; every session ends at once, a bearer token is refused from the next request, and an open invitation or recovery link closes. Nobody deactivates themselves (`identity.user.self`). The last active tenant administrator stays (`identity.user.last_administrator`, 409), under the lock Authorization's `ITenantAdministrators` takes. Reactivation restores the account, or answers a new `invitation_link` (`/invitations#<token>`) for a person who never set a password.

Security activity (TF-019, ADR-0046): password changed, recovery link issued and used, password set by recovery, login locked and unlocked, deactivated and reactivated. Each is a row of `security_events` and an audit event of the same name with the `identity.` prefix, in one transaction. `actor` says who caused it (`self`, `administrator`, `operator`, `system`), with `actor_name` and `reason` where there are. `GET /api/v1/me/security-events` answers a person's own, newest first; emailing them is S4's.

Home unit (TF-034): every principal belongs to one organisation unit of Authorization's tree, kept by id as `home_unit_id` and read through `IOrganisationUnits` in Authorization's Contracts. The seed gives every principal without one the root unit and writes `identity.home_unit_set` for each, in one transaction; `/api/v1/me` names it (`home_unit`: id, name, code). Access to other units is a role assignment scoped to them (ADR-0030).

Users by scope (ADR-0031): the users list and `GET /api/v1/users/{id}` declare `ScopedByRow()` and keep the principals whose home unit the reader holds `identity.users.read` at; a principal without a home unit needs a tenant-wide reader. A user outside answers 404 `identity.user.not_found`, the same as an unknown id, so neither a list nor a link reveals who exists. `POST /api/v1/users` (`login_id`, `display_name`, `home_unit_id`) needs `identity.users.manage` at the home unit, creates the user Invited, answers the invitation link (`/invitations#<token>`; email delivery is S4) and writes `identity.user_created` and `identity.invitation_created` in one transaction.

The session's times (TF-021): `/api/v1/me` and the login answer `session` with `started_at` (the session row's `created_at`; null for a bearer token), `expires_at` (the absolute limit) and `idle_expires_at` (the idle limit, never after the absolute one). Every request touches the session at most once a minute (`TouchSeconds`), so `GET /api/v1/me` is the shell's "Stay signed in" (ADR-0033).

What the shell may show: `/api/v1/me` answers `permissions` (held for the whole tenant) and `permissions_anywhere` (held at any scope), and `GET /api/v1/me/access?unit=<id>`, or `?record_type=&record_id=` with an optional `&unit=` for the record's unit, the permissions held there; `?unit=<id>&include_children=true` answers those held over the unit and every unit below it (ADR-0031), which is what changing an assignment to a unit and below needs. The answers only decide which actions the shell offers; every action is checked again by its endpoint.

Acting for a delegator (TF-037, ADR-0037): `POST /api/v1/me/acting-for` with `principal_id` makes the session act for a person whose delegation to the caller is active, and `DELETE` makes it act as the caller again; both answer `/me`. Only a shell session acts: a token is refused (`identity.acting.token`, 403), and so is a person with no active delegation from that one (`identity.acting.no_delegation`, 409). The session keeps the choice in `acting_for_id`; `RequestPrincipal.ActingForId` answers it, and Authorization's grants follow it. The first request after the delegation ends runs as the caller, clears the choice, writes `identity.acting_ended`, and answers the header `Iron-Acting-Ended` with the delegator's id. `identity.acting_started` and `identity.acting_stopped` are audited too, each naming both people. While acting, `/me` answers the delegator's permissions for the delegated duties, `acting_for` (id, name, duties, until), and always `delegations` (`given` and `received`, the active ones).

The working unit (TF-222, ADR-0038): `POST /api/v1/me/working-unit` with `unit_id`, or `all_units: true` for the consolidated view, sets the unit the session works for among the choices Authorization's `IWorkingUnits` answers, writes `identity.working_unit_chosen`, and answers `/me`. A unit that is not a choice, or "All my units" where it is not open, is refused (`identity.working_unit.not_yours`, 403); a token is refused (`identity.working_unit.token`, 403). The session keeps `working_unit_id` (null for the home unit) and `all_units`; `RequestPrincipal.WorkingUnitId` answers the chosen unit, else the home unit, and the home unit in the consolidated view. `/me` answers `working_unit`, `all_units` and `working_units` (`units` with their paths, `all_units_available`); a choice that may no longer be made falls back to the home unit when `/me` is read. The users list keeps to the working unit and the units below it, unless the session sees all its units; `GET /api/v1/users/{id}` is not narrowed. In a merge (ADR-0038), `HomeUnitMerge` homes the principals of the unit that goes at the unit that stays.

The directory (ADR-0037): `GET /api/v1/directory?search=` answers anyone signed in, as a paged list with the envelope, the active people whose display name or login contains the search: each row is `id`, `display_name` and `home_unit` (the unit's name), never the login, email, status or type, sorted by name. A search shorter than two characters is refused (`identity.directory.search_too_short`, 400). So a person who may not list users can still choose a delegate.
