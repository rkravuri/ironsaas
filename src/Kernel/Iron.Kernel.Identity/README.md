# Iron.Kernel.Identity

Kernel module (ADR-0029). Schema `kernel_identity`. Principals, passwords, sessions, invitations and access tokens (TF-010, TF-011, TF-018, TF-020, TF-021, TF-023, TF-029; ADR-0014, ADR-0015); the password policy, lockout, recovery links, a person's life cycle and security events (TF-012, TF-017, TF-019; ADR-0046); second factors, the MFA policy and step-up re-authentication (TF-013, TF-248; ADR-0047); single sign-on (TF-014; ADR-0048); the sessions console, the concurrent-session limit, revocation, impersonation, break-glass accounts, emergency accounts and terms acceptance (TF-021, TF-022, TF-025, TF-026, TF-028, TF-029; ADR-0049).

Configuration (`Identity` section): `Session:CookieName` (`iron.session`), `Session:IdleMinutes` (60), `Session:AbsoluteHours` (12), `Session:TouchSeconds` (60), `Session:ImpersonationCookieName` (`iron.impersonation`), `Locations:DatabasePath` (`/app/locations/dbip-city-lite.mmdb`; no file means no places), `Password:MaximumLength` (1024; the rest of the policy is the tenant's settings), `Argon2:MemoryKb` (65536), `Argon2:Iterations` (3), `Argon2:Parallelism` (1), `Invitation:ValidHours` (72). `Seed:Administrator:LoginId` and `Seed:Administrator:DisplayName` name the first administrator the `seed` command creates; `Seed:ServiceAccounts` (a list of `ClientId`, `Secret`, `Role`, `DisplayName`) the service accounts: the smoke client in a unit, the operator in the control plane. An account that exists keeps its secret when the seed is given the same one; given another, it takes the new secret and the seed writes `identity.service_account_secret_changed` in the same transaction, which is how a unit healed after a lost store (ADR-0028) gets its smoke client back. `Tokens` section: `AccessTokenMinutes` (15), `Audience` (`iron-api`), `Issuer` (default `https://<primary hostname>`), `SigningKeyPem` or `SigningKeyPath`.

Passwords (TF-012, TF-017, ADR-0046): one `PasswordPolicy` checks every password set, by an invitation, a recovery link or a change, against the tenant's settings: `identity.password.minimum_length` (12; 8 to 64), `identity.password.common_check` (always on), `identity.password.history_depth` (10; 0 to 24) and `identity.password.maximum_age_days` (0, off; or 30 to 365). There are no composition rules. A refusal answers 400 with one code per rule (`identity.password.too_short`, `too_long`, `is_login_id`, `common`, `reused`) and the rule as the field problem's code. `GET /auth/password-policy` answers the rules to anyone, for the forms of people without a session. `POST /api/v1/me/password` (`current_password`, `new_password`, `end_other_sessions`, true unless false) changes the password with the current one and ends the other sessions in the same step. A wrong current password answers `identity.password.current_wrong` on its field and counts against the login. A locked login answers 403, so the shell's session is not signed out. A right password past the maximum age answers the sign-in 401 `identity.password.expired` with `recovery_token`, the code of a recovery link, and no session. `/me` answers `password_expires_at` while the age is on.

Lockout (TF-012, ADR-0046): failed sign-ins count per login identifier, whether anyone has it or not, within `identity.lockout.window_minutes` (15). At `identity.lockout.threshold` (5) the identifier is locked for `identity.lockout.duration_minutes` (15), and even the correct password answers 401 `identity.login.locked` with one fixed message. The lock is checked before the account is looked up, so the answer says nothing about the account. The principal's status and sessions never change. The user record answers `locked_until`; `POST /api/v1/users/{id}/unlock` lifts it. Each lock and unlock is a security event of the person's, and a lock of an identifier nobody has is an audit event alone.

Links (ADR-0046): an invitation is `/invitations#<token>` and a recovery link `/recovery#<code>`, the code in the fragment, which no server receives; the shell posts it in the body. A link from the operator's path (the first administrator's invitation, the operator's recovery) is handed over through `IOperatorHandover` (Iron.Kernel), the one-time place the fleet gives the seed and `recover-admin`, and is never logged; a host run from source writes the dev administrator's link to the console.

Recovery links (TF-017, ADR-0046): a one-time code, valid 15 minutes, its SHA-256 on the principal. A newer link replaces the older one. `POST /auth/recovery` (`token`, `password`) sets a password under the policy, consumes the code, lifts a lock and ends every session; a used, replaced or expired code answers 404 `identity.recovery.invalid`, and a policy refusal leaves the link open. An administrator issues one with `POST /api/v1/users/{id}/recovery-link`, which answers `recovery_link` (`/recovery#<code>`) and `expires_at`, shown once. It needs `identity.users.manage` at the person's home unit and every permission the person holds (`identity.recovery.escalation`, 403). The operator issues one for a tenant's administrator through the control plane: the fleet runs the image's `recover-admin` command with the `Recovery` section (`LoginId`, `Operator`, `Reason`, all three required). The command issues the link only for an active tenant administrator of the whole tenant, records the operator and the reason in the tenant's audit trail and the person's security activity, and hands the link over through the job's place; without one it refuses (exit 1).

A person's life cycle (TF-010, ADR-0046): `POST /api/v1/users/{id}/deactivate` and `/reactivate` need `identity.users.manage` at the person's home unit. A deactivated person (status Disabled) cannot sign in; every session ends at once, a bearer token is refused from the next request, and an open invitation or recovery link closes. Nobody deactivates themselves (`identity.user.self`). The last active tenant administrator stays (`identity.user.last_administrator`, 409), under the lock Authorization's `ITenantAdministrators` takes. Reactivation restores the account, or answers a new `invitation_link` (`/invitations#<token>`) for a person who never set a password.

Security activity (TF-019, ADR-0046): password changed, recovery link issued and used, password set by recovery, login locked and unlocked, deactivated and reactivated. Each is a row of `security_events` and an audit event of the same name with the `identity.` prefix, in one transaction. `actor` says who caused it (`self`, `administrator`, `operator`, `system`), with `actor_name` and `reason` where there are. `GET /api/v1/me/security-events` answers a person's own, newest first; emailing them is S4's.

Home unit (TF-034): every principal belongs to one organisation unit of Authorization's tree, kept by id as `home_unit_id` and read through `IOrganisationUnits` in Authorization's Contracts. The seed gives every principal without one the root unit and writes `identity.home_unit_set` for each, in one transaction; `/api/v1/me` names it (`home_unit`: id, name, code). Access to other units is a role assignment scoped to them (ADR-0030).

Users by scope (ADR-0031): the users list and `GET /api/v1/users/{id}` declare `ScopedByRow()` and keep the principals whose home unit the reader holds `identity.users.read` at; a principal without a home unit needs a tenant-wide reader. A user outside answers 404 `identity.user.not_found`, the same as an unknown id, so neither a list nor a link reveals who exists. `POST /api/v1/users` (`login_id`, `display_name`, `home_unit_id`) needs `identity.users.manage` at the home unit, creates the user Invited, answers the invitation link (`/invitations#<token>`; email delivery is S4) and writes `identity.user_created` and `identity.invitation_created` in one transaction.

The session's times (TF-021): `/api/v1/me` and the login answer `session` with `started_at` (the session row's `created_at`; null for a bearer token), `expires_at` (the absolute limit) and `idle_expires_at` (the idle limit, never after the absolute one). Every request touches the session at most once a minute (`TouchSeconds`), so `GET /api/v1/me` is the shell's "Stay signed in" (ADR-0033).

What the shell may show: `/api/v1/me` answers `permissions` (held for the whole tenant) and `permissions_anywhere` (held at any scope), and `GET /api/v1/me/access?unit=<id>`, or `?record_type=&record_id=` with an optional `&unit=` for the record's unit, the permissions held there; `?unit=<id>&include_children=true` answers those held over the unit and every unit below it (ADR-0031), which is what changing an assignment to a unit and below needs. The answers only decide which actions the shell offers; every action is checked again by its endpoint.

Acting for a delegator (TF-037, ADR-0037): `POST /api/v1/me/acting-for` with `principal_id` makes the session act for a person whose delegation to the caller is active, and `DELETE` makes it act as the caller again; both answer `/me`. Only a shell session acts: a token is refused (`identity.acting.token`, 403), and so is a person with no active delegation from that one (`identity.acting.no_delegation`, 409). The session keeps the choice in `acting_for_id`; `RequestPrincipal.ActingForId` answers it, and Authorization's grants follow it. The first request after the delegation ends runs as the caller, clears the choice, writes `identity.acting_ended`, and answers the header `Iron-Acting-Ended` with the delegator's id. `identity.acting_started` and `identity.acting_stopped` are audited too, each naming both people. While acting, `/me` answers the delegator's permissions for the delegated duties, `acting_for` (id, name, duties, until), and always `delegations` (`given` and `received`, the active ones).

The working unit (TF-222, ADR-0038): `POST /api/v1/me/working-unit` with `unit_id`, or `all_units: true` for the consolidated view, sets the unit the session works for among the choices Authorization's `IWorkingUnits` answers, writes `identity.working_unit_chosen`, and answers `/me`. A unit that is not a choice, or "All my units" where it is not open, is refused (`identity.working_unit.not_yours`, 403); a token is refused (`identity.working_unit.token`, 403). The session keeps `working_unit_id` (null for the home unit) and `all_units`; `RequestPrincipal.WorkingUnitId` answers the chosen unit, else the home unit, and the home unit in the consolidated view. `/me` answers `working_unit`, `all_units` and `working_units` (`units` with their paths, `all_units_available`); a choice that may no longer be made falls back to the home unit when `/me` is read. The users list keeps to the working unit and the units below it, unless the session sees all its units; `GET /api/v1/users/{id}` is not narrowed. In a merge (ADR-0038), `HomeUnitMerge` homes the principals of the unit that goes at the unit that stays.

The directory (ADR-0037): `GET /api/v1/directory?search=` answers anyone signed in, as a paged list with the envelope, the active people whose display name or login contains the search: each row is `id`, `display_name` and `home_unit` (the unit's name), never the login, email, status or type, sorted by name. A search shorter than two characters is refused (`identity.directory.search_too_short`, 400). So a person who may not list users can still choose a delegate.

Second factors (TF-013, ADR-0047): an authenticator app (RFC 6238: HMAC-SHA1, 30-second steps, six digits, one step either side, each code once, of a step later than the last) or passkeys (WebAuthn through Fido2NetLib, user verification required, discoverable, the relying party the tenant's hostname). An app's secret is sealed with AES-256-GCM under `Identity:FactorKey` (32 bytes in base64 from the unit's secret, which the fleet makes once), the person's id as associated data; nothing about a factor is logged. The first factor brings ten recovery codes, shown once, each 80 bits, kept as SHA-256 of the person's id and the code, each usable once.

Signing in with a second factor: a right password for a person with a factor, or who must have one, answers `step` (`kind` `second_factor` or `enrolment`, `methods`, `expires_at`) and the cookie `iron.sign_in` (HttpOnly, `/auth`; five minutes for the second step, fifteen for enrolment) instead of a session. `POST /auth/second-factor` (`code`, `recovery_code`, or `passkey` with the credential's JSON; `POST /auth/second-factor/passkey-options` first) answers the session; a recovery code answers `enrol_new_factor: true`. Enrolment at sign-in: `POST /auth/enrolment/authenticator-app` (the secret and its `otpauth://` URI), `/authenticator-app/confirm` (`code`, `name`), `/enrolment/passkey/options` and `/enrolment/passkey` (`name`, `credential`), each answering the session with `recovery_codes`. Wrong factors count on the person: every third in a row cools 60 seconds, doubling to 15 minutes (`identity.second_factor.cooling`, `retry_after_seconds`), and the tenth locks the login identifier for the lockout's duration. `GET /auth/sign-in-options` says whether a passkey alone signs in; `POST /auth/passkey/options` and `/auth/passkey` do it where `identity.mfa.passkey_sign_in` is on. A password past its maximum age is looked at after the second step.

The MFA policy (TF-013 AC1): `identity.mfa.required_for` (`nobody`, `roles`, `everyone`; `roles`), `identity.mfa.roles` (role codes held at any scope; empty means every role holding a high-risk or critical permission), `identity.mfa.allowed_factors` (`both`, `authenticator_app`, `passkeys`), `identity.mfa.grace_days` (0 to 14, from the first sign-in that found it required; `/me` answers `mfa_enrol_by` meanwhile) and `identity.mfa.passkey_sign_in` (off). It applies to people; tokens keep their client credentials. Changing any of them needs a recent authentication. A change takes effect at the next request: `SessionService` asks on every request whether the policy now requires a factor of the person, who has none and no grace left, and the session middleware then sets a required step (`RequiredStep`), so every endpoint but the enrolment's own (declared `AllowDuringRequiredStep(IdentityErrors.MfaEnrolmentRequired)`; `/me`, the context and logout declare it with no step, for every step) answers 403 `identity.mfa.enrolment_required`, and `/me` answers `mfa_enrolment_required`. Nobody is signed out; the person enrols in the session, which goes on.

My factors: `GET /api/v1/me/factors` (the factors, `recovery_codes_left`, `required`, `allowed`, `enrol_by`); `POST /api/v1/me/factors/authenticator-app` and `/confirm`, `POST /api/v1/me/factors/passkey/options` and `/passkey`, `PATCH` and `DELETE /api/v1/me/factors/{id}` (the last one stays while it is required, `identity.factor.last`), `POST /api/v1/me/recovery-codes`. Adding, renaming, removing and new codes need a recent authentication. An administrator resets a person's factors with `POST /api/v1/users/{id}/factors/reset` (`reason`): `identity.users.manage` at the home unit, every permission the person holds (`identity.factor_reset.escalation`), a recent authentication; every session of the person ends. The record answers `factors` and `takeover_allowed`. The operator's `recover-admin` resets an administrator's factors too with `Recovery:ResetFactors`. Security events: `factor_enrolled`, `factor_removed`, `factors_reset`, `recovery_code_used`, `recovery_codes_regenerated`.

Step-up (TF-248): `RequestRecentAuthentication` answers the kernel's `IRecentAuthentication` from the session's `authenticated_at` (its sign-in, or its latest re-authentication) or a token's issue time. `POST /api/v1/me/reauthentication` says what confirming it asks (`second_factor`, `methods`, `passkey_options`) and `POST /api/v1/me/reauthenticate` (`password`, and `code`, `recovery_code` or `passkey`) confirms it; refusals are 403, and failures count as at sign-in. Behind it: recovery links, factor resets and deactivation here; role grants with a high-risk or critical permission in Authorization; the MFA policy's settings in Settings.

Single sign-on (TF-014, ADR-0048): a tenant's OpenID Connect providers are rows of `sso_providers` (`SsoProvider`: name, preset, discovery address, client identifier, allowed domains, claim names, just-in-time creation with a default role and home unit, single sign-on only, trust of the provider's MFA, group mapping as `role_mappings` jsonb), and the people linked to them `sso_links` (by the provider's `sub`). The client secret is never in the database: `ISsoClientSecrets` keeps it in the store at `<Secrets:Path>/sso/<provider id>` (`StoreSsoClientSecrets`), or in the process alone for a host without a store. `OidcDiscovery` reads and keeps the discovery document and the keys (HTTPS, or a loopback name; keys read again for an unknown key id, at most every thirty seconds); `IdTokenValidator` checks an ID token in full on the unit's clock. `SsoSignInService` runs the code flow with PKCE, `state` and `nonce` (`POST /auth/sso/start`, `POST /auth/sso/callback`, the challenge purpose `sso_sign_in`), then the people rules (verified email, allowed domain, link by subject, linking by email, just-in-time creation, never a deactivated person), the provider's group mapping through Authorization's `IProvidedAssignments`, and `LoginService.ProviderSignedInAsync` (the provider's MFA when trusted, or the tenant's policy; the provider rides into the session's `provider_id`). `SsoPeople` answers whether a person signs in only through a provider (`principal.sso_only`, or a linked provider's `sso_only`): the password step then answers 401 `identity.login.use_company_login` with the provider, and recovery links are refused. `SsoProviderService` manages providers behind `identity.sso.manage` (critical) and a recent sign-in, checks a default role and every mapping with ADR-0031's rule 1, and tests a connection (`POST /api/v1/sso/test`). `POST /auth/sso/discover` answers a domain's provider; `GET /auth/sso/{id}/sign-out` the address to sign out at the provider; `PUT /api/v1/users/{id}/sso-only` sets the mark. A person with no password confirms it is them (TF-248 AC6) through `POST /api/v1/me/reauthentication/sso`: their second factor here first, when they have one, then a sign-in at their provider with `prompt=login` and `max_age=0` (challenge purpose `sso_reauthentication`, bound to the session), which `/auth/sso/callback` counts only for the session's own person whose ID token's `auth_time` falls within the step-up window; otherwise 403 `identity.sso.reauthentication_stale`. Every refusal there is a 403 with `return_to`, and success answers `reauthenticated` with no new session. The tests run against the test provider (`tests/Iron.Testing/TestOidcProvider.cs`).

Sessions (TF-021, TF-022, ADR-0049): a session records its `method` (`password`, `passkey`, `sso`, `impersonation`, `break_glass`), `browser` and `platform` (`DeviceNames`, nothing for an agent it does not know) and `city` and `country`. `ClientAddress` takes the connection's address, or behind a private peer (the ingress) the last address of `X-Forwarded-For`; `MmdbIpLocations` reads DB-IP's IP to City Lite (CC BY 4.0, `docs/licences.md`) with MaxMind.Db. Only the city and the country stay with the session; the address goes into the sign-in's audit event. `GET /api/v1/me/sessions` lists a person's own live sessions with `current`; `POST /api/v1/me/sessions/{id}/end` ends another one and `POST /api/v1/me/sessions/end-others` all the others. `GET /api/v1/sessions` (the envelope; `principal_id`, `method`, `country` and the times filter), `GET /api/v1/sessions/summary?days=` (signed in now, and per UTC day the sessions started, the peak of people at once, the sessions ended by an administrator) and `POST /api/v1/sessions/{id}/end` (`reason`, behind step-up) need `identity.sessions.manage` (high risk). Before listing, `SessionConsole` ends the sessions past their limits. An ended session's next request answers 401 with why: `auth.session_limit`, `auth.session_ended`, `auth.session_revoked`, `auth.impersonation_ended`, else `auth.session_expired`. Every live session's answer carries `Iron-Session-Idle-Ends`. `identity.session.concurrent_limit` (0 to 10, 0 no limit): a sign-in past it ends the person's oldest sessions, each audited; impersonation sessions neither count nor end.

Revocation (TF-029, ADR-0049): `POST /api/v1/users/{id}/revoke` (`reason`; `identity.users.manage` at the unit, step-up, never oneself) sets the principal's `valid_after` and ends their sessions, for a person or a service account alike; `POST /api/v1/sessions/revoke-tenant` (`reason`, `confirmation` the tenant's identifier; `identity.sessions.manage`, step-up) records a `TenantRevocation`, ends every session, the asker's too, and is audited at high severity. Every request compares the session's start, or the token's issue time, with the principal's time (its row is read anyway) and the tenant's, which `RevocationTimes` keeps for at most 60 seconds per process and the revoking process learns at once. A token whose `iat` falls before the first whole second at or after a revocation is refused (`auth.token_revoked`).

Impersonation (TF-025, ADR-0049): `POST /api/v1/users/{id}/impersonation` (`reason`, `minutes`) needs `identity.impersonation.start` (critical) at the person's home unit, step-up and every permission the person holds; never oneself, only an active person. It sets the cookie `iron.impersonation` over the impersonator's session, which stays and is kept alive (`return_session_id`). The request then runs as the person: `RequestPrincipal.ImpersonatorId` and `ImpersonatorName` name the impersonator, and the audit writer adds them to every event. `/me` answers `impersonation` (who, why, until). At its time the next request ends it, answers `Iron-Impersonation-Ended` and runs as the impersonator; `POST /api/v1/me/impersonation/end` ends it at once. During it the recent-authentication check refuses (`auth.impersonation_forbidden`), and so do the endpoints marked `.ForbiddenDuringImpersonation()`: the person's factors, password, sessions, terms and acting for someone. `identity.impersonation.max_minutes` (15 to 120, default 120) bounds it. The person's security activity has `impersonation_started` (who, why) and `impersonation_ended`.

The operator's commands (ADR-0049): the image's `impersonate` command (section `Impersonation`: `LoginId`, `OperatorId`, `Operator`, `Reason`, `Minutes`) checks `identity.impersonation.operator_allowed` (on by default) and makes a `SignInLink` of purpose `impersonation`, handed over through the job's place in the store; `POST /auth/sign-in-link` (`code`, anonymous) takes it once within 15 minutes and starts an impersonation with no session to return to. `break-glass-open` (section `BreakGlass`: `Id`, `Operator`, `Approver`, `Ticket`, `Reason`, `Until`) creates or reopens the account `break-glass-<12 hex of the access>@break-glass.invalid` with the system role `break-glass` (every permission but the critical ones), `Principal.BreakGlassUntil`, no password, and a link of purpose `break_glass`; its sessions skip enrolment and terms and stop at its time whatever the fleet does. `break-glass-close` (`Id`, `Account`) deactivates it, ends its sessions and hands back the review: every action of the account from the audit trail (`IAuditTrail.ActionsOfAsync`). Each step is audited at high severity with both operators, the ticket and the reason.

Emergency accounts (ADR-0048, ADR-0049): `PUT /api/v1/users/{id}/emergency` (`emergency`; `identity.users.manage` at the unit, step-up, the escalation rule) marks at most two people (`identity.emergency.limit`), each a local person (`identity.emergency.not_local`) with a second factor (`identity.emergency.needs_factor`). The MFA policy always asks them for one and gives them no grace; SSO-only never applies to them. Each sign-in writes the security event `emergency_sign_in` and `identity.emergency_sign_in` at high severity; `GET /api/v1/security-alerts` (`identity.users.manage`) answers the last 24 hours, for the shell's banner.

Terms (TF-028, ADR-0049): the platform's documents come from the store at `platform/documents` (`StorePlatformDocuments`, read at most once a minute), a tenant's from `tenant_documents` (`TenantDocumentVersions`, kept a minute). A person who has not accepted the current version of each meets the required step `identity.terms.acceptance_required` before anything else, enrolment included; service accounts, impersonators and break-glass accounts never do. `GET /api/v1/me/terms` answers the versions to accept with their text; `POST /api/v1/me/terms/accept` (the versions read) records each `DocumentAcceptance`, and nothing when a newer one came meanwhile; `POST /api/v1/me/terms/decline` ends the session (`terms_declined`). `identity.documents.manage` (high risk): `GET` and `POST /api/v1/documents` (publish a new version of `key`), `POST /api/v1/documents/{key}/retire` (nobody is asked any more; the acceptances stay; open during the terms step), `GET /api/v1/documents/acceptances` and `/acceptances/export` (CSV).

Rate limits and the login's challenge (TF-072, ADR-0053): `POST /auth/login`, `POST /auth/passkey` and `POST /connect/token` are under the sign-in limit (10 a minute per address by default), and `POST /auth/recovery`, `POST /api/v1/users/{id}/recovery-link` and the control plane's administrator recovery under the recovery limit (5 an hour per account); the Protection module counts and refuses with 429 and `Retry-After`. The "Use your company login" answer is an answer of `/auth/login`, so it counts. After 5 failed sign-ins in 15 minutes from one address or for one login identifier (`ILoginChallenges` in Protection's contracts), a password sign-in needs `challenge`, the answer to `GET /auth/challenge`: without it the API answers 403 `identity.login.challenge_required` and checks nothing else; an answer that is wrong, expired or used answers 403 `identity.login.challenge_invalid`. A failure is counted for the address and the identifier; a success clears the identifier's count. Lockout counts as before, on top.

Model change: edit the entity, then `make ef-add MODULE=Identity NAME=<WhatChanged>`, `make format`, and commit `Data/Migrations`.

## Proving the signer, and identifiers never reused (TF-063, TF-219, ADR-0051)

`SignerAuthentication` implements Compliance's `ISignerAuthentication`: the first signature of a session (`sessions.signing_since` empty) asks for the login identifier, the password and the second factor the person has; later ones for the password, and the second factor when `compliance.signing.later_second_factor` is on. A person without a password, or held to their company login, signs after a fresh sign-in there (`POST /api/v1/me/reauthentication/sso`, which sets `sessions.provider_confirmed_at`), within the step-up window, one signature per sign-in. A wrong identifier or password counts against the login as a failed sign-in does (`identity.login_failed` with the reason `wrong_login_id_signature` or `wrong_password_signature`). Refused whatever the credentials: a token (`compliance.signature.token`), a service account (`service_account`), someone signed in as the person (`impersonation`), someone acting for another (`acting_for`), a break-glass account (`break_glass`).

Every principal's login identifier is reserved in `login_id_reservations` by a trigger on `principals`, and the reservation outlives the principal; an identifier never changes. Creating a person with a reserved identifier is refused (`identity.login_id.retired`, 409), and so is a company login's new account with one.
