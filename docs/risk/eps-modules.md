# Risk: EPS-modules, the eProcurement Suite's modules, and Requests and Intake

The task touched these requirements (classes from `docs/trace/risk.md`). It is documentation only: no product code changed, and the one tool changed is the requirements check.

The change is classed **high**: no requirement it touched is in a critical area.

**What could go wrong.** A new requirement could depend on a later product without an event, or a later slice, so that the plan could not be built in its order: Requests and Orders above all, since automatic orders run from Requests to Orders and a buyer's consolidation from Orders to Requests. A requirement could fall into no slice, or two. An automatic order could commit money that no approval and no check stood behind, or be made twice from one event. A requester could see another requester's request through an order line they share. A review could be skipped, or a request approved with a review still open. A licence code could not be one the kernel accepts. The module list, the ADR, the scopes, the map and section 7.2 could disagree about a module, its wave or its prefix, or a retired prefix could be given again. The requirements check could pass a real requirements document by because of its new exclusion. A leader's product, or a mandate's date, could be stated as fact when it is a vendor's claim or a date that moves.

**What proves it does not.** `make prd-check` passes: its 37 tests, then the check over every document, which holds every requirement in exactly one of section 7.2's 22 slices, none depending on one placed later except through an event, every dependency down the layers and along the process order (Orders depends on Requests' REQ-141, REQ-142, REQ-161 and REQ-162, and Requests on nothing of Orders'), and every requirement with criteria in the Given, When, Then form and at least one error case. Automatic orders are placed with PR6, after the catalogue and contract lines they need, and the shares with PR4, after the receipts they hear of. The criteria name the controls: an automatic order is submitted to the order approval configuration and issued only once approved, and a supplier on hold sends the line back to a buyer (ORD-162 AC1, AC4); one event makes one order (ORD-162 AC3); a buyer's selection is ordered all or nothing (ORD-161 AC3, REQ-161 AC3); a request is approved only when every review has approved, and a review without a reviewer refuses the submission (REQ-102 AC2, AC4); a requester asking for another's request through a shared line is refused (REQ-163 AC3). The feature codes have the form `area.feature` the kernel's `Feature` accepts. ADR-0058, the module list, the scopes, the map's section "Scopes changed after the split", `docs/prd/README.md` and section 7.2 name the same fifteen modules, waves and prefixes; `SRV-` is retired and `AUC-` reserved and unused in each. The check passes by a file named exactly `README.md`, and the new test proves a suite's README with an identifier in it is not read as a requirements document, while a requirements document is named `*-PRD.md` and still refused when the check does not know it. `make trace` passes with ADR-0058 known, 500 requirements and 1746 criteria, and S1 to S3 still complete. The research log marks every vendor's description as a vendor source, and the mandates' dates as read on 2026-10-29, to be confirmed against each tax authority when its country's feature is written (INV-141).

**Results.** make prd-check passed (37 tests; requests 26, orders 29, invoicing 39 and contracts 13 requirements; 22 slices); make trace passed (94 Python tests; 85 of 500 requirements and 289 of 1746 criteria with a test; S1 to S3 done with 31 exceptions, none missing); make format changed nothing; make security passed, the gate with nothing failing but the one approved exception, as on main (497 licences checked).

**What is left.** Every `[Decision]` default of the new requirements waits for the design session. V's slice plan does not yet name Purchasing's module skeleton, which the module list puts in V2. Each later module's place in the process order is proposed by its scope and fixed when its PRD is written (ADR-0042, decision 8).
