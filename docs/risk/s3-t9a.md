# Risk: S3 T9a, hardening the web surface

**Requirements touched:** TF-070, TF-071 and TF-072 (critical: Security); TF-060 and TF-061 (critical: Audit and compliance), for the control plane's own role and chain. TF-073 to TF-075 are T9b's.

**Headers and the policy (TF-070 AC1, AC3, AC4).** What could go wrong: a host or a path answers without the headers; a library needs inline code and the policy is quietly widened; a report endpoint is flooded or leaks what a page's address carried; a cookie is written without its flags. What proves it does not: a host test reads every header from the API and the control plane on a success, a refusal, an unknown path and a wrong method, and from the shell's own nginx configuration in its image's server, with a fresh nonce on each page and no `unsafe-inline` anywhere; in Chromium the shell's pages raise no violation and an injected script is blocked and its report reaches the endpoint (browser test); the endpoint's tests count both report forms, keep the page without its query, and refuse a flood; every cookie the code writes comes out Secure, HttpOnly and Strict, and a test finds no code writing the header around the policy. The browser test found two libraries that broke the policy, a scroll lock's style without the nonce and Zod's caught probe for eval, and both were fixed without widening it. Residual: HSTS reaches browsers only over TLS, which the laptop's ingress serves by its own certificate; on the laptop Chromium's reports through `report-to` do not reach the ingress, so its browser test reports through `report-uri`; the reports kept for the console live in each process.

**Origins (TF-070 AC2).** What could go wrong: any site's page reads a tenant's answers with the person's cookie; a removed origin keeps its access. What proves it does not: the tenant's list is empty by default and its format checked (a theory of accepted and refused origins); in memory and in Chromium an unlisted origin gets no CORS answer, a listed one does, and a removed one is refused again within the settings cache's 30 seconds (in-memory and browser tests). The session cookie is SameSite=Strict, so even a listed site's page never carries it. Residual: a tenant may list a site it should not; changing the list needs a recent sign-in and is audited as every setting is.

**Declared limits, rich text, file names and SQL (TF-071).** What could go wrong: a field takes any length or count and is used to exhaust memory or storage; a stored note carries a script; a file name carries a path, a control character or a misleading extension; SQL is built from a value. What proves it does not: the start-up check reads every endpoint's body through its validator and refuses to start a host with a field without a limit, and the host tests start every host (a unit test proves each kind of field caught, a nested and a per-item limit read, and the host refused); a request over a limit, in the body or the query, is a validation problem naming the field (tests); rich text is cleaned as it binds, and sixteen XSS forms, among them encoded schemes, SVG, MathML mutation and comments, lose their scripts while a formatted document keeps every allowed element (tests, with a sample field through a request); twenty hostile file names come out as safe display text (tests); the analyzer fails the build on each string-built form and passes parameterised ones, proven by a fixture project built with the repository's settings, and the product's three definitions that must name roles carry their reason. Residual: the analyzer does not follow a constant through a helper's parameter, so such a helper is marked with its reason and reviewed; tests and tools may build SQL.

**Rate limits and the login's check (TF-072).** What could go wrong: a password is guessed from one address or across many; a limit locks out the people it protects; the check needs a third party or can be replayed. What proves it does not: the eleventh sign-in in a minute from one address is refused with Retry-After, a principal over its API limit is refused, counted and audited at low severity, and a tenant's changed limit applies at once (tests); after five failures from an address or for an identifier the sign-in needs a challenge the server signed, which expires in five minutes and works once, and whose work doubles with each further failure, while lockout still applies on top (tests, and the browser test, which also proves no other host is asked). The smoke and the browser tests stay within the limits by waiting. Residual: the counters, failures and used answers live in each process, so with several replicas (S6) a limit is per replica until the shared store; the challenge's signing key is made at start unless configured, and T9b rotates it with the other keys.

**The control plane's role and chain (TF-060 AC2, TF-061 AC1, AC2).** What could go wrong: the control plane, as the superuser, changes its own schema or audit rows; its trail is altered with nothing to compare it to; its anchors are changed by the host they stand for. What proves it does not: on a database migrated first by the superuser and then prepared, the app role cannot alter a table, disable the guard, update, delete or truncate an event, create a table or a schema, and every object is the owner's (test); the chain is sealed by the unit's sealer, anchored in a container whose SAS refuses a delete and an overwrite with 403, verified by the read-only role, which can neither change an event nor read another table, and a tampered event is found by its identifier with a high-severity alert, the results recorded (test). Residual: on the laptop the container's protection is the SAS the control plane holds, not storage immutability; Azure's immutability policy is the first Azure deployment's requirement. The control plane's API still shares its secret with the fleet's admin connections; T9b gives the API and the fleet separate secrets and store tokens, so the API never holds the fleet's administrative database connection.
