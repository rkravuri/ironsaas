# Risk: S3 T10a, how code reaches main

The task touched these requirements (classes from `docs/trace/risk.md`):

| Requirement | Class | How it was touched |
|---|---|---|
| TF-076 Vulnerability and dependency management | critical (Security) | Dependency, licence, misconfiguration, rule and image scans through one gate with expiring exceptions; a CycloneDX bill of materials per image in the release and its validation pack; the monthly report; AC4 and AC5 added |
| TF-077 Secure development lifecycle | critical (Security) | Main protected so that it changes only through a pull request with every check green; the second developer's review as the process exception PE-1; threat models checked by the tests; the findings register with its escalation; coverage floors |
| TF-218 Validation support for regulated tenants | critical (Regulated-industry controls) | The validation pack carries each image's bill of materials, hashed in its manifest, and refuses a release without them; the release takes CI's results from the pull request that tested main's tree |
| TF-191 Continuous integration and delivery | high | The release runs nightly and on demand instead of on every push; CI runs in full on pull requests and builds the merge on main |

The change is classed **critical**.

**What could go wrong.** A change could reach main without its checks: a required check that never reports would block every merge, and a job skipped by mistake would count as green, so a broken change could merge. The release could publish images whose tests never ran, by taking the results of a run that tested another tree. A critical vulnerability could pass because a scanner read too little (Trivy read none of the transitive .NET packages before the lock files), because an exception never ran out, or because the gate misread a report. A licence that forbids our use could ship unnoticed. A module or an anonymous endpoint could be built without anyone thinking through its threats. Coverage could fall quietly. Instrumenting the assemblies for coverage could blind a rule that reads them, as it did the clock rule.

**What proves it does not.** GitHub refused a direct push and a force push to main, by the repository's administrator, recorded in `docs/security/branch-protection.md` (TF-077 AC1); the protection's tests name every setting that would let a change through, and prove every required check is a CI job and every job of a pull request's run is required, "What changed" among them so its failure cannot skip the rest into a pass (TF-077 AC1). The real Trivy over a lock file holding lodash 4.17.11 fails the gate naming the package and CVE-2019-10744, passes with unexpired exceptions and fails again the day they expire (Architecture `DependencyScanTests`, TF-076 AC1, AC2); the gate's tests cover high and medium findings, an exception's scope and its six-month limit, the same finding in many lock files, licences outside the policy, weak copyleft for named packages only, licence expressions, unreadable licences, and a rule finding named with its file and rule (TF-076 AC1, AC2, AC5). A release without a bill of materials per image, or with one that is not CycloneDX, is refused, and each is hashed in the pack's manifest (`validation_pack_test`, TF-076 AC3). A module or an anonymous endpoint without its threat model fails the architecture and host tests, which run over the real modules and hosts (TF-077 AC2). A high finding open 31 days is escalated and one open 30 is not (`security_report_test`, TF-077 AC3). Coverage below its floor, and a floor that falls without an exception, are refused, each file counted once across reports (`coverage_check_test`, TF-077 AC4). The clock rule now reads each project's own build output, and passes with coverage on. The release walks back along main's merges only while documents alone differ, and runs CI in full when no run covers the tree.

**Results.** make verify passed: 1175 .NET test cases, 389 Vitest, 148 scans, 92 Python, the gate with nothing failing, coverage at 90.35% and 85.80% against floors of 90 and 85; TF-076 has a test for every criterion (5 of 5) and TF-077 too (4 of 4), all passing, and 28 tests name ADR-0055. On the laptop the images built from the branch passed the smoke (23 of 23) and the browser tests (40 of 40) on echo, and the image scan with only the five exceptions approved at the review.

**What is left.** The review by a second developer waits for one (PE-1, re-checked 2027-04-24). The fleet image's Go findings are excepted until 2026-11-28, until a Docker CLI image built with Go 1.26.10 or later is two weeks old. Opengrep was not measured: this session refused to download and run its binary. Security monitoring and incident response are T10b's (TF-079). The Kerberos probe message of the chiseled images needs GSS encryption turned off in every unit's connection string, left to a maintenance task.
