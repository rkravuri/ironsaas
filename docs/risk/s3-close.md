# Risk: S3-close, exceptions, documentation and the closing notes

The task touched these requirements (classes from `docs/trace/risk.md`):

| Requirement | Class | How it was touched |
|---|---|---|
| TF-014 Single sign-on with OpenID Connect | critical (Identity and authentication) | AC10, new: a provider that cannot be reached is said in words at the start and at the callback, and no session or link is made; a .NET test and two page tests prove it, and no product code changed |
| TF-020 Sessions and tokens | critical (Sessions, tokens and service accounts) | AC3 is now named by T9b's rotation test, which proves it word for word; AC1's exception moves its home from S3 T4 to S7 |
| TF-018, TF-019, TF-023 | critical (Identity and authentication; Sessions, tokens and service accounts) | Exceptions with their homes, approved at the review on 2026-10-29: TF-018 AC3 and TF-019 AC1 to AC3 in S4, TF-023 AC2 and AC3 in S7 |
| TF-218 Validation support for regulated tenants | critical (Regulated-industry controls) | S3 becomes a done slice in the matrix, so every release's validation pack holds its criteria; the PRD's section 5a names GAMP 5 and ALCOA+ |

The change is classed **critical**.

**What could go wrong.** The matrix could call S3 done while a criterion of it has no test and no approved exception, so a release's validation pack would claim more than the tests prove. An exception could hide work that was meant to be built in S3, or name a home that never takes it. A requirement could fall out of every slice when S3's coverage table drops what S3 did not build. The documentation could send a newcomer down a path that no longer works, the first hour above all, now that an administrator must set up a second factor before any page; or the README could point the smoke at a tenant whose administrator a person uses, which the smoke would take over. A person whose company login is down could be left on a blank page, or with half a session.

**What proves it does not.** `make trace` passes with S1, S2 and S3 as done slices: 308 criteria, 277 with a test, 31 approved exceptions, none missing; it fails a done slice's criterion without either, and an exception a test now proves (S1's TF-020 AC3 row went with its test). Each exception names its home, and S4's and S7's plans or the PRD's section 7.1 name the same requirements; the parts of proven criteria that wait for S4 are listed beside the rows and in S4's plan. The requirements S3's table no longer holds are placed in section 7.1 (TF-015, TF-016, TF-024 and, at the review, TF-027 in S7; TF-078 in S4), and TF-134 is in S6, as ADR-0056 says, checked by `make prd-check`. The first hour was walked on a fresh tenant, golf: provisioning gave the invitation, the account was activated, the sign-in went to "Set up a second factor" before any page, a passkey in Chromium's virtual authenticator and the ten recovery codes led to the home page with its four openers, and Users listed the administrator and the smoke client; a fresh clone of the branch built with no warning. The 503 test drives the real callback after the provider went away and checks the answer's words, that no session cookie is set and that no session row and no link exist; the page tests check the words, the correlation id, and that the sign-in page stays with nothing left behind. `make verify` passed on the branch; on main after the merge, `make verify`, `make smoke TENANT=echo`, `make e2e TENANT=echo` and the release run must pass before `s3-done` is tagged.
