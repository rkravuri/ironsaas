# Risk: S3 T8, evidence exports, second approval for sensitive changes, validation pack per release

**Requirements touched:** TF-067 (critical: Audit and compliance), TF-068 (critical: Audit and compliance), TF-218 (critical: Regulated-industry controls). TF-247 is not built; ADR-0052 records how S5 extends T8's pending change into it.

**Evidence packs (TF-067).** What could go wrong: a pack shows more than an auditor should get, a secret leaks into it, it states a period's end wrongly, it is altered after it is made, or someone without the right downloads one. What proves it does not: the permission is high risk and refused without it (Compliance tests and the browser test); a company login's secret is never in the database (ADR-0048), so the access list cannot carry it, and the settings document reads the security settings by name, none of them a secret; the state at the period's end is rebuilt from the sealed field history, and tests prove that people, roles and settings changed after the period show as they stood; every file's SHA-256 is in the manifest, recomputed by a test from the ZIP, and the head names the control plane's anchor at that position, matched by a test; the bytes are checked against the pack's hash before a download, the link is the requester's own, once, for five minutes, and asking, making and downloading are audited with the requester (tests and the browser test). Residual: the field history began with T7, so a change made before T7 deployed and after a period's end is not undone; each table says so. Backups have no drills yet; the document says so.

**Four-eyes (TF-068).** What could go wrong: a governed save bypasses the gate; the requester, an impersonator, someone acting for another, a service account or a break-glass account approves; a change applies over a newer one; one administrator switches the control off; a staged secret leaks into the change's row. What proves it does not: every area's services ask `IFourEyes` before they write, the same path an approval applies through, and tests hold a save in each area (roles, assignments, single sign-on, retention, legal holds, the MFA and password settings, the signing policy, the four-eyes settings); the refusals are tests, each audited at high severity; the comparison with the subject's state now sends a stale change back for review (a test); while any area is listed the four-eyes settings are governed too (a test); the secret waits in the store under a staging id (a test reads the row). The browser test proves the whole path with two people on a real unit. Residual: the routes of the shell ask only for a signed-in person and the API decides what each sees; a change approved by someone who lost the permission since is refused at approval, not before.

**Validation pack (TF-218).** What could go wrong: a release ships with an untested requirement, a failing test, or an installation that differs from the code; a tenant gets the pack of another version. What proves it does not: the pack is built from the run's matrix and fails the release on a gap without an approved exception, a failed test, a trace problem or a failed installation check (the trace tool's tests, with a gap failing and an exception passing); the installation record checks the version, the catalogue, the migrations per schema and the seeds against the code (its tests); the fleet copies the pack of exactly the version the image says (a Fleet test), and the console serves only that one (Compliance tests, the browser test). Residual: a release's own integration stage runs before its pack exists, so its browser test of the download is skipped there and runs on the laptop and against the next release.
