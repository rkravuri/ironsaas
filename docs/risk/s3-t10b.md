# Risk: S3 T10b, security monitoring and incident response

The task touched these requirements (classes from `docs/trace/risk.md`):

| Requirement | Class | How it was touched |
|---|---|---|
| TF-079 Security monitoring and incident response | critical (Security) | Alert rules with thresholds over the audit trail every minute, in each unit and in the control plane; a failing rule as an alert; the alerts copied to the control plane and sent to Alertmanager; incidents with their timeline, the 72-hour notice and the 10-day review; the runbook |
| TF-060 Append-only audit log | critical (Audit and compliance) | Refusals and events before sign-in record the client's address; the roles' and acceptances' exports are audited with their rows; the seed's change of a system role is audited; six security event kinds declared; a summary event for policy reports |
| TF-064 Audit search, export and archive | critical (Audit and compliance) | The search filters by target and by address, and the shell's audit page opens a link's filters; its date filter sent an operator the API refuses, now fixed |
| TF-130 Distributed tracing and correlation | high | AC4: the trace exporter's own processor never holds a request and counts every span it loses |
| TF-209 Developer documentation and ADRs | high | AC3 and AC4: every alert names a section of the runbook, which a test checks exists |

The change is classed **critical**.

**What could go wrong.** An attack could go unseen: a rule silently skipped because its configuration is wrong, an
evaluation that throws, the worker stopped, or an event type a rule counts that no module writes or declares. A tenant
administrator could loosen or silence the rules before acting. One burst could flood the people paged, or the same
events raise alert after alert. An alert's link could lead to the wrong events, so the person investigating misreads it.
A unit could send alerts as another tenant, or carry a person's details out to the control plane and the pager. A
breach notice could be forgotten past its 72 hours, or a review never written. A collector that hangs could hold every
request of a unit, or lose spans unseen.

**What proves it does not.** A misconfigured value, a misspelt key or rule name, and an evaluation that throws each
make the rule failing with its reason and an alert of its own, while the other rules run (`RuleEvaluationTests`, TF-079
AC4); a gap of an hour between passes is an alert, and a rule for each event catches up on it; a host test proves every
rule of a unit and of the control plane counts types its host declares, and the Alert rules page on echo showed every
rule running. 100 denials by one principal in 10 minutes raise an alert and 99 do not (AC1); a burst continues in the
same alert under the cool-down and no event counts twice; an export of 10,001 rows raises an alert and one of 10,000
does not (AC3). A tenant's looser value is refused naming its bound, and an operator's later tightening wins over a
tenant's value. The alert's search finds exactly its 100 denials through the real audit endpoint, on the laptop too
(the smoke's `security-alert` step, which also found the copy in the control plane and the alert in Alertmanager). A
copy is kept only for the sending unit client's own tenant, and a login identifier reaches the control plane masked.
An incident runs from its declaration to its review through the API and the make targets (AC2); it cannot close with
a tenant untold; a missing review is escalated once on day 10 and a missing notice when its 72 hours are up. With the
pinned collector paused and stopped, requests stay under a second, and every span is either sent or counted as dropped
(`LostSpanTests`, TF-130 AC4). Every rule's runbook section exists (`RunbookTests`, TF-209 AC3, AC4).

**Results.** make verify passed: 1209 .NET test cases, 395 Vitest, 152 scans, 92 Python, the gate with nothing failing,
coverage at 90.77% and 85.66% against floors of 90 and 85. In its last run the format check found whitespace in a new
test; after `make format` the steps after it (the format check, the security gate, coverage and trace) ran again and
passed. TF-079 has a test for each criterion (AC1 10, AC2 4, AC3 2, AC4 10), TF-130 AC4 and TF-209 AC3 and AC4 one or
more, and 45 tests name ADR-0056. On the laptop, with images built from the branch, acme, bravo and echo updated, the
smoke passed (24 of 24) and the browser tests (42 of 42) on echo, and one incident was declared, noted, told, refused an
early close, closed and reviewed by hand.

**What is left.** Alert rules over metrics, dashboards and the on-call channel with its fallback are TF-134's (S6); the
laptop's Alertmanager pages nobody. The operator has make targets and the API for incidents and alerts, not a console
page. One alert per pass for a rule of each event: several impersonations by one person in a minute are one alert with
their count.
