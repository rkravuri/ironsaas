# Runbook: the laptop platform

Everything Foundation needs runs on the developer laptop in containers (PRD section 3.3, decision D-14, ADR-0005): the platform services, the control plane, and one Compose project per tenant unit. This runbook is the reference for starting, reaching, changing and resetting all of it. The first hour from a fresh checkout is in the README; this page is what you come back to.

## 1. Prerequisites

- WSL 2 with Ubuntu, Docker (Engine inside WSL, or Docker Desktop with WSL integration), `docker compose version` 2.x.
- .NET SDK 10 and Node.js 26, both inside WSL. `which npm` must not point under `/mnt/c`: the Windows npm runs through `cmd.exe`, which cannot work from a WSL path, and installs Windows binaries into `node_modules`.
- Ports 80, 443, 5432, 8200, 10000, 3200, 4317 and 4318 free; 5100, 5101 and 5200 free when the hosts run from source.
- Memory: about 2.5 GB for the platform with telemetry, about 0.5 GB per tenant unit, about 1 GB for the control plane as containers. The reference machine is a laptop with 16 GB of memory, with WSL limited to 12 GB and 8 GB of swap.
- WSL's memory and swap, in `%UserProfile%\.wslconfig` on Windows, under `[wsl2]`, applied after `wsl --shutdown`: on the reference machine `memory=12GB` and `swap=8GB`; on a 32 GB machine `memory=20GB` and `swap=8GB`. `memory` must stay below the machine's own memory. Without the file WSL takes half the machine's memory and a quarter of that as swap, which is too little: measured on 2026-10-19 on the reference machine with those defaults (7.4 GB and 2 GB of swap), with the platform, telemetry, the control plane as containers and four units up, `make test`, `make shell-check`, `make shell-a11y` and `make format` passed, but memory use peaked at 6.9 GB and the swap was full. That is the pressure under which WSL restarted on 2026-10-18 and took the old in-memory store with it.
- Optional: `mkcert` (`make certs`), Playwright browsers (`cd shell && npm run e2e:install`).

## 3. The map

| Service | Address | Credentials |
|---|---|---|
| Traefik dashboard | http://traefik.localhost | none |
| PostgreSQL 19 | `localhost:5432`, database `postgres` (platform), `control`, one per tenant | `POSTGRES_SUPERUSER` and its password in `infra/compose/.env` |
| Blob storage (Azurite) | `http://localhost:10000/<account>`, one container per tenant | `BLOB_ACCOUNT_NAME`, `BLOB_ACCOUNT_KEY` in `.env` |
| OpenBao | http://localhost:8200 and http://openbao.localhost, mount `secret` | `OPENBAO_ROOT_TOKEN` in `.env`, written by the first `make up`; `OPENBAO_UNSEAL_KEY` and `OPENBAO_RECOVERY_KEY` beside it |
| Grafana | http://grafana.localhost | viewer without login; `admin` with `GRAFANA_ADMIN_PASSWORD` |
| Prometheus, Tempo, Loki | http://prometheus.localhost, http://tempo.localhost (`localhost:3200`), `localhost:3100` | none |
| OTLP for hosts on the laptop | `localhost:4317` (gRPC), `localhost:4318` (HTTP) | none |
| Control plane API | http://localhost:5200 (from source or as container), http://control.localhost (container) | operator client credentials, `DEV_OPERATOR_SECRET` in the Makefile |
| A tenant unit | `http(s)://<slug>.localhost`: `/api`, `/auth`, `/connect`, `/health`, `/.well-known` to its API, everything else to its shell | the tenant's accounts |

Inside the Docker network `foundation` the services are `postgres:5432`, `blob:10000`, `openbao:8200`, `otel-collector:4317`, `tempo:3200`, `loki:3100`, `prometheus:9090`, `traefik:80`. Tenant units are separate Compose projects `tenant-<slug>` that join this network; `docker compose ls` lists them.

Hostnames: browsers resolve every `*.localhost` name to the laptop by themselves. Command line tools in WSL do not; run `make hosts` once and add the line to `/etc/hosts`, or call `http://localhost` with a `Host:` header, as the scripts do.

TLS: the `websecure` entry point has TLS on. Without `make certs` Traefik uses its own self-signed certificate, which the browser warns about once; with mkcert, trust its root on Windows as the script explains. `http://` works too, and Chrome treats `*.localhost` as secure, so the session cookie is accepted there as well.

## 4. Secrets

Every unit, the control plane included, gets its configuration at start from one secret in OpenBao: `secret/<path>/unit` with keys that are configuration keys (`ConnectionStrings:Database`, `Storage:ContainerSasUrl`, `Tokens:SigningKeyPem`, `Identity:FactorKey`, ...). The signing key and the factor key are made once and kept by every update: the factor key seals the second factors' secrets, so a new one would leave every authenticator app unreadable (ADR-0047). `make secret-dev` and `make secret-control` keep theirs in `infra/compose/.dev-factor-key` and `.control-factor-key` (git-ignored), beside the signing keys. Its environment holds only `Secrets__Address`, `Secrets__Token`, `Secrets__Path` and the tenant binding (ADR-0016). An explicit environment variable wins over the secret.

The fleet writes `tenants/<slug>/database` (the role passwords), `tenants/<slug>/storage` (the signed container URL), `tenants/<slug>/unit` (the unit's configuration) and `tenants/<slug>/fleet` (the unit token, the smoke client's secret) per tenant (ADR-0018). A job's link waits at `tenants/<slug>/handover/<job id>` until the report gives it to the operator who asked, or until it expires (ADR-0046). A unit writes its single sign-on providers' client secrets itself, at `tenants/<slug>/sso/<provider id>`, the one path its token may write (ADR-0048). `make secret-dev` writes the dev tenant's by hand; `make secret-control` writes the control plane's, with `localhost` hosts for the hosts from source and `postgres`/`blob` hosts when `make up-control` writes it for the containers.

OpenBao runs in server mode and keeps its data on the volume `openbao-data` (ADR-0028): `make down`, a restart of its container and a restart of WSL keep every secret. The configuration is `infra/compose/openbao/openbao.hcl`. At every start the static seal unseals the store with `OPENBAO_UNSEAL_KEY` from `.env`, which `make env` generates (and adds to an older `.env`). The first `make up` initialises the store: `infra/compose/scripts/init-store.sh` initialises it with one recovery share, writes `OPENBAO_ROOT_TOKEN` and `OPENBAO_RECOVERY_KEY` into `.env`, and enables KV version 2 at `secret`. Before either, the script waits for the store by its health endpoint (`/v1/sys/health`) for up to 90 seconds and says every 10 seconds where it stands: a container Docker calls healthy may still be starting its storage, and a sealed store still counts as healthy to Docker. If the store is not ready in time, the script prints the container's health state and its last 50 log lines, then fails (section 10). Every later `make up` checks that the store is unsealed and that the token opens it, and says what to do if not (section 10). The three lines belong to the volume: keep them together, and never commit `.env`. `make reset` deletes the volume and the token and recovery key lines together; the next `make up` initialises a new, empty store.

If the store lost its data anyway, the recovery is two commands: `make up-control` writes the control plane's secret again, and `make update-unit TENANT=<slug>` heals each unit (section 5).

## 5. Tenant units

`make provision TENANT=acme [ADMIN=admin@acme.localhost]` registers the tenant with the hostname `acme.localhost` and asks the fleet to provision it, then follows the job and prints every step with its duration, and at the end the first administrator's invitation link, once: the control plane gives it to the operator who asked and deletes it, and it is in no job output or log (ADR-0046). The job's eight steps are reserve, database, storage, secrets, migrate, seed, unit, verify. A failed step is printed with its error; fix the cause and run the same command again, and the job continues from that step. `GET /api/v1/tenants/acme/provisioning` on the control plane shows the job and its steps.

`make update-unit TENANT=acme` runs database, storage, secrets, migrate, seed, unit and verify (ADR-0028): it re-runs migrate and seed from the current images and re-applies the unit, which is how a unit takes a new image (`make images` first) or a changed template, and it heals a unit whose secrets the store lost. With the secrets in place the first three steps change nothing; with them lost, they make new role passwords, a new container signature and a new unit token, and the unit restarts with them. A healed tenant keeps its data and serves its users, and its smoke client takes the new secret from the seed, so a client credentials token works again. Its administrator's password is not in the store any more: the smoke's recovery step sets a new one on its next run, or `make recover-admin` gives a link for a person to use (below). The seed re-issues the administrator's invitation while it is still unaccepted. `make deprovision TENANT=acme` takes the unit's containers down and keeps its database, container and secrets.

**Plans.** `make apply-plan TENANT=echo PLAN=Enterprise` prints the preview (the plan and grace days before and after, every module and feature added, removed or changed, and the warnings), applies it, and says whether the store holds the new revision. `DRY_RUN=1` stops after the preview; `STARTS` and `ENDS` set the subscription's dates. The control plane seeds two plans: `standard` (no role export and import, 14 grace days) and `enterprise` (with them, 30 grace days). A new tenant starts on `standard` unless it is created with another; a tenant created before A4 has no entitlements until a plan is applied, so it has no role export and import. The unit reads the change within 30 seconds and the shell within a minute; `GET /api/v1/tenants/<slug>/entitlements` and `/entitlements/history` on the control plane show what it holds and every change with its operator. In the tenant, the console's Subscription page shows the plan, the modules and features with their status and dates, and the seats.

**A tenant administrator who cannot sign in** (ADR-0046). The tenant's own administrators come first: one with `identity.users.manage` at the person's unit unlocks a locked login, or issues a recovery link, on the person's record under Users. When nobody in the tenant can, because the last administrator lost their password or the store that kept the smoke's password was healed, the operator asks for a link:

```
make recover-admin TENANT=acme REASON="The administrator lost their password (ticket 4711)"
```

`ADMIN=someone@acme.localhost` names another tenant administrator than the first. The call is `POST /api/v1/tenants/{slug}/administrator-recovery` with `reason` (and `login_id`) on the control plane, which needs `tenancy.administrators.recover` (the control plane's administrators hold it after `make seed-control`). The fleet runs the unit's `recover-admin` command, which issues the link only for an active tenant administrator of the whole tenant. At the end the command prints the link, `https://acme.localhost/recovery#<code>`, once: the control plane gives it only to the operator who asked, deletes it, and keeps it in no job output or log, so give it to the administrator at once, and ask again if it is lost. It works once, for 15 minutes; a newer link replaces it, and using it ends all their sessions. The control plane's audit trail records the request, and the tenant's own trail and the administrator's Security activity record the link with your name and the reason. An administrator who is still Invited needs the invitation again instead: `make update-unit TENANT=acme`, whose seed re-issues it.

**Resetting a tenant administrator's second factors** (ADR-0047). An administrator who lost the device that holds their authenticator app or passkey, and has no recovery code left, cannot sign in even with their password. Another tenant administrator who holds every permission they hold resets their factors on their user record ("Reset factors", with a reason, after confirming it is them). When there is none, the operator does it with the recovery:

```
make recover-admin TENANT=acme REASON="Lost phone and password (ticket 4712)" RESET_FACTORS=1
```

The request carries `reset_factors: true`; the unit's `recover-admin` issues the link, removes every second factor and recovery code of the administrator, and ends their sessions, in one transaction. The job's output says the factors were reset. Both audit trails record it with your name and the reason, and the administrator's Security activity shows "Second factors reset". The administrator sets a new password with the link, signs in with it, and, since the policy requires a factor of a tenant administrator, sets one up at once before any page, receiving new recovery codes. The smoke sets the administrator's password with the operator's recovery on every run and keeps it, with their authenticator app's key (`administrator_totp_secret`), in `secret/tenants/<slug>/smoke`, which `make e2e` reads. It resets the factors this way only when it keeps no key or the unit refuses the one it keeps, and then enrols a new app and keeps its key.

**Settings.** The tenant's settings are the tenant's: its administrators change them on the console's Settings page (`/console/settings`), for the whole organisation or for a unit, and each person sets their colour scheme and density in My profile (ADR-0036). They live in the unit's database, so nothing in the control plane or the store changes them. `GET /api/v1/settings?scope=tenant` and `/api/v1/settings/{key}/history?scope=tenant` on the unit show the values and every change with its author.

**Flags and kill switches.** `make flag KEY=flags.example_tone VALUE=warm TENANT=echo` sets the flag's one unconditional rule for the tenant (without `TENANT`, for the platform), keeps its other rules, and prints the rule and the flag's revision. Scopes below the tenant, percentages and attributes go through `PUT /api/v1/flags/{key}/rules` on the control plane; `GET /api/v1/flags`, `/flags/{key}/rules` and `/flags/{key}/history` show the flags, their rules and every change with its operator.

`make kill-switch PATH=imports ON=true REASON="A fault in role import is being fixed; back this afternoon."` stops a path for the whole platform, with one write to `platform/flags`; `TENANT=echo` stops it for one tenant. Only the control plane's operators may (`tenancy.kill_switches.manage`), and the reason is required: the tenant's administrators read it in the banner at the top of every page. Within 30 seconds the units refuse the path with 503 `flags.killed`; within a minute the banner shows and the shell hides what the path offers (Import on the Roles page for `imports`). `ON=false` with a reason turns it off the same way. `GET /api/v1/kill-switches` shows each switch, since when, why, and the tenants it is on for. The paths are `email`, `webhooks`, `sms`, `ai`, `push` and `imports`; only `imports` is wired in S2.

A kill switch stays on while the store does not answer, and through a restart: the unit keeps the last rules it read, without expiry. A unit that has never read any rules runs on the code defaults, with nothing stopped, and alerts (section 10).

**A hostname no unit serves.** The ingress answers it itself with `404 page not found`, over HTTP and HTTPS, and no unit receives the request: Traefik routes a request only to the unit whose hostname it names (TF-003 AC3, ADR-0019). Checked by hand on 2026-10-21 (S3 T1), with the units acme, bravo, echo and smoke running: `curl -sk -H 'Host: nobody.localhost' https://localhost/api/v1/me` and the same over `http` answered 404 `404 page not found`, while `https://echo.localhost/health/live` answered 200.

What the fleet renders is in `infra/compose/units/<slug>/` (git-ignored): one `compose.yaml` from the embedded template and the unit's `.env`. `docker compose -p tenant-acme ps`, `logs` and `images` work on it directly; `images` is the quick way to confirm a unit runs the image you just built.

**A company login (single sign-on, ADR-0048).** A tenant administrator connects one in the console, under Single sign-on: a preset fills the discovery address (Microsoft Entra ID from the directory (tenant) ID, Okta from its domain, Google's fixed), the client identifier and secret come from the provider, and the provider must list `https://<tenant hostname>/sso/callback` as a redirect URI, which the page shows with a copy button. "Test connection" says in words what works before anything is saved. The secret goes to the store, never the database. Units provisioned before S3 T4 need `make update-unit TENANT=<slug>` once, so their token may write it.

**The test provider.** `make test-provider` starts navikt's mock-oauth2-server (profile `sso`, capped at 300 MB) behind the ingress at `http://idp.localhost`; any first path segment is an issuer of its own, so `http://idp.localhost/<anything>/.well-known/openid-configuration` is a provider ready to connect. Its login page takes a user name and the claims of the sign-in as JSON, for example `{"email": "ada@example.test", "email_verified": true, "name": "Ada", "groups": ["buyers"], "amr": ["pwd", "mfa"]}`. Traefik answers `idp.localhost` inside the platform network too, so a unit's API reaches the provider at the same address and issuer as the browser: after pulling S3 T4, `make up` once recreates Traefik with that alias. Its keys are made at its start: a restart gives new ones, which a unit reads again at the first token that names one.

**Sessions** (ADR-0049). Each person sees and ends their own sessions in My profile, under Sessions. A tenant's administrators with `identity.sessions.manage` see everyone's live sessions on the console's Sessions page (`/console/sessions`), with how many people are signed in now and the last days' summary, and end any one with a reason after confirming it is them. The person's next request is refused with `auth.session_ended`, and their Security activity and the audit trail name who ended it and why. The tenant's setting `identity.session.concurrent_limit` (console, Settings; 0 is no limit) ends a person's oldest session at a sign-in past it, and that session's next page says so.

**Revoking after an incident** (TF-029, ADR-0049). When a person's password, device or a service account's secret may be in the wrong hands, revoke that principal: "Revoke everything" on their user record, with a reason. When the whole tenant may be affected, revoke everything of the tenant on the console's Sessions page: type the tenant's identifier and a reason. Both need a recent confirmation that it is you. Every session the revocation covers ends at once, and every token issued before it is refused (`auth.session_revoked`, `auth.token_revoked`) within a minute on every API process: each keeps the tenant's revocation time for at most 60 seconds. The tenant-wide one signs you out too. Then:

1. Look at what happened: the console's Audit trail, filtered to `severity` high, lists the revocation, emergency sign-ins and break-glass accesses; a person's Security activity lists theirs.
2. Change what leaked: the person sets a new password with a recovery link (their record, "Issue a recovery link"), a lost device's factors are reset ("Reset factors"), and a service account gets a new secret from the seed (`make update-unit TENANT=<slug>` for the smoke client).
3. Clients sign in again: a person at the login page, a client with a new token; a token asked for in the same second as the revocation is refused too, so a client that retries at once waits a second.

**Signing in as a person, as the operator** (TF-025, ADR-0049). For support, with the tenant's consent (`identity.impersonation.operator_allowed`, on by default, on the console's Settings page):

```
make impersonate TENANT=acme LOGIN=pat@acme.localhost REASON="Pat cannot see the March orders (ticket 4713)" MINUTES=30
```

The call is `POST /api/v1/tenants/{slug}/impersonation` on the control plane (`tenancy.impersonation.start`, critical, with a fresh token). The fleet runs the unit's `impersonate` command and the script prints your link, `https://acme.localhost/sign-in-link#<code>`, once: open it at once in a private window, as it works once, within 15 minutes. The shell then runs as the person under a band that names you, the reason and the end; "End" in the band, or the time, signs you out, since you have no session of your own in the unit. You cannot confirm it is you there, so nothing behind step-up, no signature and no second approval is possible, nor the person's password, factors, sessions or terms. The tenant's audit trail names you on every action, and the person's Security activity shows who, when and why. Checked on echo on 2026-10-22: the link signed in once and a second use answered 404, step-up answered 403, and "End" answered 204.

**Break-glass** (TF-026, ADR-0049). When a tenant needs the operator's hands and nobody in it can act, two operators open a time-limited account in its unit. The control plane seeds two: `operator` and `operator-two` (`make seed-control`, or `make up-control`).

```
make break-glass-request TENANT=acme TICKET=INC-1 REASON="Orders stuck in approval since 09:00" MINUTES=60
make break-glass-approve ID=<id>     # as operator-two, within 30 minutes
make break-glass-link ID=<id>        # as the operator who asked: the sign-in link, once
make break-glass-end ID=<id>         # when the work is done, before its time
make break-glass-show ID=<id>        # where it stands, and the review once it ended
```

The request names a ticket and a reason and waits for a second operator, never the one who asked; unapproved after 30 minutes it expires, and an approval then is refused. On approval the fleet opens the account `break-glass-<12 hex>@break-glass.invalid` with the role `break-glass` (every permission but the critical ones) until the time asked, at most 240 minutes. The link is printed once, valid 15 minutes: open it in a private window. At its time, or at `make break-glass-end`, the fleet closes the account and ends its sessions, and the control plane keeps the review: every action of the account, in order. The fleet host does this every minute, so `make break-glass-show` says ended a minute or two later. The tenant's audit trail records each step at high severity with both operators, the ticket and the reason. Checked on echo on 2026-10-22: requested, approved by `operator-two`, the link given once and refused the second time, ended early, and ended with its review 20 seconds after.

**Emergency accounts** (ADR-0048, ADR-0049). A tenant that signs in through its company login keeps up to two local accounts for when the provider is down: an administrator marks them with "Make emergency account" on the user record. Each must have a second factor, always signs in with password and factor, and is never held to single sign-on only. Every sign-in with one raises an alert: the person's Security activity, the audit trail at high severity, and a banner for the tenant's administrators for 24 hours.

**Terms and documents** (TF-028, ADR-0049). The platform's terms of service and privacy notice are the operator's:

```
make platform-document KEY=terms_of_service TITLE="Terms of service" FILE=path/to/terms.md
```

writes a new version to the store (`platform/documents`), and every person of every unit must accept it at their next request, within a minute. A tenant's administrators publish their own documents, see who accepted which version, export the acceptances and retire a document on the console's Documents page (`/console/documents`). A person who declines is signed out and asked again at the next sign-in. Units provisioned before S3 T5 need `make update-unit TENANT=<slug>` once, so their token may read `platform/documents`.

## 6. The control plane

From source, for daily work: `make secret-control && make migrate-control && make seed-control` once, then `make run-control` (API on :5200) and `make run-fleet` (the fleet worker with the Compose runtime, driving this machine's Docker) in two terminals. The seed creates the `operator` account (tenant-administrator), `operator-two` (tenant-administrator, the second operator break-glass needs) and the `smoke-reader` account (service-default, for the smoke's denial case); re-run `make seed-control` after pulling a change that adds accounts.

As containers, as the pipeline runs it: `make up-control` writes the control secret with container hosts, migrates and seeds the control plane's database with the image (so a new image's migrations and permissions are in place before it serves), and starts `control-api` and `fleet` from the images. The two cannot run beside the source processes: stop `make run-control` and `make run-fleet` first (port 5200), and run `make secret-control` again before going back to source.

## 7. The dev tenant from source

For work on a module without a provisioned tenant: `make migrate`, `make seed` (system roles, the administrator `admin@dev.localhost` with its invitation link on the console, the `smoke-client`), then `make run-api` on :5100 and `make run-worker` on :5101, bound to tenant `dev`. `make secret-dev` and `make run-api-secrets` run the same API the way a unit runs, from its secret. For shell work, `make shell-install` once, then `make shell-dev`: Vite on :5173 proxies the API paths to :5100, so the session cookie is first-party.

## 8. Proving a change

- `make test`: the unit and integration tests. It starts one PostgreSQL, one Azurite and one OpenBao for the run (`tests/test-services.sh`, containers `iron-test-postgres`, `iron-test-azurite` and `iron-test-openbao` on loopback ports, pulled first if missing), runs four test projects at a time, each in a database, blob containers and a store mount of its own, and removes the three whatever the result. Docker must be running. Measured on the reference machine with the stack up, straight after `make shell-a11y`: about a minute, peak memory 8.6 GB against 10.0 GB and some forty containers before the services were shared. `TEST_PARALLEL=n` changes the four.
- `make shell-check`: lint, Prettier's check, the type check, the tests and the build of the shell. `make format` runs `dotnet format` and Prettier; run it before a commit.
- `make shell-a11y`: the gallery built and scanned in both schemes and densities; no stack needed. Its screenshots land in `shell/test-results/a11y/`, the browser tests' in `shell/test-results/e2e/`; each run empties only its own folder.
- `make smoke [TENANT=x]`: twenty steps against the live stack with the control plane and the fleet running and the telemetry profile up; provisions the `smoke` tenant (or `TENANT`) once and reuses it; writes `smoke-report.json`; keeps the administrator's password at `secret/tenants/<tenant>/smoke`. Its `recovery` step runs the operator's recovery on every run (ADR-0046): a link with the run's reason, used once to set a new password, refused the second time, the earlier password refused, the reason in both audit trails. So the smoke ends knowing the administrator's password even when it started without it, after a heal or an invitation accepted by hand. The last three steps take about two minutes: `scoped-role` (a unit of the run's own with a person who reads its users; they list only that unit's people, and the tenant's administrator is not found), `plan-change` (Standard until role export is refused, then the tenant's own plan until it works; a tenant on Standard goes the other way) and `kill-switch` (`kill.imports` on until a dry-run import answers `flags.killed`, then off; a tenant on Standard borrows Enterprise for the step). Each restores the tenant, also when it fails, and reports each wait; `scoped-role` deactivates the person it made, and any reader earlier runs left active. Then `second-factor` (a person of the run with an authenticator app and recovery codes, ADR-0047), `single-sign-on` (the tenant's "Smoke test provider" tested and connected, and a new person of the run signed in through it and created at that sign-in, ADR-0048), `end-session` (an administrator ends a person's session with a reason; its next request answers `auth.session_ended`, and the audit trail has the reason) and `revoke-person` (everything of a person with two sessions revoked; both answer `auth.session_revoked`), each deactivating the person it made (ADR-0049).
- `make e2e [TENANT=x]`: the Playwright tests against `https://<tenant>.localhost` with that administrator, read from `secret/tenants/<tenant>/smoke` (browsers once with `cd shell && npm run e2e:install`; `E2E_BASE_URL` points them elsewhere). Run `make smoke` with the same `TENANT` first. Each run works in a unit of its own, `E2E run <run>` under the root, with its branches, people and assignments inside it (`infra/compose/scripts/e2e-data.py`), and at the end, whatever the result, deactivates the people homed in the browser tests' units (this run's, and earlier runs' still active) and then the run's units. A run never sees what an earlier one left, and leaves no active people behind.
- `make integration [TENANT=x]`: the pipeline's stage on this machine: platform and control plane from images, the control database migrated and seeded through the control-plane image, then the smoke, its twenty steps (`TENANT=echo`, or `TENANT=smoke` on a laptop whose `acme` administrator has been accepted by hand).

## 9. Known limits of the laptop stack

- A unit healed after a lost store has new credentials; its administrator's password is gone from the store until the smoke's next run or `make recover-admin` (section 5). Its factor key is new too: authenticator apps enrolled before the loss no longer verify, and their people need a reset of their factors (section 5), while passkeys keep working (ADR-0047).
- The browser tests' tenant names the roles it requires a second factor of (the tenant administrator and `e2e-mfa`), set by `e2e-data.py`; the default policy, every role holding a high-risk or critical permission, is proven by the .NET tests (ADR-0047).
- PostgreSQL is the 19 release candidate until the GA image; an RC to GA change can require `make reset`.
- Azurite implements most of the Azure Blob API, not all of it. Reading container properties is refused under a container signature, so the units check their container by listing one page instead.
- Tenant units share the platform network; isolation between tenants is the database roles, the container signatures and the unit tokens (proven by the Fleet tests), not the network. Network policies arrive on Kubernetes.
- The chiseled images print `Cannot load library libgssapi_krb5.so.2` once at start: Npgsql probes for Kerberos, which the image does not carry; the connection uses SCRAM and works.
- A platform document published with `make platform-document` holds every person of every unit, the smoke's and the browser tests' administrator too, until they accept it: accept it once in the browser as each tenant's administrator before `make smoke` and `make e2e`. The browser tests' own terms are a tenant document of the run, retired at its end.
- The tree of a tenant the browser tests run on gathers one inactive `E2E run <run>` unit per run, and the smoke one inactive `Smoke <run>` unit per run, with their people deactivated since S3 T2: no API deletes a unit yet.

## 10. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `make up` ends with `tempo did not become ready` | `make logs SERVICE=tempo`; usually a configuration error after a version bump |
| `make up` stops on a service with a health timeout | `make logs SERVICE=<name>`; most often a port is taken on the laptop |
| Tenant units restart again and again; `docker logs tenant-<slug>-api-1` says `The secret store refused to read 'tenants/<slug>/unit': 403` | The store lost its data or was replaced (a store from before ADR-0028, or a `make reset` under running units): `make up-control` writes the control plane's secret, then `make update-unit TENANT=<slug>` for each unit heals it (section 5). For the smoke, provision a fresh tenant |
| `make up` ends with `OpenBao at http://localhost:8200 is not ready after 90 seconds` | The lines above it are the container's state, its health check and the end of its log. `no answer` with a container that is `restarting` or `exited`: the log says why the server stopped, usually its configuration or its volume. A server still starting on a slow machine: `make up` again |
| `make up` ends with `Initialising the store ... did not answer within 60 seconds` | The store may have initialised without handing over its root token. Run `make up` again: if it says `.env` has no `OPENBAO_ROOT_TOKEN`, `make reset` starts over (a new store holds nothing yet) |
| `make up` ends with `The store stays sealed` | `OPENBAO_UNSEAL_KEY` in `.env` is not the key the store was initialised with: the log printed above it says `failed to unseal`, after 90 seconds of `sealed`. Put the right key back; without it the data is locked, and `make reset` starts over with a new store |
| `make up` ends with `The root token in infra/compose/.env does not open the store` or `has no OPENBAO_ROOT_TOKEN` | The token line was lost or belongs to an earlier store. With `OPENBAO_RECOVERY_KEY`, `bao operator generate-root` inside the container makes a new root token; put it in `.env`. Otherwise `make reset` |
| `docker compose` says `OPENBAO_UNSEAL_KEY is missing` | The `.env` predates ADR-0028: `make env` adds the key and changes nothing else |
| `permission denied` on `/var/run/docker.sock` | Your user is not in the `docker` group: `sudo usermod -aG docker $USER`, then reopen the terminal |
| `bind: address already in use` for port 80 or 443 | Another web server on Windows or WSL; stop it or publish Traefik on other ports |
| `failed to bind host port 0.0.0.0:5200` when `make up-control` or `make integration` starts | The control plane from source is still running: `ss -ltnp 'sport = :5200'` shows the process; stop it |
| A control container fails to resolve `openbao` or `postgres` ("temporarily unavailable") | It was created during a failed start and kept a broken network namespace: `docker rm -f <container>`; the Makefile and the integration script recreate the two control containers on every start since T18 |
| `npm` errors with `UNC paths are not supported` or `CMD.EXE was started` | The Windows npm is on the PATH in WSL; install Node 26 with nvm inside WSL, `rm -rf shell/node_modules`, `make shell-install` |
| A unit keeps old behaviour after `make images` | The unit still runs the previous image: `docker compose -p tenant-<slug> images` shows `<none>` for it; `make update-unit TENANT=<slug>` after the build, not before |
| `https://<slug>.localhost` answers `404 page not found` | A router without TLS on the `websecure` entry point (fixed in T15; `traefik/traefik.yaml` must have `http.tls` on it) or no unit for that hostname: `docker compose ls` |
| A unit's log has `ALERT: the entitlements are unknown`; `/health/ready` shows `entitlements` degraded; role export answers `entitlements.feature_disabled` with the reason `unknown`; the Subscription page says the subscription cannot be confirmed | The unit has had no answer from the store for 24 hours, or never had one, so everything licensed is off (ADR-0034). If the log names a 403 on `tenants/<slug>/entitlements`, the unit's policy predates A4: `make update-unit TENANT=<slug>` writes the policy and the entitlements again. If the store does not answer, see the rows above about the store. Before 24 hours the readiness check is degraded with "has not answered since" and the last answer still stands |
| A unit's log has `ALERT: the settings have not refreshed`; `/health/ready` shows `settings` degraded | The unit's API or worker has not read `kernel_settings` for five minutes, so changes made in the console since then are not seen there; the values read before stand (ADR-0036). It is the database: see `make logs SERVICE=postgres` and the rows about the store and the database. The process that saved a change sees it at once; the others within 30 seconds of the database answering again |
| A unit's log has `ALERT: no flag rules are known`; `/health/ready` shows `flags` degraded | The unit has never read its flags, so every flag has its code default and no kill switch is on (ADR-0035). If the log names a 403 on `platform/flags` or `tenants/<slug>/flags`, the unit's policy predates A5: `make update-unit TENANT=<slug>` writes the policy and both paths. If the store does not answer, see the rows above about the store |
| A unit's flags are stale: `/health/ready` shows `flags` degraded with "has not answered since", and `flags.age` keeps growing | The store has not answered the unit's reads; the rules confirmed at the time shown stand, kill switches included, until it does. Nothing to do in the unit: bring the store back (rows above). A change made in the control plane meanwhile reaches the unit on its first good read |
| A change from `make kill-switch` or `make flag` has not reached the unit after a minute | The store refused the write: the control plane's log says `could not be written to the store`. The change is committed, and the fleet writes it within a minute (`make logs SERVICE=fleet` shows `Reconciled 1 of 1 flag path(s)`). Is the fleet running? If the unit's log names a 403 on a flags path, see the first row on flags above |
| `make kill-switch` answers 403 `authz.permission_denied` | The account is not an operator of the control plane, or the control plane's seed predates A5: `make seed-control` gives the administrator role `tenancy.kill_switches.manage` |
| The control plane's log, or the fleet's weekly line, lists flags past their removal date or rules for flags that are gone | `GET /api/v1/flags/report` shows the same with each owner. A flag past its date: its owner removes it from the code and marks it retired in the catalogue (developer guide). Rules for a retired or unknown flag: replace its rules with none (`PUT /api/v1/flags/{key}/rules` with `"rules": []`) |
| `make apply-plan` says the store is behind | The store refused the write; the change is committed and the fleet writes it within a minute (`make logs SERVICE=fleet` shows `Reconciled the entitlements`). Is the fleet running? |
| The invitation link says the invitation does not exist | It was accepted already, or the seed ran again and re-issued it, and the provisioning report gave the new link once to the operator who asked that job. `make update-unit TENANT=<slug>` issues a new one while the administrator is still Invited, and prints it |
| `make provision`, `make update-unit` or `make recover-admin` printed no link | The report gives a job's link once, to the operator who asked: someone or something read the report first (the smoke reads it on its own runs), or the link expired. Ask again: an update re-issues an open invitation, a recovery request issues a new link |
| The smoke fails at `recovery` with 409 `tenancy.tenant.not_provisionable`, or the job fails with `identity.recovery.not_administrator` or `not_allowed` | The tenant is not active, or its administrator is not an active tenant administrator of the whole tenant: an administrator still Invited needs `make update-unit TENANT=<slug>` (the seed re-issues the invitation, and the smoke accepts it); one whose role was removed needs it back from another administrator |
| `make recover-admin` or the smoke's `recovery` answers 403 `authz.permission_denied` | The control plane's seed predates T2: `make seed-control` (or `make up-control`) gives its administrator role `tenancy.administrators.recover` |
| A sign-in answers "Too many failed sign-ins for this login" | The login identifier is locked after five failures in fifteen minutes, known or not (ADR-0046): wait fifteen minutes, or an administrator unlocks it on the person's record; a recovery link lifts the lock too |
| The grid shows "Not found" on reload or on a pasted link | The shell image predates T17; `make images` and `make update-unit` |
| After `make images` and `make update-unit` on a laptop from before ADR-0029, a tenant answers but its users, roles and audit trail are gone; `\dn` in its database lists both `identity` and `kernel_identity` | The schemas carry their layer prefix since ADR-0029 and start from a new `Initial` migration, so the new images create empty `kernel_*` schemas beside the old ones and never read the old. There is no bridge: start over once (section 11) and provision the tenants again |
| Old credentials after recreating `.env` | The volumes still hold the old values: `make reset`, then `make up` |
| `curl` in WSL cannot reach `acme.localhost` | Add the `/etc/hosts` line from `make hosts`, or use `http://localhost` with `-H 'Host: acme.localhost'` |
| The shell or the API still shows a plan, a flag or a kill switch that was changed minutes ago | The unit has not read the store since: `/health/ready` shows `entitlements` or `flags` degraded with "has not answered since". The values confirmed then stand until it does (ADR-0034, ADR-0035); see the rows above on the store. A change reaches the API within 30 seconds of a good read and the shell within a minute; reload the page if a tab was hidden, since the shell reads `/me/context` only while its tab is visible |
| After `make update-unit` healed a unit, its log says the store refused a read (403 on `tenants/<slug>/unit`, `entitlements` or `flags`) | The heal issued a new unit token, and the unit still runs with the old one: the job stopped before its `unit` step, which restarts the containers with the new token. `GET /api/v1/tenants/<slug>/provisioning` on the control plane names the step that failed; fix its cause and run `make update-unit TENANT=<slug>` again, which continues from that step. `docker compose -p tenant-<slug> ps` shows the containers' start time |
| A reviewer cannot decide an item: the API answers 403 `authz.review.own_item` and the page shows the item without Confirm and Revoke | Nobody decides their own access (ADR-0037): the item stays with the other reviewers of its unit and of the units above it, and goes to the campaign's owner when there is none. The campaign's owner sees it with `with_owner` set |
| A grant, a delegation or a role's change is refused with 409 `authz.sod.conflict` | A conflict rule that blocks names itself in the message (ADR-0039): change the grant, or ask the rule's owner, on the console's Conflict rules page, whether the rule should warn instead |
| `make test` stops with `The test service iron-test-postgres did not answer within a minute` (or Azurite, OpenBao) | Docker is not running, or a container of an interrupted run is in the way: `docker ps -a --filter name=iron-test`; `sh tests/test-services.sh down` removes them, and the next `make test` starts them again |
| `make images` fails at the API image's `locations` stage: `curl: (22) ... 404`, or `sha256sum: WARNING: 1 computed checksum did NOT match` | DB-IP keeps only the last few months of IP to City Lite online, and the pinned month went (ADR-0049). In `src/Hosts/Iron.Host.Api/Dockerfile`, set `LOCATIONS_MONTH` to the current month, download `https://download.db-ip.com/free/dbip-city-lite-<month>.mmdb.gz` once, put its `sha256sum` in `LOCATIONS_SHA256`, and change the month and the sum in `docs/licences.md` in the same commit. A checksum that fails for the same month means the file changed upstream: look before you trust it |
| Every session's place says "Unknown place" | The API runs without the location database: an image built before S3 T5, or `Identity:Locations:DatabasePath` pointing elsewhere. Sign-ins work the same; `make images` and `make update-unit`. A private address (the laptop's own) has no place either |
| `make impersonate` or the break-glass approval answers 403 `auth.reauthentication_required` | The token is older than the five minutes step-up allows: the scripts ask a fresh one each time, so a clock far off between WSL and the containers is the likely cause |
| `make impersonate`'s job fails with `identity.impersonation.operator_refused` | The tenant turned `identity.impersonation.operator_allowed` off on its Settings page: only its administrators may turn it back on |
| A break-glass access stays `ending` for more than two minutes | The fleet host is not running (`make logs SERVICE=fleet`), or its close job failed: the log says `The close of break-glass ... failed`, and it is asked again every minute. The unit refuses the account after its time whatever the fleet does |
| `make shell-check` fails at `prettier --check` | A file is not formatted: `make format` (or `cd shell && npm run format`) and commit the result (ADR-0040) |

## 11. Starting over

`make down-control` (if containers), stop `make run-control` and `make run-fleet`, then `make reset` deletes every platform volume, the store's included, and the store's token and recovery key lines in `.env`. The tenant units are separate projects: `docker compose ls` lists them; `docker compose -p tenant-<slug> down` removes each. Then `make up` (which initialises a new store), `make secret-control && make migrate-control && make seed-control`, and provision again. Delete `infra/compose/.env` only together with `make reset`; the credentials and the seal key must match the volumes.
