# Runbook: the laptop platform

Everything Foundation needs runs on the developer laptop in containers (PRD section 3.3, decision D-14, ADR-0005): the platform services, the control plane, and one Compose project per tenant unit. This runbook is the reference for starting, reaching, changing and resetting all of it. The first hour from a fresh checkout is in the README; this page is what you come back to.

## 1. Prerequisites

- WSL 2 with Ubuntu, Docker (Engine inside WSL, or Docker Desktop with WSL integration), `docker compose version` 2.x.
- .NET SDK 10 and Node.js 26, both inside WSL. `which npm` must not point under `/mnt/c`: the Windows npm runs through `cmd.exe`, which cannot work from a WSL path, and installs Windows binaries into `node_modules`.
- Ports 80, 443, 5432, 8200, 10000, 3200, 4317, 4318 and 9093 free; 5100, 5101 and 5200 free when the hosts run from source.
- Memory: about 2.5 GB for the platform with telemetry, about 0.5 GB per tenant unit, about 1 GB for the control plane as containers. The reference machine is a laptop with 16 GB of memory, with WSL limited to 12 GB and 8 GB of swap.
- WSL's memory and swap, in `%UserProfile%\.wslconfig` on Windows, under `[wsl2]`, applied after `wsl --shutdown`: on the reference machine `memory=12GB` and `swap=8GB`; on a 32 GB machine `memory=20GB` and `swap=8GB`. `memory` must stay below the machine's own memory. Without the file WSL takes half the machine's memory and a quarter of that as swap, which is too little: measured on 2026-10-19 on the reference machine with those defaults (7.4 GB and 2 GB of swap), with the platform, telemetry, the control plane as containers and four units up, `make test`, `make shell-check`, `make shell-a11y` and `make format` passed, but memory use peaked at 6.9 GB and the swap was full. That is the pressure under which WSL restarted on 2026-10-18 and took the old in-memory store with it.
- Optional: `mkcert` (`make certs`), Playwright browsers (`cd shell && npm run e2e:install`).

Tenant units are separate Compose projects `tenant-<slug>` that join this network; `docker compose ls` lists them.

Hostnames: browsers resolve every `*.localhost` name to the laptop by themselves. Command line tools in WSL do not; run `make hosts` once and add the line to `/etc/hosts`, or call `http://localhost` with a `Host:` header, as the scripts do.

TLS: the `websecure` entry point has TLS on. Without `make certs` Traefik uses its own self-signed certificate, which the browser warns about once; with mkcert, trust its root on Windows as the script explains. `http://` works too, and Chrome treats `*.localhost` as secure, so the session cookie is accepted there as well.

## 4. Secrets

Every unit, the control plane included, gets its configuration at start from one secret in OpenBao: `secret/<path>/unit` with keys that are configuration keys (`ConnectionStrings:Database`, `Storage:ContainerSasUrl`, `Keys:Prefix`, ...). A unit holds no key (ADR-0054): its keys are in the store's transit engine (mount `transit`), three per tenant, `tenant-<slug>-data`, `-index` and `-signing`, and the control plane's `control-data`, `-index` and `-signing`; the secret only names the family, and the unit's token may use its own family's keys and no other. The database password in the secret is read again a minute after it was last read, or at once when PostgreSQL refuses it, so a rotated password needs no restart. `make secret-dev` makes the dev tenant's keys; `make run-api` without a store derives its keys from `infra/compose/.dev-key-material` (git-ignored, written on first start). The factor keys of ADR-0047 are retired (ADR-0054): the first update after T9b moved the authenticator secrets they sealed onto the key service, and V0 dropped the old column, so nothing reads them any more; V0 deleted `infra/compose/.control-factor-key` once the control plane, acme, bravo and echo were updated. Its environment holds only `Secrets__Address`, `Secrets__Token`, `Secrets__Path` and the tenant binding (ADR-0016). An explicit environment variable wins over the secret.

The fleet writes `tenants/<slug>/database` (the role passwords), `tenants/<slug>/storage` (the signed container URL), `tenants/<slug>/unit` (the unit's configuration) and `tenants/<slug>/fleet` (the unit token, the smoke client's secret) per tenant (ADR-0018), and makes the tenant's three keys. A job's link waits at `tenants/<slug>/handover/<job id>` until the report gives it to the operator who asked, or until it expires (ADR-0046). A unit writes its single sign-on providers' client secrets itself, at `tenants/<slug>/sso/<provider id>`, the one path its token may write (ADR-0048). `make secret-dev` writes the dev tenant's by hand; `make secret-control` writes the control plane's, with `localhost` hosts for the hosts from source and `postgres`/`blob` hosts when `make up-control` writes it for the containers.

OpenBao runs in server mode and keeps its data on the volume `openbao-data` (ADR-0028): `make down`, a restart of its container and a restart of WSL keep every secret. The configuration is `infra/compose/openbao/openbao.hcl`. At every start the static seal unseals the store with `OPENBAO_UNSEAL_KEY` from `.env`, which `make env` generates (and adds to an older `.env`). The first `make up` initialises the store: `infra/compose/scripts/init-store.sh` initialises it with one recovery share, writes `OPENBAO_ROOT_TOKEN` and `OPENBAO_RECOVERY_KEY` into `.env`, and enables KV version 2 at `secret`. Before either, the script waits for the store by its health endpoint (`/v1/sys/health`) for up to 90 seconds and says every 10 seconds where it stands: a container Docker calls healthy may still be starting its storage, and a sealed store still counts as healthy to Docker. If the store is not ready in time, the script prints the container's health state and its last 50 log lines, then fails (section 10). Every later `make up` checks that the store is unsealed and that the token opens it, and says what to do if not (section 10). The three lines belong to the volume: keep them together, and never commit `.env`. `make reset` deletes the volume and the token and recovery key lines together; the next `make up` initialises a new, empty store.

If the store lost its data anyway, the recovery is two commands: `make up-control` writes the control plane's secret again, and `make update-unit TENANT=<slug>` heals each unit (section 5).

## 5. Tenant units

`make provision TENANT=acme [ADMIN=admin@acme.localhost] [SUITES=procurement REASON="..."]` registers the tenant with the hostname `acme.localhost`, and the suites it bought (see Suites below), and asks the fleet to provision it, then follows the job and prints every step with its duration, and at the end the first administrator's invitation link, once: the control plane gives it to the operator who asked and deletes it, and it is in no job output or log (ADR-0046). The job's eight steps are reserve, database, storage, secrets, migrate, seed, unit, verify. A failed step is printed with its error; fix the cause and run the same command again, and the job continues from that step. `GET /api/v1/tenants/acme/provisioning` on the control plane shows the job and its steps.

`make update-unit TENANT=acme` runs database, storage, secrets, migrate, seed, unit and verify (ADR-0028): it re-runs migrate and seed from the current images and re-applies the unit, which is how a unit takes a new image (`make images` first) or a changed template, and it heals a unit whose secrets the store lost. With the secrets in place the first three steps change nothing; with them lost, they make new role passwords, a new container signature and a new unit token, and the unit restarts with them. A healed tenant keeps its data and serves its users, and its smoke client takes the new secret from the seed, so a client credentials token works again. Its administrator's password is not in the store any more: the smoke's recovery step sets a new one on its next run, or `make recover-admin` gives a link for a person to use (below). The seed re-issues the administrator's invitation while it is still unaccepted. `make deprovision TENANT=acme` takes the unit's containers down and keeps its database, container and secrets.

**Plans.** `make apply-plan TENANT=echo PLAN=Enterprise` prints the preview (the plan and grace days before and after, every module and feature added, removed or changed, and the warnings), applies it, and says whether the store holds the new revision. `DRY_RUN=1` stops after the preview; `STARTS` and `ENDS` set the subscription's dates. The control plane seeds two Foundation plans, `standard` (no role export and import, 14 grace days) and `enterprise` (with them, 30 grace days), and each suite's starter plans: the eProcurement Suite's `procurement-essentials` (Purchasing, 30 grace days). A plan belongs to the Foundation or to one suite and names only that group's modules and features; one that names another group's is refused when saved or applied (ADR-0059). A tenant holds one Foundation plan and one plan per suite it has: applying a plan changes only its own group, and the unit receives the union, each entry with its own plan's grace days. A suite's plan applies only to a tenant that has the suite. A new tenant starts on `standard` unless it is created with another; a tenant created before A4 has no entitlements until a plan is applied, so it has no role export and import. The unit reads the change within 30 seconds and the shell within a minute; `GET /api/v1/tenants/<slug>/entitlements` and `/entitlements/history` on the control plane show what it holds, in which group, and every change with its operator. In the tenant, the console's Subscription page shows the plan, the modules and features with their status and dates, and the seats.

**Suites** (TF-244, ADR-0059). A tenant has the Foundation and the suites it bought; its unit migrates, seeds and loads a suite only when it has it. Register a tenant with a suite, each under its only plan:

```
make provision TENANT=delta SUITES=procurement REASON="Bought the eProcurement Suite (order 1234)"
```

Add a suite to an active tenant, under its only plan or the one you name, and take it away again:

```
make suite-add TENANT=bravo SUITE=procurement REASON="Bought the eProcurement Suite (order 1235)" [PLAN=procurement-essentials]
make suite-remove TENANT=bravo SUITE=procurement REASON="The contract ended (ticket 4713)"
```

Each needs `tenancy.suites.manage` (critical; the control plane's administrators hold it after `make seed-control`) and a reason, which the control plane's audit trail keeps with your name (`tenancy.suite_added`, `tenancy.suite_removed`) and the entitlements' history with every module and feature the change added or removed. Each asks the fleet for an update job, which the command follows as it does provisioning. Adding applies the suite's plan, then the job migrates the suite's schemas, seeds them (the suite's installation row records the job and the release), and recreates the unit with the suite in its environment (`Suites__Installed`). Removing takes the suite's entitlements away at once, so the unit refuses its modules within a minute, then the job recreates the unit without it: its routes answer 404 and the home page loses its group. Nothing drops the suite's schemas, rows or files; adding it again finds them, and its About page shows the first installation and the latest. A tenant's suites are on `GET /api/v1/tenants/<slug>/suites` and in its record. An add or remove while another job of the tenant is open is refused and changes nothing; ask again when it ends. An expired suite plan switches the suite's modules off after its grace days and uninstalls nothing. In the tenant, an administrator sees the suite on its About page, `https://<slug>.localhost/procurement/about`.

**A tenant administrator who cannot sign in** (ADR-0046). The tenant's own administrators come first: one with `identity.users.manage` at the person's unit unlocks a locked login, or issues a recovery link, on the person's record under Users. When nobody in the tenant can, because the last administrator lost their password or the store that kept the smoke's password was healed, the operator asks for a link:

```
make recover-admin TENANT=acme REASON="The administrator lost their password (ticket 4711)"
```

`ADMIN=someone@acme.localhost` names another tenant administrator than the first. The call is `POST /api/v1/tenants/{slug}/administrator-recovery` with `reason` (and `login_id`) on the control plane, which needs `tenancy.administrators.recover` (the control plane's administrators hold it after `make seed-control`). The fleet runs the unit's `recover-admin` command, which issues the link only for an active tenant administrator of the whole tenant. At the end the command prints the link, `https://acme.localhost/recovery#<code>`, once: the control plane gives it only to the operator who asked, deletes it, and keeps it in no job output or log, so give it to the administrator at once, and ask again if it is lost. It works once, for 15 minutes; a newer link replaces it, and using it ends all their sessions. The control plane's audit trail records the request, and the tenant's own trail and the administrator's Security activity record the link with your name and the reason. An administrator who is still Invited needs the invitation again instead: `make update-unit TENANT=acme`, whose seed re-issues it.

**Resetting a tenant administrator's second factors** (ADR-0047). An administrator who lost the device that holds their authenticator app or passkey, and has no recovery code left, cannot sign in even with their password. Another tenant administrator who holds every permission they hold resets their factors on their user record ("Reset factors" under More, with a reason, after confirming it is them). When there is none, the operator does it with the recovery:

```
make recover-admin TENANT=acme REASON="Lost phone and password (ticket 4712)" RESET_FACTORS=1
```

The request carries `reset_factors: true`; the unit's `recover-admin` issues the link, removes every second factor and recovery code of the administrator, and ends their sessions, in one transaction. The job's output says the factors were reset. Both audit trails record it with your name and the reason, and the administrator's Security activity shows "Second factors reset". The administrator sets a new password with the link, signs in with it, and, since the policy requires a factor of a tenant administrator, sets one up at once before any page, receiving new recovery codes. The smoke sets the administrator's password with the operator's recovery on every run and keeps it, with their authenticator app's key (`administrator_totp_secret`), in `secret/tenants/<slug>/smoke`, which `make e2e` reads. It resets the factors this way only when it keeps no key or the unit refuses the one it keeps, and then enrols a new app and keeps its key.

**Settings.** The tenant's settings are the tenant's: its administrators change them on the console's Settings page (`/console/settings`), for the whole organisation or for a unit, and each person sets their colour scheme and density in My profile (ADR-0036). They live in the unit's database, so nothing in the control plane or the store changes them. `GET /api/v1/settings?scope=tenant` and `/api/v1/settings/{key}/history?scope=tenant` on the unit show the values and every change with its author.

**Flags and kill switches.** `make flag KEY=flags.example_tone VALUE=warm TENANT=echo` sets the flag's one unconditional rule for the tenant (without `TENANT`, for the platform), keeps its other rules, and prints the rule and the flag's revision. Scopes below the tenant, percentages and attributes go through `PUT /api/v1/flags/{key}/rules` on the control plane; `GET /api/v1/flags`, `/flags/{key}/rules` and `/flags/{key}/history` show the flags, their rules and every change with its operator.

`make kill-switch PATH=imports ON=true REASON="A fault in role import is being fixed; back this afternoon."` stops a path for the whole platform, with one write to `platform/flags`; `TENANT=echo` stops it for one tenant. Only the control plane's operators may (`tenancy.kill_switches.manage`), and the reason is required: the tenant's administrators read it in the banner at the top of every page. Within 30 seconds the units refuse the path with 503 `flags.killed`; within a minute the banner shows and the shell hides what the path offers (Import on the Roles page for `imports`). `ON=false` with a reason turns it off the same way. `GET /api/v1/kill-switches` shows each switch, since when, why, and the tenants it is on for. The paths are `email`, `webhooks`, `sms`, `ai`, `push` and `imports`; only `imports` is wired in S2.

A kill switch stays on while the store does not answer, and through a restart: the unit keeps the last rules it read, without expiry. A unit that has never read any rules runs on the code defaults, with nothing stopped, and alerts (section 10).

**A hostname no unit serves.** The ingress answers it itself with `404 page not found`, over HTTP and HTTPS, and no unit receives the request: Traefik routes a request only to the unit whose hostname it names (TF-003 AC3, ADR-0019). Checked by hand on 2026-10-21 (S3 T1), with the units acme, bravo, echo and smoke running: `curl -sk -H 'Host: nobody.localhost' https://localhost/api/v1/me` and the same over `http` answered 404 `404 page not found`, while `https://echo.localhost/health/live` answered 200.

What the fleet renders is in `infra/compose/units/<slug>/` (git-ignored): one `compose.yaml` from the embedded template and the unit's `.env`. `docker compose -p tenant-acme ps`, `logs` and `images` work on it directly; `images` is the quick way to confirm a unit runs the image you just built.

**A company login (single sign-on, ADR-0048).** A tenant administrator connects one in the console, under Single sign-on: a preset fills the discovery address (Microsoft Entra ID from the directory (tenant) ID, Okta from its domain, Google's fixed), the client identifier and secret come from the provider, and the provider must list `https://<tenant hostname>/sso/callback` as a redirect URI, which the page shows with a copy button. "Test connection" says in words what works before anything is saved. The secret goes to the store, never the database. Units provisioned before S3 T4 need `make update-unit TENANT=<slug>` once, so their token may write it.

**The test provider.** `make test-provider` starts navikt's mock-oauth2-server (profile `sso`, capped at 300 MB) behind the ingress at `http://idp.localhost`; any first path segment is an issuer of its own, so `http://idp.localhost/<anything>/.well-known/openid-configuration` is a provider ready to connect. Its login page takes a user name and the claims of the sign-in as JSON, for example `{"email": "ada@example.test", "email_verified": true, "name": "Ada", "groups": ["buyers"], "amr": ["pwd", "mfa"]}`. Traefik answers `idp.localhost` inside the platform network too, so a unit's API reaches the provider at the same address and issuer as the browser: after pulling S3 T4, `make up` once recreates Traefik with that alias. Its keys are made at its start: a restart gives new ones, which a unit reads again at the first token that names one.

**Sessions** (ADR-0049). Each person sees and ends their own sessions in My profile, under Sessions. A tenant's administrators with `identity.sessions.manage` see everyone's live sessions first on the console's Sessions page (`/console/sessions`), and end any one with a reason after confirming it is them; how many people are signed in now and the last days' summary, and revoking everything, are its other two tabs. The person's next request is refused with `auth.session_ended`, and their Security activity and the audit trail name who ended it and why. The tenant's setting `identity.session.concurrent_limit` (console, Settings; 0 is no limit) ends a person's oldest session at a sign-in past it, and that session's next page says so.

**Revoking after an incident** (TF-029, ADR-0049). When a person's password, device or a service account's secret may be in the wrong hands, revoke that principal: "Revoke everything" under More on their user record, with a reason. When the whole tenant may be affected, revoke everything of the tenant on the console's Sessions page, under its Revoke everything tab: type the tenant's identifier and a reason. Both need a recent confirmation that it is you. Every session the revocation covers ends at once, and every token issued before it is refused (`auth.session_revoked`, `auth.token_revoked`) within a minute on every API process: each keeps the tenant's revocation time for at most 60 seconds. The tenant-wide one signs you out too. Then:

1. Look at what happened: the console's Audit trail, filtered to `severity` high, lists the revocation, emergency sign-ins and break-glass accesses; a person's Security activity lists theirs.
2. Change what leaked: the person sets a new password with a recovery link (their record, "Issue a recovery link"), a lost device's factors are reset ("Reset factors", under More), and a service account gets a new secret from the seed (`make update-unit TENANT=<slug>` for the smoke client).
3. Clients sign in again: a person at the login page, a client with a new token; a token asked for in the same second as the revocation is refused too, so a client that retries at once waits a second.

**Signing in as a person, as the operator** (TF-025, ADR-0049). For support, with the tenant's consent (`identity.impersonation.operator_allowed`, on by default, on the console's Settings page):

```
make impersonate TENANT=acme LOGIN=pat@acme.localhost REASON="Pat cannot see the March orders (ticket 4713)" MINUTES=30
```

The call is `POST /api/v1/tenants/{slug}/impersonation` on the control plane (`tenancy.impersonation.start`, critical, with a fresh token). The fleet runs the unit's `impersonate` command and the script prints your link, `https://acme.localhost/sign-in-link#<code>`, once: open it at once in a private window, as it works once, within 15 minutes. The shell then runs as the person under a band that names you, the reason and the end; "End" in the band, or the time, signs you out, since you have no session of your own in the unit. You cannot confirm it is you there, so nothing behind step-up, no signature and no second approval is possible, nor the person's password, factors, sessions or terms. The tenant's audit trail names you on every action, and the person's Security activity shows who, when and why. Checked on echo on 2026-10-22: the link signed in once and a second use answered 404, step-up answered 403, and "End" answered 204.

**Break-glass** (TF-026, ADR-0049). When a tenant needs the operator's hands and nobody in it can act, two operators open a time-limited account in its unit. The control plane seeds two: `operator` and `operator-two` (`make seed-control`, or `make up-control`).

```
make break-glass-request TENANT=acme TICKET=INC-1 REASON="Orders stuck in approval since 09:00" MINUTES=60
make break-glass-approve ID=<id>     # as operator-two, within 30 minutes
make break-glass-link ID=<id>        # as the operator who asked: the sign-in link, once
make break-glass-end ID=<id>         # when the work is done, before its time
make break-glass-show ID=<id>        # where it stands, and the review once it ended
```

The request names a ticket and a reason and waits for a second operator, never the one who asked; unapproved after 30 minutes it expires, and an approval then is refused. On approval the fleet opens the account `break-glass-<12 hex>@break-glass.invalid` with the role `break-glass` (every permission but the critical ones) until the time asked, at most 240 minutes. The link is printed once, valid 15 minutes: open it in a private window. At its time, or at `make break-glass-end`, the fleet closes the account and ends its sessions, and the control plane keeps the review: every action of the account, in order. The fleet host does this every minute, so `make break-glass-show` says ended a minute or two later. The tenant's audit trail records each step at high severity with both operators, the ticket and the reason. Checked on echo on 2026-10-22: requested, approved by `operator-two`, the link given once and refused the second time, ended early, and ended with its review 20 seconds after.

**Emergency accounts** (ADR-0048, ADR-0049). A tenant that signs in through its company login keeps up to two local accounts for when the provider is down: an administrator marks them with "Make emergency account" under More on the user record. Each must have a second factor, always signs in with password and factor, and is never held to single sign-on only. Every sign-in with one raises an alert: the person's Security activity, the audit trail at high severity, and a banner for the tenant's administrators for 24 hours.

**Terms and documents** (TF-028, ADR-0049). The platform's terms of service and privacy notice are the operator's:

```
make platform-document KEY=terms_of_service TITLE="Terms of service" FILE=path/to/terms.md
```

writes a new version to the store (`platform/documents`), and every person of every unit must accept it at their next request, within a minute. A tenant's administrators publish their own documents, see who accepted which version, export the acceptances and retire a document on the console's Documents page (`/console/documents`). A person who declines is signed out and asked again at the next sign-in. Units provisioned before S3 T5 need `make update-unit TENANT=<slug>` once, so their token may read `platform/documents`.

No automated run accepts a document (ADR-0049): the smoke never does, and the pipeline never publishes one. So after `make platform-document`, or a tenant document published by hand, accept the new versions deliberately as the stored test administrator of each tenant you run the smoke on:

```
make accept-documents TENANT=echo
```

It signs in as `admin@<tenant>.localhost` with the password and the authenticator app's key `make smoke` keeps at `secret/tenants/<tenant>/smoke`, prints each version it accepts, and accepts nothing for anyone else. Checked on echo on 2026-10-23 with a tenant document: the administrator's requests answered 403 `identity.terms.acceptance_required`, the target accepted the one version, the same session then answered 200, and a second run said there was nothing to accept.

**The audit chain** (TF-061, ADR-0050). Each unit's worker seals its audit events into a chain every few seconds and sends the control plane an anchor after each seal; the fleet verifies every tenant once a day, in full once a month. Units made before S3 T6 have neither the fleet's verifier role nor their own control-plane client: `make update-unit TENANT=x` gives them both (the fleet logs once an hour that it cannot verify a unit until then). Units reach the control plane at `http://control-api:8080`, so anchors flow when it runs as containers (`make up-control`), not from `make run-control`.

```
make verify-audit TENANT=echo            # verify now and print the record
make verify-audit TENANT=echo FULL=1     # from the first position kept
make audit-chain TENANT=echo             # the latest records and anchors
```

A tenant's administrators see the same on the Chain status page under Audit.

*Reading a verification failure.* A record that did not pass says `FAILED` and lists each problem with its position and the event's identifier:

- `missing`: no event at that position. Someone deleted it past the database's permissions.
- `modified`: the event's content no longer gives its hash. Someone changed it.
- `relinked`: the event points at a different event before it.
- `anchor_mismatch`: the chain disagrees with the control plane's anchor at that position.
- `unknown_version`: a hash made with a canonical form this build does not know; a newer build sealed it.

The alert is an error line starting `ALERT:` in the fleet's log, the counter `audit.verification_failures`, and `tenancy.audit_chain_broken` at high severity in the control plane's trail. Treat it as an incident: keep the tenant's database as it is (a copy for the investigation), find the event's time and correlation id in the archive or a backup, and check the database's own logs for who connected as the owner. The Audit README's canonical form lets anyone recompute a hash by hand.

*A restore point.* After the tenant's database is restored from a backup, its chain ends before the latest anchor. The record says `RESTORED` and names the restore point: the last position whose hash matches an anchor, and that anchor's time. Every event after it was lost with the restore; the trail from before is intact. New events are sealed from the restored head, so the anchors for positions the control plane already held are refused as conflicts (`tenancy.audit_anchor_conflict`), and each verification reports the same restore point until it is accepted.

*Accepting a restore.* Once the incident is investigated and the restore point is the one you expect, accept it with its ticket and a reason:

```
make audit-accept-restore TENANT=echo TICKET=INC-77 REASON="Restored from last night's backup after the disk failure"
```

It needs `tenancy.audit_restores.accept` (critical) and a fresh token, which the script asks for. The control plane keeps the restore for good, writes `tenancy.audit_restore_accepted`, and asks the fleet for a full verification, which the script waits for and prints: it passes. The chain continues as a new segment from the position after the restore point; the lost positions keep their old anchors in the segment before. Within a minute the unit records the acceptance in the tenant's own trail (`audit.restore_accepted`) and the Chain status page shows the restore and the range lost from then on. A restore that is not the one you expect is not to be accepted: treat it as a verification failure. `make audit-chain TENANT=echo` lists the accepted restores with the verifications and anchors.

*An anchor conflict* without a restore means the unit sealed a different event at a position the control plane anchored: treat it as a verification failure.

**Legal holds** (TF-066, ADR-0050). A hold keeps records their retention would delete: one record, every record of a master (a supplier's documents), or the whole tenant, the audit trail's oldest end included. A person with `audit.legal_holds.manage` (critical; the tenant administrator's role carries it) places one on the Legal holds page under Audit, with what it keeps and a reason, after confirming it is them (step-up). Releasing needs a reason too; a released hold stays listed. Both are in the audit trail. Place a hold before the retention job's next run (daily) for anything that must stay.

**Retention** (TF-066, ADR-0050). The Retention page under Audit lists each class (business documents, sessions, security activity, notifications, the audit trail and how long it stays in the database before the archive), its period and the operator's limits. A person with `audit.retention.manage` changes a period within them, with a reason and step-up; below the minimum is refused. The operator's limits are configuration in the unit secret (`Retention:Limits:<class>:MinimumDays` and `MaximumDays`). The daily retention job archives each expired record to the tenant's container (`retention/<type>/<yyyy-MM>/<id>.json`) before deleting it, and archives audit events past the online period to `audit/archive/`, where the Archive tab of the Audit trail searches them by date range.

**Evidence packs** (TF-067, ADR-0052). Under Compliance, Evidence packs, a person with `compliance.evidence.export` (high risk; the tenant administrator's role carries it) chooses a period of whole days in UTC and makes a pack; the unit's worker makes it within seconds, and its page shows the pack's SHA-256, the manifest's, and the audit chain's head with the control plane's anchor. Download gives a link that is yours alone, works once and lasts five minutes. The ZIP holds five numbered folders (access list, administrative actions, security settings, chain verification, backup drills), each a page and its CSVs headed by the tenant and the period, and `manifest.json` with every file's hash. Asking, making and downloading are in the audit trail with the requester's name. To check one by hand: `unzip`, then `sha256sum` each file against the manifest, and `make audit-chain TENANT=x` for the anchor at the head's position.

**Four-eyes approval** (TF-068, ADR-0052). Under Console, Settings, Four-eyes approval, a tenant chooses the areas whose changes wait for a second administrator (roles and assignments, single sign-on, audit retention, the MFA and password policies, legal holds, the signing policy), the areas whose approvals are electronic signatures, and how many days a change waits (7). A save in a chosen area answers that it waits, with a link; Console, Pending changes lists the changes to approve, your own, and with `changes.changes.read` every one, each with its state before and after side by side. Another person who may make the change approves it with a reason (after confirming it is them, or signing), and it applies at once unless what it changes was changed meanwhile, in which case it goes back for a new review. Nobody approves their own change, and nobody signed in as someone else, acting for someone, or with a break-glass account. While any area is chosen, turning four-eyes off waits for a second administrator too. The browser test that turns it on sets it back whatever happens, approved by the run's second administrator; if a run stopped before that, `make e2e` refuses to start until someone else who holds `settings.values.manage` for the organisation approves the reset under Pending changes.

**The installed version and its validation pack** (TF-218, ADR-0052). The help panel and Compliance, Validation (`compliance.validation.read`) show the version a unit runs; an image built on a laptop is a development build. A release's pipeline publishes its pack to the platform's releases container, and the fleet's ninth step places the pack of the unit's version at every provisioning and update. On the laptop, after `make smoke TENANT=echo` and `make e2e TENANT=echo`:

```
make installation-record TENANT=echo   # the images, migrations and seeds checked against the code
make validation-pack                   # the development pack from the last runs, published to the releases container
make update-unit TENANT=echo           # places it in echo's container
```

`make validation-pack` writes the pack whatever it finds and exits 1 when the pack says the release would fail (a gap without an exception, a failed test, a failed installation check); it publishes the pack either way, so the page can be tried. A release's pack is attached to its GitHub release, tagged `v<version>`.

**The clock** (TF-065, ADR-0050). Every process measures its clock against `pool.ntp.org` every ten minutes (`Telemetry__Clock__Server` to change it, `Telemetry__Clock__Enabled=false` to stop it). More than a second off raises `ALERT: this process's clock is ... seconds off` in its log, the gauge `clock.offset_seconds`, and the readiness check `clock` Degraded. WSL's clock drifts after the laptop sleeps: `wsl --shutdown` from Windows, or `sudo hwclock -s` inside WSL, sets it right. A time server it cannot reach is only a warning.

**Reading the policy's reports** (TF-070 AC3, ADR-0053). Every page's content security policy reports a violation to `/api/v1/csp-reports` on its own host. The API counts them by directive in `protection.csp_reports` (Grafana, Explore, Prometheus: `sum by (directive) (rate(protection_csp_reports_total[5m]))`), writes a few a minute to its log as `CSP violation: <directive> blocked <what> on <page>` (`make logs SERVICE=...`, or `docker logs tenant-echo-api-1`), and keeps the latest 100 in the process: `GET https://echo.localhost/api/v1/csp-reports` with `protection.csp_reports.read` lists each with its page (without its query), the rule it broke, what it blocked and a sample. A flood is refused at 60 a minute per address and counted in `protection.csp_reports_dropped`. On the laptop, Chromium sends its reports through the Reporting API, which does not upload to the ingress's self-signed certificate: Firefox, or a browser that trusts the certificate for every request, shows them. A report from a page you did not change usually means a browser extension; one from a page you changed means inline code or a style element without the page's nonce.

**A tenant's rate limits** (TF-072, ADR-0053). Under Console, Settings, Protection of the sign-in and the API, a tenant administrator sets the sign-in attempts per address (10 a minute), the recovery links per account (5 an hour), the API calls per person (600 a minute) and the exports per person (20 an hour), within the operator's bounds, after a recent sign-in; a change applies within 30 seconds. The operator's bounds are configuration, `Protection__Limits__login__Minimum` and `__Maximum` (and `recovery`, `api`, `exports`), set on the unit's container. A refused request answers 429 with `Retry-After`; the refusals are counted in `protection.rate_limited` by limit, and the first of each window is in the tenant's audit trail at low severity (`protection.rate_limited`). The same page lists the other sites allowed to call the API from a browser, empty by default. After five failed sign-ins from an address or for a login, the login form asks for the check, "I am a person, not a program", which the browser solves itself; the smoke and the browser tests solve it too, and wait when a limit says so.

**Keys** (TF-073, TF-074, TF-075, ADR-0054). A tenant's data key encrypts the fields a module marks, its index key makes the hashes that find them by exact value, and its signing key signs access tokens and the login's check. The fleet rotates them on a schedule (the data and index keys every 365 days by default, which a tenant administrator sets under Console, Settings, Keys, between 30 and 730; the signing key yearly; the database password every 90 days), and a key officer, a holder of `tenancy.keys.manage` with a recent sign-in, on demand:

```
make key-status TENANT=echo
make rotate-key TENANT=echo KEY=index REASON="Index key rotation after the supplier import (ticket 4711)"
make rotate-key TENANT=echo KEY=database REASON="Quarterly drill"
```

`make key-status` prints each key's version, the oldest version still readable (`from`), its last and next rotation, and the latest rotations: state, versions, who asked (an operator, or `schedule`), the reason and, for a data or index key, how many values have moved. `make rotate-key` asks for one rotation (a second one of the same key while one runs is refused), then follows it for at most three minutes. Read a rotation's states in order:

| State | What it means | What to do when it stays there |
|---|---|---|
| `requested` | Asked for; the fleet takes it within five seconds | `docker logs foundation-fleet-1`: the fleet is down or the store refused |
| `rotated` | The key service has the new version, which encrypts, hashes and signs from now on; the unit is moving every value to it (`done of total`) | `docker logs tenant-echo-worker-1`: the unit's worker moves a batch of values at a time and reports each; it resumes where it stopped after a restart |
| `finished` | Every value moved; the fleet retires the old version next (a signing key 30 minutes after its rotation, so tokens signed before it stay valid until they expire) | The fleet's log |
| `retired` | Nothing reads the old version any more | Nothing |
| `failed` | Its error is printed; the fleet's log has the alert and the control plane's trail `tenancy.key_rotation_failed` | Fix the cause and rotate again; the values already moved stay moved |

Every step is in the control plane's audit trail and the tenant's (`keys.key_rotated`, `keys.reencryption_finished`, `keys.key_retired`), with who asked and why. In the tenant, Console, Keys (`keys.keys.read`) shows the same, read only. A rotation of the database password writes the new password to the store first, then sets it in the database; the unit reads it at its next new connection, without a restart, and a connection opened in between is retried. A tenant made before T9b gets its keys at its next `make update-unit`, whose seed moves its authenticator secrets to its data key.

**Logs.** Operational logs keep identifiers, not people: emails and properties named like a name, an email, a phone or an address show as `[masked]`, and Loki deletes lines after 30 days. Look a person up by their id in the console; the audit trail, not the log, is the record of what they did.

## 6. The control plane

The control plane has a unit's three roles (ADR-0053): `control_owner` owns its database and runs its migrations and seeds, `control_app` is what its API and the fleet run with, and `control_audit` reads its audit chain and nothing else. `make secret-control` and `make up-control` write the fleet's bootstrap secret (`fleet/unit`, with the administrative connections), then run the fleet's `prepare-control` with the root token, which makes the roles (and moves a database made before them to the owner), the anchors container `control-audit-anchors` with a SAS that may add anchors and never change or delete one, the control plane's keys, and three secrets: `control/unit` (the API's: the app role's connection, its anchors, its keys), `fleet/unit` (the fleet's: the same with the administrative connections and the token role `tenant-units`) and `control-migrate/unit` (the owner's). Migrate and seed read the last (`Secrets__Path=control-migrate`).

The API and the fleet each have their own store token and policy (ADR-0054): `prepare-control` makes both and keeps them at `secret/control-tokens/unit`, which only the root token reads, and `infra/compose/scripts/write-control-tokens.sh` copies them into `.env` as `CONTROL_API_STORE_TOKEN` and `FLEET_STORE_TOKEN`, which Compose and `make run-control`/`make run-fleet` hand each process. The API's token cannot read the fleet's secret, the migrate secret or the tokens, and cannot make a token; the fleet makes the tenants' tokens through the token role, which allows tenant policies only. The tokens are kept while they open the store; after `make reset`, or when one was revoked, the next `make up-control` makes new ones. The root token is used only to prepare the control plane.

Its own chain: the API seals the control plane's audit trail every few seconds and adds each seal's anchor to that container. The fleet verifies the chain once a day (in full once a month) with `control_audit`, and records the result beside the tenants' under `control`:

```
make verify-control-audit                # verify now; exit 0 when it passed, 2 when not
make verify-control-audit FULL=1         # from the first position
make audit-chain TENANT=control          # the records, as for a tenant
```

A run that does not pass writes `ALERT: the audit chain of tenant control ...` to the fleet's log and `tenancy.audit_chain_broken` (high severity) to the control plane's trail, with the event's id. Treat it as a security incident.

From source, for daily work: `make secret-control && make migrate-control && make seed-control` once, then `make run-control` (API on :5200) and `make run-fleet` (the fleet worker with the Compose runtime, driving this machine's Docker) in two terminals. The seed creates the `operator` account (tenant-administrator), `operator-two` (tenant-administrator, the second operator break-glass needs) and the `smoke-reader` account (service-default, for the smoke's denial case); re-run `make seed-control` after pulling a change that adds accounts.

As containers, as the pipeline runs it: `make up-control` writes the control secret with container hosts, migrates and seeds the control plane's database with the image (so a new image's migrations and permissions are in place before it serves), and starts `control-api` and `fleet` from the images. The two cannot run beside the source processes: stop `make run-control` and `make run-fleet` first (port 5200), and run `make secret-control` again before going back to source.

### Security alerts and incidents (ADR-0056)

Each unit's worker runs the security alert rules every minute over the tenant's audit trail; the console's Security
alerts and Alert rules pages show what they raised and how they run. Each alert is copied to the control plane, which
runs the same rules over its own trail and posts every alert to Alertmanager, in the `telemetry` and `ci` profiles,
limited to 64 MB, paging nobody on the laptop:

```
make security-alerts [TENANT=echo] [STATE=open]     # the control plane's alerts, its own and the units'
make security-alert-resolve ID=<id> NOTE="..."       # one of the control plane's own; a unit's is resolved in the unit
```

The operator's values of the rules are `Monitoring:Rules:<rule>:*` in the unit secret; a value the rule cannot run with
shows as a failing rule on the Alert rules page, with an alert of its own. Incidents follow
`docs/security/incident-response.md`:

```
make incident-declare SEVERITY=2 SUMMARY="..." LEAD="..." [COMMS=...] [SCRIBE=...] [TENANTS=echo] [PERSONAL_DATA=1] [KNOWN_AT=...]
make incident-note ID=<id> TEXT="..." [KIND=note|communication|notice] [TENANT=echo]
make incident-note ID=<id> TENANT=acme PERSONAL_DATA=1      # a tenant found affected
make incident-close ID=<id> SUMMARY="..."                   # once every tenant whose personal data was affected is told
make incident-review ID=<id> WHAT="..." WHY="..." CHANGES="..."
make incident-show [ID=<id>]
```

## 8. Proving a change

- `make test`: the unit and integration tests. It starts one PostgreSQL, one Azurite and one OpenBao for the run (`tests/test-services.sh`, containers `iron-test-postgres`, `iron-test-azurite` and `iron-test-openbao` on loopback ports, pulled first if missing), runs four test projects at a time, each in a database, blob containers and a store mount of its own, and removes the three whatever the result. Docker must be running. Measured on the reference machine with the stack up, straight after `make shell-a11y`: about a minute, peak memory 8.6 GB against 10.0 GB and some forty containers before the services were shared. `TEST_PARALLEL=n` changes the four.
- `make shell-check`: lint, Prettier's check, the type check, the tests and the build of the shell. `make format` runs `dotnet format` and Prettier; run it before a commit.
- `make shell-a11y`: the gallery built and scanned in both schemes and densities; no stack needed. Its screenshots land in `shell/test-results/a11y/`, the browser tests' in `shell/test-results/e2e/`; each run empties only its own folder.
- `make smoke [TENANT=x]`: twenty-three steps against the live stack with the control plane and the fleet running and the telemetry profile up; provisions the `smoke` tenant (or `TENANT`) once and reuses it; writes `smoke-report.json`; keeps the administrator's password at `secret/tenants/<tenant>/smoke`. Its `recovery` step runs the operator's recovery on every run (ADR-0046): a link with the run's reason, used once to set a new password, refused the second time, the earlier password refused, the reason in both audit trails. So the smoke ends knowing the administrator's password even when it started without it, after a heal or an invitation accepted by hand. The last three steps take about two minutes: `scoped-role` (a unit of the run's own with a person who reads its users; they list only that unit's people, and the tenant's administrator is not found), `plan-change` (Standard until role export is refused, then the tenant's own plan until it works; a tenant on Standard goes the other way) and `kill-switch` (`kill.imports` on until a dry-run import answers `flags.killed`, then off; a tenant on Standard borrows Enterprise for the step). Each restores the tenant, also when it fails, and reports each wait; `scoped-role` deactivates the person it made, and any reader earlier runs left active. Then `second-factor` (a person of the run with an authenticator app and recovery codes, ADR-0047), `single-sign-on` (the tenant's "Smoke test provider" tested and connected, and a new person of the run signed in through it and created at that sign-in, ADR-0048), `end-session` (an administrator ends a person's session with a reason; its next request answers `auth.session_ended`, and the audit trail has the reason) and `revoke-person` (everything of a person with two sessions revoked; both answer `auth.session_revoked`), each deactivating the person it made (ADR-0049). Last come `audit-trail` (ADR-0050), `tls` (the ingress refuses TLS 1.0 and TLS 1.2's old suites, ADR-0054) and `key-rotation` (the tenant's index key rotated with the run's reason, every hash made again, the old version retired, and a sample value still found by its exact value, ADR-0054), which takes about a minute.
- `make e2e [TENANT=x]`: the Playwright tests against `https://<tenant>.localhost` with that administrator, read from `secret/tenants/<tenant>/smoke` (browsers once with `cd shell && npm run e2e:install`; `E2E_BASE_URL` points them elsewhere). Run `make smoke` with the same `TENANT` first. Each run works in a unit of its own, `E2E run <run>` under the root, with its branches, people and assignments inside it (`infra/compose/scripts/e2e-data.py`), and at the end, whatever the result, deactivates the people homed in the browser tests' units (this run's, and earlier runs' still active) and then the run's units. A run never sees what an earlier one left, and leaves no active people behind.
- `make integration [TENANT=x]`: the pipeline's stage on this machine: platform and control plane from images, the control database migrated and seeded through the control-plane image, then the smoke, its twenty-three steps (`TENANT=echo`, or `TENANT=smoke` on a laptop whose `acme` administrator has been accepted by hand).

- `make security`: the dependencies (every `packages.lock.json` and the shell's lock, dev packages included), their licences and the misconfigurations through Trivy, the repository's rules through Semgrep (their test first), then the gate; about 75 seconds with the scanners' images and database cached in `~/.cache/trivy`. `make images-security` scans the five local images (`IMAGE_REPOSITORY=foundation TAG=dev`) and writes their CycloneDX bills of materials to `artifacts/sbom/`. `make coverage` checks the floors after `make test COVERAGE=1` (which adds about 80 seconds) and `make shell-check` (ADR-0055).

### The pipeline from the laptop (ADR-0055)

- **Main takes no push.** Push the branch and open a pull request (`gh pr create`); it merges with `gh pr merge --merge` once every check is green and the branch is up to date with main (`gh pr update-branch` when it is not). `make protection-check` compares main's protection on GitHub with `.github/branch-protection.json`; `make protect-main` applies it again, as an administrator.
- **The release runs at 02:23 UTC** when main has changed since the last `v*` tag. To release now: `gh workflow run release.yml --ref main`. It takes CI's results from the pull request the merge came from; when none ran in full on main's tree (a documents-only merge on top of an older one), it asks for a full CI run on main and waits for it.
- **The monthly security report** opens an issue on the first of each month; run it now with `gh workflow run security-report.yml`. It also says when DB-IP no longer publishes the pinned location month, before an image build fails on it.

## 9. Known limits of the laptop stack

- A unit healed after a lost store has new credentials; its administrator's password is gone from the store until the smoke's next run or `make recover-admin` (section 5). Its factor key is new too: authenticator apps enrolled before the loss no longer verify, and their people need a reset of their factors (section 5), while passkeys keep working (ADR-0047).
- The browser tests' tenant names the roles it requires a second factor of (the tenant administrator and `e2e-mfa`), set by `e2e-data.py`; the default policy, every role holding a high-risk or critical permission, is proven by the .NET tests (ADR-0047).
- PostgreSQL is the 19 release candidate until the GA image; an RC to GA change can require `make reset`.
- Azurite implements most of the Azure Blob API, not all of it. Reading container properties is refused under a container signature, so the units check their container by listing one page instead.
- Tenant units share the platform network; isolation between tenants is the database roles, the container signatures and the unit tokens (proven by the Fleet tests), not the network. Network policies arrive on Kubernetes.
- The chiseled images print `Cannot load library libgssapi_krb5.so.2` once at start: Npgsql probes for Kerberos, which the image does not carry; the connection uses SCRAM and works.
- A platform document published with `make platform-document` holds every person of every unit until they accept it: `make accept-documents TENANT=<slug>` frees the stored test administrator before `make smoke`. The browser tests make new people on every run, and each of them would be held too, and a platform version cannot be retired: do not publish a platform document on a laptop you run `make e2e` on. The browser tests' own terms are a tenant document of the run, retired at its end.
- The tree of a tenant the browser tests run on gathers one inactive `E2E run <run>` unit per run, and the smoke one inactive `Smoke <run>` unit per run, with their people deactivated since S3 T2: no API deletes a unit yet.

| Symptom | Cause and fix |
|---|---|
| A unit's log says `permission denied` from the store on `transit/...`, or its API answers 500 on sign-in after `make update-unit` | The unit's policy does not grant its keys yet, or its keys were not made: run `make update-unit TENANT=<slug>` again and read the secrets step; a unit made before T9b gets its keys there |
| An update stops at the secrets step with "still holds the retired factor key", or at the migrate step with "authenticator app secrets are still sealed under the retired factor key" | The unit never had the update after T9b, whose seed moves its authenticator secrets onto the key service; this release can no longer move them and drops their old column (ADR-0054). Nothing has changed: run the unit's update with the images of a release from v2026.10.28.43 up to the last before V0 first, then this one. Where the key itself was lost, reset those people's second factors (`make recover-admin ... RESET_FACTORS=1` for the administrator), set the old column to null and remove the key from the unit and fleet secrets, then update |
| `make up-control` fails on `prepare-control` with a store refusal | `OPENBAO_ROOT_TOKEN` in `.env` no longer opens the store (section 4); the API's and the fleet's tokens come from it |
| `make rotate-key` answers 403 | The operator account lacks `tenancy.keys.manage` (re-run `make seed-control`), or its token is older than the recent sign-in the rotation asks: run the command again |
| `make up` ends with `tempo did not become ready` | `make logs SERVICE=tempo`; usually a configuration error after a version bump |
| `make up` stops on a service with a health timeout | `make logs SERVICE=<name>`; most often a port is taken on the laptop |
| Tenant units restart again and again; `docker logs tenant-<slug>-api-1` says `The secret store refused to read 'tenants/<slug>/unit': 403` | The store lost its data or was replaced (a store from before ADR-0028, or a `make reset` under running units): `make up-control` writes the control plane's secret, then `make update-unit TENANT=<slug>` for each unit heals it (section 5). For the smoke, provision a fresh tenant |
| `make up` ends with `OpenBao at http://localhost:8200 is not ready after 90 seconds` | The lines above it are the container's state, its health check and the end of its log. `no answer` with a container that is `restarting` or `exited`: the log says why the server stopped, usually its configuration or its volume. A server still starting on a slow machine: `make up` again |

| `make up` ends with `The store stays sealed` | `OPENBAO_UNSEAL_KEY` in `.env` is not the key the store was initialised with: the log printed above it says `failed to unseal`, after 90 seconds of `sealed`. Put the right key back; without it the data is locked, and `make reset` starts over with a new store |
| `make up` ends with `The root token in infra/compose/.env does not open the store` or `has no OPENBAO_ROOT_TOKEN` | The token line was lost or belongs to an earlier store. With `OPENBAO_RECOVERY_KEY`, `bao operator generate-root` inside the container makes a new root token; put it in `.env`. Otherwise `make reset` |
| `docker compose` says `OPENBAO_UNSEAL_KEY is missing` | The `.env` predates ADR-0028: `make env` adds the key and changes nothing else |
| `permission denied` on `/var/run/docker.sock` | Your user is not in the `docker` group: `sudo usermod -aG docker $USER`, then reopen the terminal |
| `bind: address already in use` for port 80 or 443 | Another web server on Windows or WSL; stop it or publish Traefik on other ports |
| `failed to bind host port 0.0.0.0:5200` when `make up-control` or `make integration` starts | The control plane from source is still running: `ss -ltnp 'sport = :5200'` shows the process; stop it |
| A control container fails to resolve `openbao` or `postgres` ("temporarily unavailable") | It was created during a failed start and kept a broken network namespace: `docker rm -f <container>`; the Makefile and the integration script recreate the two control containers on every start since T18 |
| `npm` errors with `UNC paths are not supported` or `CMD.EXE was started` | The Windows npm is on the PATH in WSL; install Node 26 with nvm inside WSL, `rm -rf shell/node_modules`, `make shell-install` |
| A unit keeps old behaviour after `make images` | The unit still runs the previous image: `docker compose -p tenant-<slug> images` shows `<none>` for it; `make update-unit TENANT=<slug>` after the build, not before |
| `https://<slug>.localhost` answers `404 page not found` | A router without TLS on the `websecure` entry point (fixed in T15; `traefik/traefik.yaml` must have `http.tls` on it) or no unit for that hostname: `docker compose ls` |
| A unit's log has `ALERT: the entitlements are unknown`; `/health/ready` shows `entitlements` degraded; role export answers `entitlements.feature_disabled` with the reason `unknown`; the Subscription page says the subscription cannot be confirmed | The unit has had no answer from the store for 24 hours, or never had one, so everything licensed is off (ADR-0034). If the log names a 403 on `tenants/<slug>/entitlements`, the unit's policy predates A4: `make update-unit TENANT=<slug>` writes the policy and the entitlements again. If the store does not answer, see the rows above about the store. Before 24 hours the readiness check is degraded with "has not answered since" and the last answer still stands |
| A unit's log has `ALERT: the settings have not refreshed`; `/health/ready` shows `settings` degraded | The unit's API or worker has not read `kernel_settings` for five minutes, so changes made in the console since then are not seen there; the values read before stand (ADR-0036). It is the database: see `make logs SERVICE=postgres` and the rows about the store and the database. The process that saved a change sees it at once; the others within 30 seconds of the database answering again |
| A unit's log has `ALERT: no flag rules are known`; `/health/ready` shows `flags` degraded | The unit has never read its flags, so every flag has its code default and no kill switch is on (ADR-0035). If the log names a 403 on `platform/flags` or `tenants/<slug>/flags`, the unit's policy predates A5: `make update-unit TENANT=<slug>` writes the policy and both paths. If the store does not answer, see the rows above about the store |
| A unit's flags are stale: `/health/ready` shows `flags` degraded with "has not answered since", and `flags.age` keeps growing | The store has not answered the unit's reads; the rules confirmed at the time shown stand, kill switches included, until it does. Nothing to do in the unit: bring the store back (rows above). A change made in the control plane meanwhile reaches the unit on its first good read |
| A change from `make kill-switch` or `make flag` has not reached the unit after a minute | The store refused the write: the control plane's log says `could not be written to the store`. The change is committed, and the fleet writes it within a minute (`make logs SERVICE=fleet` shows `Reconciled 1 of 1 flag path(s)`). Is the fleet running? If the unit's log names a 403 on a flags path, see the first row on flags above |
| The control plane's API or fleet does not start: `password authentication failed for user "control_app"`, or `permission denied for schema kernel_...` | The control plane's secret predates its roles, or a database was migrated by the superuser after them: `make secret-control` (or `make up-control`) prepares it again and moves everything to the owner; then `make migrate-control` |
| `make verify-control-audit` says `ControlAudit:AnchorsSasUrl is not set` | The fleet's secret predates the anchors: `make up-control` (or `make secret-control`, then restart the fleet) |
| The fleet's log has `ALERT: the audit chain of tenant <slug> ...`, the Chain status page shows the failure, and the control plane's trail has `tenancy.audit_chain_broken` | A verification did not pass: an event is missing, modified or relinked, or disagrees with its anchor. Read the record (`make verify-audit TENANT=<slug>`) as section 5's "Reading a verification failure" says, keep the database as it is, and follow `docs/security/incident-response.md`. A record that says `RESTORED` after a restore from a backup is accepted with `make audit-accept-restore` once investigated |
| A process's log has `ALERT: this process's clock is ... seconds off the time server`; `/health/ready` shows `clock` degraded | The host's clock drifted more than a second, which shifts every time it stores (TF-065). In WSL after the laptop slept: `wsl --shutdown` from Windows, or `sudo hwclock -s` inside WSL. Where no time server is reachable, `Telemetry__Clock__Enabled=false` stops the check (section 5) |
| The Alert rules page shows a rule as Failing, and the Security alerts page has an alert that names it | The rule's values are wrong (a misspelt key or rule in `Monitoring:Rules:*`, a value out of its bounds), it counts an event type no module declares, its evaluation threw, or the worker ran no pass for more than ten minutes; the page and the alert say which. Fix the operator's value in the unit secret (section 4), or start the worker; the rule says Running again at its next pass, a minute later (ADR-0056) |
| A page answers 429 `protection.rate_limited` during the smoke or by hand | A rate limit: the answer's `Retry-After` says how long to wait. The smoke waits; to raise a tenant's limit, use its Settings within the operator's bounds |
| `make kill-switch` answers 403 `authz.permission_denied` | The account is not an operator of the control plane, or the control plane's seed predates A5: `make seed-control` gives the administrator role `tenancy.kill_switches.manage` |
| The control plane's log, or the fleet's weekly line, lists flags past their removal date or rules for flags that are gone | `GET /api/v1/flags/report` shows the same with each owner. | `make apply-plan` says the store is behind | The store refused the write; the change is committed and the fleet writes it within a minute (`make logs SERVICE=fleet` shows `Reconciled the entitlements`). Is the fleet running? |
| The invitation link says the invitation does not exist | It was accepted already, or the seed ran again and re-issued it, and the provisioning report gave the new link once to the operator who asked that job. `make update-unit TENANT=<slug>` issues a new one while the administrator is still Invited, and prints it |
| `make provision`, `make update-unit` or `make recover-admin` printed no link | The report gives a job's link once, to the operator who asked: someone or something read the report first (the smoke reads it on its own runs), or the link expired. | The smoke fails at `recovery` with 409 `tenancy.tenant.not_provisionable`, or the job fails with `identity.recovery.not_administrator` or `not_allowed` | The tenant is not active, or its administrator is not an active tenant administrator of the whole tenant: an administrator still Invited needs `make update-unit TENANT=<slug>` (the seed re-issues the invitation, and the smoke accepts it); one whose role was removed needs it back from another administrator |

| A push to main answers `GH006: Protected branch update failed` | Main changes only through a pull request (ADR-0055): push a branch and open one |

## 11. Starting over

`make down-control` (if containers), stop `make run-control` and `make run-fleet`, then `make reset` deletes every platform volume, the store's included, and the store's token and recovery key lines in `.env`. The tenant units are separate projects: `docker compose ls` lists them; `docker compose -p tenant-<slug> down` removes each. Then `make up` (which initialises a new store), `make secret-control && make migrate-control && make seed-control`, and provision again. Delete `infra/compose/.env` only together with `make reset`; the credentials and the seal key must match the volumes.
