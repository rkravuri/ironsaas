# ADR-0036: Settings: typed definitions as the accessor, resolved in the unit, preferences that follow the person

**Status:** Accepted
**Date:** 2026-10-20
**Decided by:** Product owner and architect

## Context

TF-057 to TF-059 and TF-221 ask for settings declared in code with a key, a type (text, number, boolean, choice, JSON, secret reference), a default, a rule, the scopes a value may be set at and a description; one service that resolves user, unit walking up the tree, tenant and system default with a cache of at most 60 seconds; a console that shows them by module and scope with defaults, who changed what and when, and reset; an audit of every change with before and after; secret references that never show the secret; a typed accessor so an undeclared key does not compile; the effective non-secret settings for the shell; changes without a restart; and the last value with an alert when the cache cannot refresh. TF-021 makes the session limits tenant settings.

ADR-0034 and ADR-0035 built a channel from the control plane to the units through the store, for what the operator decides. Settings are not the operator's: they belong to the tenant, its administrators change them, and many will name the tenant's own units and people.

## Decision

1. **A typed definition is the accessor; there is no source generator.** A module declares each setting as a static `Setting<T>` in its Contracts (the type and the factories are in the vocabulary, `Iron.Kernel`), and lists them in `IModule.Settings`. Code reads `await settings.GetAsync(IdentitySettings.SessionIdleMinutes, context, ct)` and gets an `int`. A key nobody declared is a missing member, a key written as text has no overload, and a value read as another type does not convert, so all three are compile errors (TF-059 AC1); a Roslyn test compiles each. A declaration refuses a key that is not dotted lowercase words, a missing description, no scope, a choice without choices, a secret reference the shell may see, and a default that breaks its own rule.
2. **One list, written for the control plane and the shell.** `make catalogue` writes the settings into the catalogue the control plane carries (ADR-0034) and writes `shell/src/api/setting-keys.ts`, a TypeScript file of the keys the shell may see with their value types and defaults. The host test fails while either file and the code differ. `useSetting(key)` takes only those keys.
3. **Settings live in the unit.** The Settings module (`Iron.Kernel.Settings`, schema `kernel_settings`) keeps one row per setting and place: the tenant, a unit, or a person, the target being the unit's or the person's id. Every change also writes an append-only history row (before, after, who, when) and the audit event `settings.value_changed` or `settings.value_reset` with the key, the scope, the unit or the person, before and after, in one transaction (TF-058 AC1, ADR-0013). Settings do not travel through the store: the tenant decides them, they name the tenant's units and people, and no operator needs them.
4. **The resolution order.** For a person: their own value, then their home unit and the units above it, nearest first, then the tenant, then the default in code. For a unit (a record's owning unit, TF-221): the unit and the units above it, then the tenant, then the default. A level the declaration does not allow is skipped, and so is a stored value whose rule has since been tightened, so a bad value is never served. The tree is asked, one read of the materialised path (ADR-0030), only when some unit has a value for the key. "System" is the default in code; an operator-wide override is not part of S2. Where a module had a configured value before, the configuration remains the system default: Identity's `Identity:Session:IdleMinutes` and `AbsoluteHours` apply while the tenant has set nothing.
5. **A cache of at most 30 seconds, the last values through a failure.** Each process reads every value of the tenant before it serves, every 30 seconds (`Settings:RefreshSeconds`, at most 30), and at once after a change it saved. So the process that saved answers the change on its next request and every other process within 30 seconds, without a restart (TF-059 AC2). 30, not TF-057's 60, as A4's refresh, so a change reaches the shell's 30-second read of `/me/context` within a minute. A failed read keeps the last values, however old: a setting is the tenant's decision and no default is safer than it. After five minutes of failures the alert is raised: an error line starting `ALERT: the settings have not refreshed`, the gauge `settings.stale` (meter `Iron.Settings`), and the readiness check `settings` Degraded (TF-059 AC4).
6. **Saving, and who may.** `PUT /api/v1/settings/{key}` with a scope (`tenant`, `unit` with its id, `user`) and a value, and `DELETE` at a scope to reset, which removes the value there so the inherited one applies (TF-058 AC2). A value that breaks the rule is refused with the rule in words on the field `value` (TF-057 AC2); a scope the setting does not allow, an unknown key and an unknown unit are refused with their own codes. The permissions are `settings.values.read` and `settings.values.manage`, named with the three parts every permission has. A tenant's value needs `manage` tenant-wide, a unit's at the unit or above it (TF-221 AC3), and reading needs `read` at the place read. A person sets their own values without a permission, and the user scope is always the caller. Because the permission depends on the place in the request, the writes declare `RequireSignedIn` and the handler checks the permission at the place; the reads declare `settings.values.read` at any scope and check the place in the handler (ADR-0031's pattern). The evaluator audits every denial.
7. **Secret references keep the secret in the store.** The value stored for a secret-reference setting is a path under the unit's own `tenants/<slug>/settings/`, which the unit's store policy reads (the fleet's secrets step writes it). The API and the console see the path; `/me/context` leaves secret references out. Code reads the secret through `ISecretSettings`, which fetches the key `value` at the path from the store when asked and keeps it at most five minutes (TF-057 AC3, TF-059 AC3). No real secret setting exists yet; a test-only declaration proves it.
8. **Preferences follow the person.** `shell.colour_scheme` and `shell.density` are user settings. The browser keeps its copy in `localStorage`, which `public/scheme.js` and the density read before the first paint, so a reload never flashes. After sign-in the person's own value wins and is written to the copy; a person with no value yet takes up the choice this browser had; from then on a change in the browser is saved, and a change made in another browser arrives with `/me/context` and is applied. A new browser shows the device's scheme on the login page and the person's after sign-in.
9. **The first real settings.** `identity.session.idle_minutes` (tenant, 15 to 480, default 60) and `identity.session.absolute_hours` (tenant, 1 to 24, default 12): a new session takes them and keeps them, so a changed limit never shortens an open session, and `/me` answers the session's own limits, which the shell's warning follows. `identity.invitation.valid_days` (tenant and unit, 1 to 30, default 3, TF-018's 72 hours): an invitation takes the value of the home unit it is sent into.

## Options considered

- A source generator writing typed accessors from a declaration file. Rejected: the static definition already is a typed accessor the compiler checks, and a generator is a second build step to maintain, debug and keep in step with the declarations.
- String keys checked against a registry at run time. Rejected: TF-059 AC1 asks for a compile error, and a typo would surface only on the code path that reads it.
- Settings through the store, as entitlements and flags. Rejected for the reasons in decision 3.
- 60 seconds, as TF-057 allows. Rejected: two caches of 60 in series would let a change take two minutes to reach the shell.
- Let stale values expire into the defaults, as entitlements do after 24 hours. Rejected: a default is no safer than the tenant's last decision, and a session limit or an invitation's validity would change by itself.
- A separate endpoint for a person's preferences. Rejected: one endpoint with the user scope keeps one rule for saving, validation and audit; the scope is always the caller's.
- Preferences in the browser only. Rejected: a person who signs in on another browser would start over.
- A changed session limit applied to open sessions. Rejected: a session that shortens under someone working ends their work without the warning they expected; TF-021 limits sessions as they start.

## Consequences

- Easier: a module declares a setting in its own code and gets resolution, validation, the console, the audit, the shell's typed key and, for a secret, the store, without more work.
- Every process reads all of the tenant's values twice a minute. Fine for the settings in sight; revisit with many thousands of values (read only what changed since the last read).
- The console shows the setting's key and description from the server and its name from the shell's catalogue; a setting without a name there shows its key.
- An operator-wide override of a setting's default, writing a secret into the store from the console, and settings at a record's scope are later items.
