# ADR-0035: Feature flags: declared in code, ruled in the control plane, last known before defaults

**Status:** Accepted
**Date:** 2026-10-20
**Decided by:** Product owner and architect

## Context

TF-050 to TF-056 ask for feature flags of four types with rules by scope (global, region, tenant, organisation unit, user, percentage rollout, attribute match), evaluated through OpenFeature in the API and the shell; kill switches for the risky paths that only an operator flips, with a reason; a lifecycle in which a flag has an owner and a removal date and cannot linger; and a provider that can be replaced by configuration. S2 builds TF-050, TF-051, TF-052, TF-054 and TF-056, and the audit of rule changes from TF-053. Exposure events for experiments and tenant-visible flags are later.

ADR-0034 built the channel this decision reuses: the control plane writes to the store after every committed change, the unit reads its path every 30 seconds and keeps the last known answer, the shell reads `/me/context` every 30 seconds. ADR-0016 gave every unit a token that reads its own paths only.

TF-050 AC3 said that when the flag service is unavailable, the default in code applies. For a kill switch that is dangerous: if the store blinks while imports are stopped, the default ("not stopped") starts them again.

## Decision

1. **Declarations in code.** A module declares its flags in `IModule.Flags`: key, type (boolean, string, number, JSON), kind (release, experiment, operational, permission-like), purpose, owner, planned removal date and default. The `Flag` record refuses a declaration without an owner or a purpose, a default of another type, and a release or experiment flag without a removal date, so neither the build nor the catalogue can hold one. `make catalogue` writes every flag into the catalogue the control plane carries (ADR-0034), with its module and a status, `active` or `retired`.
2. **Kill switches are a reserved family.** `kill.<path>` is declared by the kernel's vocabulary (`KillSwitches` in `Iron.Kernel`) and nowhere else: email, webhooks, sms, ai, push and imports, each an operational boolean whose default is off. Every host therefore declares them, and a module that declares a `kill.` flag is refused. The slices that build email, webhooks, SMS, AI and push wire their switches; imports is wired now, on role import.
3. **Rules in the control plane, in Tenancy.** A flag's rules are a list: a scope and its target, an optional condition (a percentage of tenants or of users, or an attribute among values) and a value of the flag's type. They are replaced together, with the revision they were read at (a stale revision answers 409), in one transaction with an append-only history row (operator, before, after, reason) and the audit event `tenancy.flag_rules_changed`. A rule for a flag the catalogue does not have, a value of the wrong type, or a tenant that does not exist is refused. The permissions are `tenancy.flags.read`, `tenancy.flags.manage` and `tenancy.kill_switches.manage` (critical): they name the module that checks them, as every permission does. They exist only in the control plane's catalogue, so only its administrator role, which the operator client holds, carries them.
4. **A kill switch flips through its own endpoint, with a reason.** `PUT /api/v1/kill-switches/{path}` with `on`, `reason` and an optional tenant. On writes one unconditional rule at that scope; off removes it, so the switch is either on or absent. A rule that says false for a kill switch is refused with `tenancy.kill_switch.false_rule`, by this endpoint and by the rules endpoint alike: removing the rule is how a switch goes off. The reason is required, stored in the rule and the history, and audited as `tenancy.kill_switch_flipped`. A kill switch's rules can also be edited as a flag's, but only with `tenancy.kill_switches.manage`; anyone else gets 403 with "Only the platform's operators turn kill switches on and off." The rule keeps its first creation time while it is unchanged, so "since" is when the operator stopped the path.
5. **Two paths in the store.** Global and region rules of every flag go to `platform/flags`, one write for the whole platform: a global kill switch is one write, not one per tenant. A tenant's tenant, unit and user rules go to `tenants/<slug>/flags`, with the tenant's region and plan as attributes, so a plan change republishes it. Each path has a revision and a published revision in `kernel_tenancy.flag_publications`; the fleet worker writes every path the store refused, every minute. The fleet's secrets step widens the unit's policy to both paths and writes them on every provisioning and update.
6. **The unit reads both every 30 seconds and keeps the last known rules, without expiry.** `FlagRefresher` reads before the host serves and every 30 seconds (`Flags:RefreshSeconds`, at most 60), and keeps both documents in `kernel_flags.last_known` (on a change, and at most every ten minutes otherwise), so a restart during an outage still knows them. The row is written with one upsert, so the unit's API and worker can both write it at once on a first start without one of them failing on the unique key. A failed read keeps what the unit has, however old.
   - Why no expiry, unlike the entitlements' 24 hours: a flag carries no commercial promise that goes stale, and an expiry would switch a kill switch off by itself during a long outage.
   - The code defaults apply only when the unit never knew any rules. That is the alert: an error log line starting `ALERT: no flag rules are known` (once, then hourly), the gauge `flags.unknown` at 1 (meter `Iron.Flags`, beside `flags.age`, `flags.refresh_failures` and `flags.refusals`), and the readiness check `flags` Degraded. TF-050 AC3 is amended to say so.
7. **The evaluation order.** The most specific scope with a matching rule wins: user, then organisation unit (the principal's home unit first, then the units above it, nearest first), then tenant, region, global. Within a scope the rules are tried in their order; the first whose target and condition match decides. No match: the declaration's default. A percentage is a stable hash: SHA-256 of `<flag key>:<subject id>`, the first four bytes big-endian, modulo 10,000, so the same tenant or person always lands the same way on every node and in every release, and one flag's buckets do not follow another's. Attributes are `principal_type`, `plan` and `region`, and the list can grow. A rule whose value does not fit the flag's type is skipped, a second guard behind the control plane's refusal.
   - **A kill switch is the exception: it is on when any rule that applies says so, at any scope, whatever a more specific rule says.** So a tenant, unit or user rule can never exempt anyone from a switch the operator turned on for the platform or a region, and the control plane refuses a rule that says false (decision 4). Why: a kill switch stops a path because running it is dangerous now; an exemption would be a quieter second switch that keeps the path running for someone, unseen by the operator who stopped it, and still there when the switch goes on again next time. A tenant that needs its path back while the platform's stays stopped needs the fault fixed, not an exemption. The most specific rule that says so is the one reported to the banner, with its reason and time.
8. **OpenFeature in the API, chosen by configuration.** The .NET `OpenFeature` SDK with an in-house provider, `iron`, over the rules. `Flags:Provider` names it; an unknown provider, an unknown `Flags:Source`, or `store` without a configured store stops the host at start with a message that says which, and a provider that cannot start fails the start too. Each host binds its provider under a domain of its own, so hosts in one process do not share it. The evaluation context carries the tenant, its region and plan, the principal (the targeting key) and its type, and the home unit with the units above it. The control plane and the fleet are no tenant: they read global rules from `Flags:Rules` with `Flags:Source=configuration`.
9. **Filters in the API.** `RequireFlagOff("kill.imports")` and `RequireFlag("area.flag")` run after authentication and the entitlement check and before the permission check. A kill switch that is on answers 503 `flags.killed`, with `Retry-After: 30`, the flag and the operator's reason: the refusal is temporary and says nothing about the caller. A flag that is off answers 404 `flags.disabled`: the endpoint does not exist for this person yet. Both are logged, counted and audited as `flags.access_denied`. The start-up check refuses an endpoint naming a flag no module of the host declares. Role import requires `kill.imports` off.
10. **The shell evaluates nothing itself.** `/me/context` gains a `flags` part: every active flag evaluated for the person by the API's provider, whether rules are known, and, for an administrator only (a principal with a `.manage` permission for the whole tenant), the kill switches that are on with path, since when and reason. The shell's `@openfeature/web-sdk` provider answers from that part; `useFlag(key, default)` is the one hook. A flag it has no value for, a value of another type, or a flags part that fails to load gives the caller's default, and the shell works. The shell never decides security by a flag: it shows and hides, the API decides. The kill-switch banner sits in the page's flow above the work, in words with an icon.
11. **A flag cannot vanish while active.** Retiring a flag is an explicit change: the catalogue marks it `retired` in the same change that removes it from the code. `make catalogue` refuses, and the host test fails, naming the flag and its owner, when a flag leaves the code while the catalogue marks it active, or when a retired flag is still declared. The control plane reports flags past their removal date with their owner, and rules left for flags the catalogue no longer has or has retired: in its log at start, in `GET /api/v1/flags/report`, and in the fleet worker's log once a week.

## Options considered

- The rules in a control-plane part of `Iron.Kernel.Flags`. Rejected: a second control-plane module with its own schema and migrations, which would still need Tenancy for the tenants, their region and plan, and the store publishing that Tenancy already does for entitlements. The unit side stays in `Iron.Kernel.Flags`.
- One path per tenant, with the global rules copied into each. Rejected: a global kill switch would be one write per tenant, half done while the store refuses some of them.
- The code default when the store is unavailable, as TF-050 AC3 first said. Rejected: a kill switch would switch itself off during an outage.
- Let the last known rules expire after 24 hours, as the entitlements do. Rejected for the same reason.
- A flag service beside the store (flagd, Unleash or a hosted one). Rejected for now: another service per laptop and per region and another credential, for what the store already carries. OpenFeature keeps that door open (TF-056).
- Evaluate in the browser from the rules. Rejected: it would send other people's targeting and the rollout buckets to the browser, and two evaluators can disagree. The API evaluates once, for the shell too.
- 403 for a kill switch. Rejected: nothing is wrong with the caller's rights; 503 with `Retry-After` tells a client to come back.
- The most specific rule decides for kill switches too, so a tenant rule that says false exempts that tenant. Rejected after the review of A5 for the reasons in decision 7.
- Decide in the shell who sees the banner. Rejected: the API sends the kill switches to administrators only, so the reason never reaches anyone else's browser.

## Consequences

- Easier: a module declares a flag in its own code, and the catalogue, the control plane's checks, the evaluation, the API filter and the shell's hook come with it. A new risky path gets its kill switch by name.
- A kill switch that is on stays on through a store outage and a restart during it; a unit that never knew any rules alerts until it does.
- Every flag of the build is evaluated for `/me/context` every 30 seconds per signed-in person. Fine for the handful of flags in sight; revisit with hundreds (evaluate only the flags the shell asks for).
- Each unit reads two more paths twice a minute, beside its entitlements. The same review as ADR-0034 applies with many hundreds of units.
- A flag removed from code needs the catalogue changed in the same commit; the build says so, with the flag named.
- Later: exposure events for experiments (TF-053 AC2), tenant-visible flags (TF-055), a console page for rules, and the email, webhook, SMS, AI and push switches when their paths exist (S4 for email).
