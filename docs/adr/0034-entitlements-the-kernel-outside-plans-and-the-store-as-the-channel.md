# ADR-0034: Entitlements: the kernel outside plans, one catalogue, and the store as the channel

**Status:** Accepted
**Date:** 2026-10-20
**Decided by:** Product owner and architect

## Context

TF-040 to TF-046 ask the control plane to hold, per tenant, the licensed modules and features with a status (Enabled, Disabled, ReadOnly), subscription dates, user limits and a subscription type; to apply plans in one action with the differences shown first; to keep a history nobody can edit; and the unit to hide and refuse what is not entitled, with one effective-entitlement service whose cache is at most 60 seconds, so that a change "is visible everywhere within a minute". When the control plane is unreachable, the last known answer stands for 24 hours, with an alert (TF-043 AC3).

ADR-0029 placed entitlements in the kernel and made the layers explicit. ADR-0016 gave every unit a store token that reads its own path only. ADR-0017 made the control plane a unit like any other. The Business and Products layers are still empty, so nothing licensed per module exists yet; the proof uses a feature of a kernel module.

The task corrected two points of the old outline: a disabled module cannot "map no endpoints", because that needs a restart and the requirement is a minute; and the laptop proof needs something that can be switched off today.

## Decision

1. **The kernel is the platform, outside plans.** Kernel modules (audit, authorization, identity, files, entitlements, tenancy, fleet, and those to come) are always on and never in a plan. Business and Products modules are licensed per module. Features may be licensed in any layer: the kernel declares one now, `authorization.role_transfer` (role export and import), which the Enterprise plan has and Standard does not.
   - Why: every tenant needs the kernel to work at all, and kernel modules depend on each other (every module writes through audit and is guarded by authorization), so a plan without one is a broken tenant, not a cheaper one. What is sold is what a tenant could do without.
   - How the build holds it: `IModule` declares `Licence` (code and subscription type: per person, per transaction, platform) and `Features`, both empty by default. The architecture test `LicensingRules` refuses a kernel module with a licence and a Business or Products module without one. The catalogue lists the kernel modules under `platform`, and a plan that names one is refused with "is a platform module: it is always on and is never in a plan".
2. **One source: the declarations in code; the control plane reads a file made from them.** `LicensingCatalogue.From(modules)` builds the catalogue from the unit host's module list (`Iron.Host.Api.UnitModules`). `make catalogue` runs the host's `catalogue` command, which writes `src/Kernel/Iron.Kernel.Tenancy/Services/licensing-catalogue.json` and builds no host; Tenancy embeds the file, so the control plane image carries it, and checks every plan against it when it is saved, applied and seeded. A host test fails, naming `make catalogue`, when the file and the declarations differ, so every build that passes CI carries the catalogue of its own modules.
   - Why a committed file: the control plane must not load Business or Products modules (their services, contexts and dependencies), so it cannot build the catalogue itself. Writing the file during the build would make the control plane's image build run the unit host. A generated file under version control, held to the code by a test, gives the same guarantee, needs nothing at run time, and shows in a diff what a change adds to what can be sold.
3. **The store is the channel to the unit.** After every committed change the control plane writes the tenant's effective entitlements to the store at `tenants/<slug>/entitlements` (key `document`, `EntitlementsDocument` with a format version and a revision). When the store refuses, the change stays committed and the tenant's `published_revision` stays behind; the fleet worker writes every tenant whose copy is behind, every minute. The fleet's secrets step writes the unit's policy on every provisioning and update, for its unit secret and this path, so a unit made before A4 reads the path with its existing token after `make update-unit`; it writes the document again too, so a store that lost it heals with the unit (ADR-0028).
   - Why the store and not a call from the unit to the control plane: the unit already holds a token that reads its own path and nothing else (ADR-0016), so no new credential, no new network path from every unit to the control plane, and no runtime dependency of every tenant on the control plane, which can be down for an upgrade while the tenants work. The store is built to be read often and to be highly available; the control plane never needs to know where a unit runs.
4. **A minute everywhere: 30 seconds at the unit, 30 seconds in the shell.** The unit's `Iron.Kernel.Entitlements` reads the store every 30 seconds (`Entitlements:RefreshSeconds`, at most 60) and once before the host serves; the shell reads `GET /api/v1/me/context` with the session and every 30 seconds while its tab is visible, never while it is hidden, and at once when the tab is shown again. The two caches are in series: at 60 seconds each, as first written into the task, a change could take two minutes to reach the shell. At 30 each, it reaches the API within 30 seconds and the shell within a minute, and each cache stays within TF-043's "at most 60 seconds".
5. **The last known answer for 24 hours, then disabled, with an alert.** The unit keeps the last document in `kernel_entitlements.last_known` with the time the store last confirmed it (written on a change, and at most every ten minutes otherwise), so a restart while the store is down still knows. When the answer is older than 24 hours (`Entitlements:StaleAfterHours`), or there never was one, every licensed module and feature answers Disabled with the reason `unknown`; the kernel keeps working. The alert is an error log line starting with `ALERT: the entitlements are unknown` (once, then hourly), the gauge `entitlements.stale` at 1 (meter `Iron.Entitlements`, beside `entitlements.age` and `entitlements.refresh_failures`), and the readiness check `entitlements` Degraded with the reason. Degraded, not Unhealthy: the probe stays at 200 and the tenant keeps its platform. A path with nothing in it is an answer, not a failure: nothing is licensed, and nothing alerts.
6. **Filters, not unmapped endpoints.** `MapModules` maps a licensed module's endpoints into a route group that carries its licence; `RequireFeature("area.feature")` names a feature on an endpoint. The check runs inside the permission and sign-in filters, after authentication and before the permission, so a person whose tenant lacks the module hears that, and no permission denial is written for it; an anonymous endpoint is checked by `EntitlementFilter`. The refusals are 403 `entitlements.module_disabled`, `entitlements.read_only` (any method but GET, HEAD and OPTIONS on a read-only module or feature), `entitlements.feature_disabled` and `entitlements.seat_required`, each with `entitlement` and `reason` in the problem, logged, counted (`entitlements.refusals`) and audited as `entitlements.access_denied`. The start-up check refuses a feature no module of the host declares and a licensed endpoint without an `IEntitlementGate`. Endpoints stay mapped, so a change counts on the next request.
7. **One evaluator, on the unit's clock.** `IEntitlements` (Entitlements Contracts) and the API's `IEntitlementGate` are one service. A subscription runs from its start date to its end date, both included, in UTC; after the end date the plan's grace days follow, in which the status the control plane set still applies (reason `in_grace`); then it is Disabled (`expired`). Expired is never stored. A feature is governed by its module: a module that is not available makes its features unavailable (`module_unavailable`, TF-046 AC3), a read-only module makes them read only. A per-person module also needs the person's seat, looked up on every request, so a removed seat counts on the next one (TF-041 AC2).
8. **Plans in the control plane; seats in the unit.** A plan holds licensed modules (status, subscription type from the catalogue, seats), features and grace days. Applying one is a transaction: the tenant's plan, grace days and revision, its entitlements, one append-only history row per change with the operator, before and after, and the audit event; the dry run answers the differences and the warnings first. A new tenant gets its plan's entitlements in the transaction that creates it. The history has insert and select grants only, as `kernel_audit.events`. Seats name the tenant's people, so they live in the unit: the control plane holds the count, the unit the holders, and an assignment above the count is refused with the count in the message.
9. **The control plane and the fleet are no tenant.** Their Entitlements module reads the `Entitlements` configuration section instead of the store, with every feature of the build.

## Options considered

- License kernel modules like the others. Rejected: a tenant without one is broken, and kernel modules depend on each other.
- Let the control plane reference every Business and Products Contracts project and read the declarations there. Rejected: a second list of modules beside the unit host's, which drifts, and the control plane would load code it does not run.
- Write the catalogue during the build from the unit host. Rejected: the control plane's image build would have to build and run the unit host.
- Let each unit report its catalogue to the control plane. Rejected: the control plane would trust what a unit says it can sell, and a plan could not be checked before a unit exists.
- The unit calls the control plane for its entitlements. Rejected for the reasons in decision 3.
- The fleet re-applies the unit with the entitlements in its environment. Rejected: a restart per change, minutes instead of seconds, and no answer during an outage of the fleet.
- Unmap the endpoints of a disabled module. Rejected: it needs a restart, and the requirement is a minute.
- 60 seconds at the unit and in the shell. Rejected: two minutes in the worst case.
- Mark a unit Unhealthy when its entitlements are stale. Rejected: the ingress would take the whole tenant down, the platform included, over what only licensed parts need.
- Count a store with nothing at the path as a failure. Rejected: a tenant whose plan licenses nothing would alert forever.

## Consequences

- Easier: a Business or Products module is licensed by declaring its licence and features in its own code, and the build checks the rest; the check, the refusal, the audit and the shell's hiding come with `MapModules` and `RequireFeature`.
- A module or feature added to the unit host is licensable once `make catalogue` has written the file; the host test says so until then.
- Each unit reads the store twice a minute. Fine for the fleets in sight; revisit with many hundreds of units (a longer interval with a push, or a version check).
- A store unreachable for 24 hours switches off everything licensed in every unit; the kernel stays, and the alert says why.
- Tenants created before A4 have no entitlements until a plan is applied (`make apply-plan`), so they lose role export and import until then; the laptop's acme, bravo and echo were moved to Enterprise.
- Later: the counts of affected data in the preview (with the first module that has data), trials and their banners (TF-044), an operator's change of one entitlement without a plan, and seats in the console.
