# S4: platform services

The instruction file for slice S4 (`docs/slices/S4-platform-services.md`, ADR-0023). One section per task. **How to use:** start a fresh Claude Code session in `~/foundation` inside WSL, with a clean working tree on `main` and no unmerged `slice/*` branch, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, opens a pull request, and stops with a report. Bring the report to the design session; the answer is one message: accept and merge, or stop and adjust. T1 is complete; T2 to T9 are outlines, sharpened in the design session before each starts.

S4 gives every module and suite the services they share: events, jobs, files, notifications, documents, languages, import and export, forms, and connectors. It also delivers what S3 left waiting: every email, the PDFs of evidence packs and signature blocks, and two jobs. **The rule V carries into every task:** whatever S4 sends, attaches, exports, imports or asks about concerning a record goes only to people who may read that record, visibility tags included; and whatever a suite declares (templates, events, jobs, strings, forms, reference data) exists only where the suite is installed.

## T1. Domain events and the transactional outbox

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, docs/STATUS.md, docs/slices/S4-platform-services.md,
docs/adr/0001, 0007, 0013, 0029, 0042, 0043, 0044 and the ADRs of V, and TF-085, TF-110, TF-111,
TF-112 and TF-113 in docs/prd/foundation/technical-foundation-PRD.md. Then read
src/Kernel/Iron.Kernel.Data (the unit of work, the audit write in the same transaction, the sample
module), src/Kernel/Iron.Kernel.Api (IModule and module registration, the catalogue), the unit's
worker, src/Suites (the suite rules), tests/Iron.Architecture.Tests, and tools (make catalogue and
its drift test). Then read docs/prompts/S4.md: commit it alone first on a new branch slice/s4-t1 from
main, and follow section T1. Write a short plan into the session, and build without waiting for
approval unless the "When to stop" rule in CLAUDE.md applies. Done when: S4's plan has its task
table and the PRD's section 7.1 places TF-206 in S4; modules declare their events in code and the
catalogue lists them; an event is written in the same transaction as the change that raises it, and
never without it; subscribers inside the platform receive every event at least once, handle it once,
in order per record, with retries and a dead letter; an administrator inspects events and replays
them to a subscriber, audited; a suite's events exist only where the suite is installed; the ADR
says how a message broker could take over later; every criterion of TF-085 and TF-110 to TF-112 has
a test; make verify passes, make smoke TENANT=echo and make e2e TENANT=echo pass, and the change
merges through a pull request. Finish with the report, its Risk section, the matrix's counts, the
brief's six questions for any page you changed, and screenshots in both schemes. Then stop.
```

### Instructions

1. **The plan and the PRD.** Fill S4's task table from this file, with a State column, and record the owner's decisions above. Move TF-206 into S4 in the PRD's section 7.1, with a change-log line.
2. **The event catalogue** (TF-110).
   - A module declares each event it publishes in code: a name (`module.record.happened`, for example `identity.person.deactivated`), a version, the shape of its data, its owner, and whether it carries personal data (named fields only, never free text).
   - `make catalogue` lists events beside modules, features, flags and settings, grouped by suite, and its drift test covers them.
   - Versioning: adding an optional field keeps the version; anything else is a new version, and both versions are published until no subscriber uses the old one. Record the rule in the ADR.
   - An event carries identifiers, not copies of records: the record's type and identifier, the tenant, the actor, the time, the correlation id, and the data its declaration names.
3. **The transactional outbox** (TF-085).
   - Publishing an event inside the unit of work writes it to an outbox table in the same transaction as the change and the audit event. If the transaction rolls back, the event never existed.
   - A dispatcher in the unit's worker reads the outbox in order and hands each event to its subscribers. Dispatch has a measured latency target (for example, under a second on the laptop with the stack up); record what you measure.
   - Choose the outbox's place (one kernel table, or one per module schema) by the same kind of measurement V1 did for tags, and record the choice.
4. **Subscriptions inside the platform** (TF-111).
   - A module subscribes to an event by name and version, through the publishing module's Contracts, following ADR-0042: events let an earlier module or product hear from a later one without calling it.
   - Delivery is at least once. Each subscriber handles an event once, through a record of the events it has handled (an inbox), so a repeated delivery changes nothing.
   - Order is kept per record: two events about the same record reach a subscriber in the order they were written. Events about different records may run in parallel.
   - A failing handler is retried with growing waits, then the event goes to a dead letter for that subscriber, with the error, and an alert (T10b's rules). The other subscribers are not held up. T2's job console will show dead letters; until then they are listed through the inspection endpoint.
5. **Inspection and replay** (TF-112). An administrator, with a new permission, searches events by type, record, time and correlation id, sees which subscribers handled each one, and replays an event or a range to one subscriber. Replay is idempotent through the inbox, needs a reason and step-up, and is audited. The operator can do the same for a tenant through the control plane.
6. **Broker readiness** (TF-113, a Could). No broker is added. The ADR explains how the dispatcher's interface lets a broker (for example RabbitMQ, Kafka or Azure Service Bus) replace in-process delivery later, without changing publishers or subscribers.
7. **Suites.** A suite's events are declared, stored, dispatched and replayable only in units where the suite is installed. A unit without the suite has none of its events or subscribers.
8. **First real uses.** Prove the mechanism on the data tests' sample module, and on two real kernel events of your choice with a real subscriber each (for example, a person deactivated, or a unit merged). Name them and why in the report.
9. **Tests.** Each names its criteria, and every criterion of TF-085 and TF-110 to TF-112 has a test. Also: a rolled-back change leaves no event; a crash between commit and dispatch still delivers the event after restart; a repeated delivery changes nothing; order per record under parallel dispatch; a failing subscriber retried, then dead-lettered, while others continue; replay idempotent and audited; a suite's events absent where it is not installed; the catalogue's drift test. The smoke gains a step that raises a sample event and sees it handled.
10. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`.

Documentation: the next free ADR (the catalogue and versioning; the outbox's place and its measurement; at-least-once with an inbox; order per record; dead letters; replay; broker readiness; suites); a "Publishing and subscribing to events" section in the developer guide; the threat model of the events module; STATUS.

### Review checklist

- [ ] No event exists without its change, and no change loses its event.
- [ ] A repeated delivery changes nothing; order holds per record.
- [ ] One failing subscriber never holds up the others, and its dead letters raise an alert.
- [ ] Replay is idempotent, needs a reason and step-up, and is audited.
- [ ] A suite's events exist only where the suite is installed.

## T4. Notifications (outline)
