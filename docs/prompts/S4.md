# S4: platform services

The instruction file for slice S4 (`docs/slices/S4-platform-services.md`, ADR-0023). One section per task. **How to use:** start a fresh Claude Code session in `~/foundation` inside WSL, with a clean working tree on `main` and no unmerged `slice/*` branch, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, opens a pull request, and stops with a report. Bring the report to the design session; the answer is one message: accept and merge, or stop and adjust. T1 is complete; T2 to T9 are outlines, sharpened in the design session before each starts.

S4 gives every module and suite the services they share: events, jobs, files, notifications, documents, languages, import and export, forms, and connectors. It also delivers what S3 left waiting: every email, the PDFs of evidence packs and signature blocks, and two jobs. **The rule V carries into every task:** whatever S4 sends, attaches, exports, imports or asks about concerning a record goes only to people who may read that record, visibility tags included; and whatever a suite declares (templates, events, jobs, strings, forms, reference data) exists only where the suite is installed.

## T1. Domain events and the transactional outbox

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, docs/STATUS.md, docs/slices/S4-platform-services.md,
docs/adr/0001, 0007, 0013, 0029, 0042, 0043, 0044 and the ADRs of V, and TF-085, TF-110, TF-111,
TF-112 and TF-113 in docs/prd/foundation/technical-foundation-PRD.md. Then read
src/Kernel/Iron.Kernel.Data (the unit of work, the audit write in the same transaction, the sample
module), src/Kernel/Iron.Kernel.Api (IModule and module registration, the catalogue), the unit's
worker, src/Suites (the suite rules), tests/Iron.Architecture.Tests, and tools (make catalogue and
its drift test). Then read docs/prompts/S4.md: commit it alone first on a new branch slice/s4-t1 from
main, and follow section T1. Write a short plan into the session, and build without waiting for
approval unless the "When to stop" rule in CLAUDE.md applies. Done when: S4's plan has its task
table and the PRD's section 7.1 places TF-206 in S4; modules declare their events in code and the
catalogue lists them; an event is written in the same transaction as the change that raises it, and
never without it; subscribers inside the platform receive every event at least once, handle it once,
in order per record, with retries and a dead letter; an administrator inspects events and replays
them to a subscriber, audited; a suite's events exist only where the suite is installed; the ADR
says how a message broker could take over later; every criterion of TF-085 and TF-110 to TF-112 has
a test; make verify passes, make smoke TENANT=echo and make e2e TENANT=echo pass, and the change
merges through a pull request. Finish with the report, its Risk section, the matrix's counts, the
brief's six questions for any page you changed, and screenshots in both schemes. Then stop.
```

### Instructions

1. **The plan and the PRD.** Fill S4's task table from this file, with a State column, and record the owner's decisions above. Move TF-206 into S4 in the PRD's section 7.1, with a change-log line.
2. **The event catalogue** (TF-110).
   - A module declares each event it publishes in code: a name (`module.record.happened`, for example `identity.person.deactivated`), a version, the shape of its data, its owner, and whether it carries personal data (named fields only, never free text).
   - `make catalogue` lists events beside modules, features, flags and settings, grouped by suite, and its drift test covers them.
   - Versioning: adding an optional field keeps the version; anything else is a new version, and both versions are published until no subscriber uses the old one. Record the rule in the ADR.
   - An event carries identifiers, not copies of records: the record's type and identifier, the tenant, the actor, the time, the correlation id, and the data its declaration names.
3. **The transactional outbox** (TF-085).
   - Publishing an event inside the unit of work writes it to an outbox table in the same transaction as the change and the audit event. If the transaction rolls back, the event never existed.
   - A dispatcher in the unit's worker reads the outbox in order and hands each event to its subscribers. Dispatch has a measured latency target (for example, under a second on the laptop with the stack up); record what you measure.
   - Choose the outbox's place (one kernel table, or one per module schema) by the same kind of measurement V1 did for tags, and record the choice.
4. **Subscriptions inside the platform** (TF-111).
   - A module subscribes to an event by name and version, through the publishing module's Contracts, following ADR-0042: events let an earlier module or product hear from a later one without calling it.
   - Delivery is at least once. Each subscriber handles an event once, through a record of the events it has handled (an inbox), so a repeated delivery changes nothing.
   - Order is kept per record: two events about the same record reach a subscriber in the order they were written. Events about different records may run in parallel.
   - A failing handler is retried with growing waits, then the event goes to a dead letter for that subscriber, with the error, and an alert (T10b's rules). The other subscribers are not held up. T2's job console will show dead letters; until then they are listed through the inspection endpoint.
5. **Inspection and replay** (TF-112). An administrator, with a new permission, searches events by type, record, time and correlation id, sees which subscribers handled each one, and replays an event or a range to one subscriber. Replay is idempotent through the inbox, needs a reason and step-up, and is audited. The operator can do the same for a tenant through the control plane.
6. **Broker readiness** (TF-113, a Could). No broker is added. The ADR explains how the dispatcher's interface lets a broker (for example RabbitMQ, Kafka or Azure Service Bus) replace in-process delivery later, without changing publishers or subscribers.
7. **Suites.** A suite's events are declared, stored, dispatched and replayable only in units where the suite is installed. A unit without the suite has none of its events or subscribers.
8. **First real uses.** Prove the mechanism on the data tests' sample module, and on two real kernel events of your choice with a real subscriber each (for example, a person deactivated, or a unit merged). Name them and why in the report.
9. **Tests.** Each names its criteria, and every criterion of TF-085 and TF-110 to TF-112 has a test. Also: a rolled-back change leaves no event; a crash between commit and dispatch still delivers the event after restart; a repeated delivery changes nothing; order per record under parallel dispatch; a failing subscriber retried, then dead-lettered, while others continue; replay idempotent and audited; a suite's events absent where it is not installed; the catalogue's drift test. The smoke gains a step that raises a sample event and sees it handled.
10. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`.

Documentation: the next free ADR (the catalogue and versioning; the outbox's place and its measurement; at-least-once with an inbox; order per record; dead letters; replay; broker readiness; suites); a "Publishing and subscribing to events" section in the developer guide; the threat model of the events module; STATUS.

### Review checklist

- [ ] No event exists without its change, and no change loses its event.
- [ ] A repeated delivery changes nothing; order holds per record.
- [ ] One failing subscriber never holds up the others, and its dead letters raise an alert.
- [ ] Replay is idempotent, needs a reason and step-up, and is audited.
- [ ] A suite's events exist only where the suite is installed.

## T2. Jobs

Sharpened on 2026-10-30 after T1. Background work today runs as separate loops in the unit's worker (sealing the audit chain, dispatching events, retention, re-encryption, alert rules, digests to come). T2 gives every module and suite one framework for jobs: declared in code, run exactly once per tenant per interval even with several worker processes, visible and controllable in a console, retried with backoff, dead-lettered with an alert, and fair between tenants (TF-120 to TF-124). It also closes two of S3's exceptions: a job triggered by a request links to that request's trace (TF-130 AC3), and a job's queries and telemetry stay within its own tenant (TF-003 AC2).

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, .claude/rules/frontend.md, docs/STATUS.md,
docs/slices/S4-platform-services.md, docs/adr/0010, 0019, 0044, 0050, 0056, 0060 and the ADRs of V,
and TF-003, TF-120 to TF-124 and TF-130 in docs/prd/foundation/technical-foundation-PRD.md. Then read
the unit's worker and every background loop in it (the chain sealing, the event dispatcher, retention,
re-encryption, the alert rules), src/Kernel/Iron.Kernel.Telemetry, src/Kernel/Iron.Kernel.Fleet (the
unit's resource limits and its template), src/Kernel/Iron.Kernel.Monitoring, src/Suites, and in the
shell the console and the Domain events page. Then read docs/prompts/S4.md, replace section T2 with
docs/prompts/S4-T2.md, delete that file, and commit the prompt alone first on a new branch
slice/s4-t2 from main. Then follow section T2: write a short plan into the session, and build without
waiting for approval unless the "When to stop" rule in CLAUDE.md applies. Done when: jobs are declared
in code with schedule or trigger, scope, timeout, retry policy, concurrency and priority class; with
two worker processes, exactly one run happens per tenant per interval; a timed-out job is cancelled,
logged and retried; administrators and the operator see, pause, resume, trigger and re-run jobs,
audited, in a console that also shows dead letters of jobs and events; retries grow with jitter and
end in a dead letter with an alert; a missed schedule raises an alert; the worker's existing loops run
as jobs; priority classes order the work and a suspended tenant's jobs are skipped; a job started by a
request links to its trace, and its queries and telemetry stay in its tenant; a suite's jobs run only
where it is installed; every criterion of TF-120, TF-121, TF-123 and TF-124 has a test or an
exception with its home; make verify passes, make smoke TENANT=echo and make e2e TENANT=echo pass,
and the change merges through a pull request. Finish with the report, its Risk section, the matrix's
counts, the brief's six questions for the pages you changed, and screenshots in both schemes. Then stop.
```

### Instructions

1. **Jobs in code** (TF-120).
   - A module declares each job: name, a schedule (a cron expression in the tenant's time zone, or an interval) or a trigger (an event from T1, or an explicit start), scope (this tenant), timeout, retry policy, concurrency (one at a time, or parallel up to a limit), priority class (interactive, normal, bulk) and owner. The catalogue lists jobs by suite, with its drift test.
   - Jobs must be idempotent; the developer guide says how, and the declaration names the key that makes a run unique.
   - **Exactly once per tenant per interval, with several workers.** Use PostgreSQL itself for the coordination (no new infrastructure): a lease or advisory lock per job and interval, so a second worker process skips a run another already holds. Compare a proven library with a scheduler on PostgreSQL built in the repository, choose by fit and simplicity, and record the choice in the ADR. Prove it with two worker processes against one tenant database.
   - A run that passes its timeout is cancelled, logged, and retried by its policy (AC2). A retried run has the same effect as one run (AC3).
2. **The worker's loops become jobs** (TF-124). The chain sealing and its verification, the event dispatcher and its archiving, retention and archive, re-encryption, the alert rules, session and token cleanup, and the flag and setting cache refresh run on the framework, keeping their behaviour and their tests. New tenants get every maintenance job active (AC1). The jobs that need later work become exceptions with their homes: notification delivery (T4), webhook delivery (T9), file quarantine and orphan purge (T3), metering (with billing), and backup verification (the first Azure deployment).
3. **Retries, dead letters and alerts** (TF-123). Exponential backoff with jitter up to the policy's limit, then a dead letter with the error and an alert (T10b's rules). An alert also fires when dead letters grow, and when a job misses its schedule by more than one interval.
4. **The job console** (TF-121).
   - In the console, for administrators with the jobs permission: every job with its schedule, its last and next run, durations, the last failure with its message and run log, and the backlog. Pause, resume, trigger now, and re-run a failed run, each with a reason and audited. Without the permission, the page is refused (AC3).
   - One "Dead letters" view lists the dead letters of jobs and of T1's event subscriptions together, each replayable from there.
   - The operator does the same for a tenant through the control plane (`make jobs TENANT=x`, `make job-run`, `make job-pause`), audited in both planes.
5. **Fairness and priority** (TF-122, a Should).
   - Inside a unit, priority classes order the queue: interactive before normal before bulk (AC2). A job without a declared class is refused in tests (AC4).
   - Between tenants, fairness comes from what each unit cannot exceed: its container's CPU and memory limits (from S1) and a connection limit on its database role, set by the fleet. Prove AC1 with a bulk sample job saturating one tenant while another's job still starts within a minute, on the laptop with two units.
   - A suspended tenant's jobs are skipped and logged (AC3).
6. **Traces and tenant scope** (S3's exceptions).
   - A job started by a request carries the request's trace context, and its spans link to the originating trace (TF-130 AC3).
   - A job's database connection is its tenant's only, and its telemetry carries its tenant's identifier (TF-003 AC2). Prove both, and remove the two exception rows.
7. **Suites.** A suite's jobs are declared and run only where the suite is installed; removing a suite holds its jobs as T1 holds its deliveries.
8. **The shell.** The Jobs page and the Dead letters view in the console, on the console template, every string in the catalogue, the scan in both schemes.
9. **Tests.** Each names its criteria. Also: two worker processes and one run per interval; a crash during a run, recovered by the next worker; pause and resume; a re-run after a fix; the priority order; the missed-schedule alert; the loops' behaviour unchanged after the move. The smoke gains a step that triggers a sample job and finds its run.
10. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, the fairness proof with two units, `make smoke TENANT=echo`, `make e2e TENANT=echo`.

Documentation: the next free ADR (jobs in code; coordination on PostgreSQL and the choice; idempotency; priority classes and fairness; the loops moved; dead letters in one view); a "Writing a job" section in the developer guide; the runbook (the job console, the operator's job targets, reading a missed-schedule alert); the threat model; STATUS.

### Review checklist

- [ ] Exactly one run per tenant per interval, proven with two workers.
- [ ] Every existing loop runs as a job, with its behaviour unchanged.
- [ ] Every failure ends in a retry or a dead letter with an alert, never in silence.
- [ ] Pause, resume, trigger and re-run are audited, with a reason.
- [ ] One tenant's bulk work cannot stop another's.
- [ ] TF-130 AC3 and TF-003 AC2 are proven, and their exceptions removed.

## T5. Documents (outline)

## T6. Localisation (outline)

TF-140 externalised strings with a translation workflow, a pseudo-language in every build that fails on untranslated text, and German as the first real second language; TF-141 server messages and errors localised, including audit event names; TF-142 locale formats for dates, numbers and currencies; TF-145 Unicode and locale-aware text (sorting, searching, comparison). A suite's strings exist only where it is installed. Right-to-left layouts belong to the experience foundations slice.

## T7. Import, export and reference data (outline)

TF-205 the import framework (templates, validation, a dry run with errors per row, then a confirmed apply, audited), on T1's events and T2's jobs; TF-086 bulk loading; TF-089 export and portability; TF-088 reference data and seeding, with one seed hash per installed suite (V's carry-over). Every export and import goes through the record's access policy, tags included.

## T8. Forms (outline)

TF-242 the forms engine (sections, typed questions, validation, conditional questions, scores, versions, attachments with issue and expiry dates, section reviewers, pre-fill, response versions with comparison), and surveys for any suite; TF-245 mapping answers to records as change proposals handed to the owning module, never direct writes; TF-246 the one-time verified link for people without an account (a known contact, an emailed code, one purpose, expiry, rate limits, audit). A form about a record follows the same access rule as notifications.

## T9. Connectors and webhooks (outline)

TF-114 outbound connectors and webhooks on T1's events (signed payloads, retries, delivery log, per-tenant configuration); TF-206 connector configuration for external systems, with secrets in the store, and the three connector kinds Supplier Management needs: identity and tax status, bank account verification, sanctions screening. Providers are chosen per country when Supplier Management is built; T9 proves each kind with a test double.

## S4-close (outline)

S4 as a done slice in the matrix, with every gap an approved exception with its home; STATUS settled; the documentation true for S4; the closing notes; S5's plan readied; an on-demand release on main; the tag `s4-done`.
