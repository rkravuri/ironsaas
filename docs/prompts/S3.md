# S3: trust and compliance

The instruction file for slice S3 (`docs/slices/S3-trust-and-compliance.md`, ADR-0023). One section per task. **How to use:** start a fresh Claude Code session in `~/foundation` inside WSL, with a clean working tree on `main` and no unmerged `slice/*` branch, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, and stops with a report. Bring the report and `git diff --stat main..slice/<task>` to the design session; the answer is one message: accept and merge, or stop and adjust. T1 is complete; T2 to T10 are outlines, sharpened in the design session before each starts.

S3 makes IronSaaS Foundation trustworthy for regulated customers: stronger sign-in (passwords, MFA, single sign-on), control over sessions, an audit trail nobody can alter unnoticed, field-level change history, electronic signatures with their manifestation, evidence for auditors, and the security practices behind them. Part 11 controls are active for every tenant from S3 (the technical PRD's D-16).

```

docs/prompts/S3.md: commit it alone first on a new branch slice/s3-t1 from main, and follow section

stop" rule in CLAUDE.md applies. Done when: S3's slice plan has its task table; every test names the
requirement criteria or the decision it proves; make trace builds the matrix with each test's

make shell-check, make shell-a11y and make format are clean. Finish with the report: the counts of
```

### Instructions

1. **The slice plan.** Fill the task table of `docs/slices/S3-trust-and-compliance.md` from this file's table, with a State column. Fold every STATUS later item that belongs to S3 into the task it fits, and say which in the plan.
2. **Naming what a test proves.** Every test names at least one of:
   - a requirement criterion, written `TF-033 AC2` (or `REQ-012 AC1` for a suite's requirement), or a whole requirement `TF-033` when it proves all its criteria;
   - a decision, written `ADR-0029`, for tests that prove a rule of the build or the architecture rather than a requirement.

   The form, by test kind:
   - **.NET:** a custom trait attribute in `Iron.Testing`, `[Proves("TF-033 AC2")]`, usable several times, filterable (`--filter "proves=TF-033"`), with an analyzer or an architecture test that refuses a test method without one.
   - **Vitest and Playwright:** the test title ends with the bracketed list, for example `"a child-unit administrator sees only its users [TF-033 AC2]"`; a lint rule or a test refuses a title without one.
   - **The smoke:** each step names what it proves in its report line.
   - Record the forms in ADR-0044.
3. **The backfill.** Name what every existing test proves, from S1 and S2. Read each test against the requirement texts; do not guess from a test's name alone. A test that proves nothing the documents state is listed in the report for the design session, not tagged to fit.
4. **The matrix.** `make trace` reads the requirement documents and the tests' result files (TRX from `dotnet test`, JUnit from Vitest and Playwright, the smoke's report) and writes, into the build output (not committed):
   - per requirement and criterion: the tests that prove it, with pass or fail from the last run;
   - the requirements of each done slice (from the slice plans' requirement lists) without a test for every criterion;
   - tests naming an identifier that does not exist, which fails the command.

   A requirement of a done slice without a test for a criterion fails the command too, unless it is listed in `docs/trace/exceptions.md` with its reason and the date it was approved. Write the first exceptions list from the backfill's findings; the design session approves it at the review.
5. **CI.** The CI workflow produces the result files, runs `make trace`, and uploads the matrix as an artifact on every run; the release workflow keeps the matrix with the images it builds. TF-218's validation pack (T8) builds on this.
6. **A check sequence that holds under load.** The shell's page tests have timed out at 5 seconds when they ran straight after `make test` with the stack up (STATUS). Measure the slowest page tests under that load, find the cause, and choose the fix by the measurement: fewer workers when the machine is loaded, a longer default for page tests only, or a pause between suites. Record the choice in ADR-0044. Add `make verify`, which runs `make prd-check`, `make test`, `make shell-check`, `make shell-a11y`, the format check and `make trace` in that order. Done when it passes three times in a row with the stack running.
7. **Documentation.** ADR-0044 (the forms, the matrix, the exceptions list, the reliability choice); a section "Naming what a test proves" in the developer guide; a line in the definition of done ("every new test names the requirement criteria or the decision it proves"); a line in CLAUDE.md's rules; `.claude/rules/backend.md` and `frontend.md`; STATUS.

### Review checklist

- [ ] Every test names what it proves, and the build refuses one that does not.
- [ ] The matrix shows each criterion's tests with their results, and fails on an unknown identifier.
- [ ] Done slices are covered criterion by criterion, or their gaps are listed with reasons.
- [ ] CI publishes the matrix.
- [ ] `make verify` passed three times in a row with the stack running.

## T2. Passwords: policy, lockout, recovery and change

Sharpened on 2026-10-21 after T1. TF-012 (policy, history and lockout), TF-017 (recovery and change) and TF-019 (account security events). It also closes two STATUS items from S2: a tenant whose administrator password is lost cannot recover it, and test runs leave people behind because nobody can be deactivated.

Email delivery arrives with S4's notifications. Until then, a recovery link is handed over by a person, as invitations are today, and the security events are shown in the product rather than emailed. TF-012's lockout email and TF-019's emails become exceptions with their home in S4.

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, .claude/rules/frontend.md, docs/STATUS.md,
docs/adr/0014 (identity, sessions and passwords), 0031, 0036 and 0044, and TF-010, TF-011,
TF-012, TF-017, TF-018, TF-019 and TF-036 in docs/prd/foundation/technical-foundation-PRD.md.
Then read src/Kernel/Iron.Kernel.Identity (the login, session and invitation services, the
password hasher, the seeder), src/Kernel/Iron.Kernel.Settings, src/Kernel/Iron.Kernel.Tenancy and
src/Kernel/Iron.Kernel.Fleet (how the fleet runs a command in a unit), tools/Iron.Smoke, shell/e2e,
and in the shell src/auth and the identity module. Then read docs/prompts/S3.md: replace section
T2 with docs/prompts/S3-T2.md, delete that file, and commit the prompt alone first on a new branch
slice/s3-t2 from main. Then follow section T2: write a short plan into the session, and build
without waiting for approval unless the "When to stop" rule in CLAUDE.md applies. Done when: the
password policy is a set of tenant settings enforced on every path that sets a password; lockout
counts failures for known and unknown login identifiers alike and an administrator can unlock;
history refuses reuse; a recovery link is one-time, 15 minutes, consumed on use, and issued by an
administrator for a person in scope or by the operator for a tenant's administrator, with a reason,
audited in both planes; a person changes their password with the current one and may end other
sessions in the same step; security events are recorded and shown in My profile; a person can be
deactivated and reactivated, and the smoke and the browser tests deactivate the people they create;
every new test names what it proves; make verify passes, and make smoke TENANT=echo and make e2e
TENANT=echo pass. Finish with the report, the matrix's counts for TF-012, TF-017 and TF-019, the
brief's six questions for the pages you changed, and screenshots of them in both schemes. Then stop.
```

### Instructions

1. **The policy as tenant settings** (TF-012, A6):

   | Setting | Default | Allowed |
   |---|---|---|
   | Minimum length | 12 | 8 to 64 |
   | Common-password check | on | on only |
   | History depth (passwords that may not be reused) | 10 | 0 to 24 |
   | Maximum age | off | off, or 30 to 365 days, with a warning 14 days before |
   | Lockout threshold, window, duration | 5 failures in 15 minutes, locked 15 minutes | 3 to 10; 5 to 60 minutes; 5 to 120 minutes |

   - The same rules apply on every path that sets a password: accepting an invitation, changing it, and using a recovery link. They are checked in the API; the shell shows them in words before the person types, and shows which one failed.
   - No composition rules (character classes). Length and the common-password list protect better, as NIST SP 800-63B recommends.
   - The common-password list is bundled with the image, never fetched at runtime; its source and licence go into `docs/licences.md`.
   - Maximum age stays optional because some regulated customers' procedures require it.
2. **Lockout.**
   - Failures are counted per login identifier, including identifiers that do not exist, so the locked answer never reveals whether an account exists (TF-011).
   - While locked, even the correct password is refused with the locked message (TF-012 AC2).
   - An administrator with `identity.users.manage` at the person's home unit can unlock; unlocking is audited.
   - Attempts spread over many identifiers from one address are T9's rate limits, not this rule.
3. **History.** The last N password hashes (Argon2id) are kept per person; a match is refused with its reason.
4. **Recovery** (TF-017).
   - A recovery link carries a one-time code, valid 15 minutes, consumed on use; a newer link makes the older one invalid.
   - Using it sets a new password under the policy and ends all of the person's sessions.
   - Who can issue one:
     - **an administrator** for a person in their scope, shown once with a copy button, as invitations are;
     - **the operator**, through the control plane, for a tenant's administrator, with a reason, through a command the fleet runs in the unit. It is audited in both planes, and the tenant's audit trail names the operator and the reason;
     - **the person themself** once email exists (S4). Until then, the login page's "Forgot your password?" says to ask the administrator.
5. **Change** (TF-017). In My profile: the current password, the new one under the policy, and "End my other sessions", ticked by default. Audited.
6. **Security events** (TF-019).
   - Recorded for: password changed, recovery link issued, recovery link used, lockout, unlock, a password set by recovery, and (later) MFA changes and impersonation.
   - Shown to the person in My profile, under "Security activity", newest first.
   - Each is also an audit event. Email delivery is S4: TF-012's lockout email and TF-019 AC1 become exceptions with their home in S4.
7. **A person's life cycle.**
   - Deactivate and reactivate a person, with `identity.users.manage` at their home unit. A deactivated person cannot sign in, their sessions end, and their tokens are refused. Both actions are audited and recorded as security events.
   - The last tenant administrator cannot be deactivated, by the same guard as A2.
   - The smoke and the browser tests deactivate the people they create, at the end and whatever the result, so runs stop leaving people behind.
   - The smoke uses the operator's recovery when it does not know a tenant administrator's password, which ends STATUS's item about healed tenants.
8. **The shell.** The password form with the policy in words; Change password in My profile; Unlock, Issue a recovery link, Deactivate and Reactivate on the user record, each shown only where `/me/access` allows it; the "Forgot your password?" text on the login page; "Security activity" in My profile. Every string in the catalogue; the scan covers the new dialogs.
9. **Tests.** Each names its criteria. They cover: each policy setting and its limits; the common-password refusal; lockout for a known and an unknown identifier; unlock; history; a recovery link used once, used twice, expired, and replaced; the operator's recovery with its audit in both planes; a change ending other sessions; deactivation ending sessions and refusing tokens; the last-administrator guard.
10. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`.

Documentation: the next free ADR (ADR-0046 if nothing else takes it first) on (the policy's defaults and why no composition rules, lockout without revealing accounts, the three ways to issue recovery, the operator's recovery and its audit); the Identity README; the runbook (`make recover-admin TENANT=x`, or the control-plane call, and when to use it); STATUS.

### Review checklist

- [ ] Every path that sets a password applies the same policy.
- [ ] Lockout does not reveal whether an account exists.
- [ ] A recovery link is one-time, 15 minutes, and ends all sessions when used.
- [ ] The operator's recovery needs a reason and is visible in the tenant's own audit trail.
- [ ] Deactivation ends sessions and refuses tokens; the last administrator stays.
- [ ] Test runs leave no active people behind.

## T3. Multi-factor authentication and step-up re-authentication

Sharpened on 2026-10-21 after T2. TF-013: authenticator-app codes (TOTP), passkeys (WebAuthn), recovery codes, and a tenant policy that requires MFA for everyone or for roles. It also adds one kernel mechanism that later tasks reuse: **step-up re-authentication** before a high-risk action (new requirement TF-248). T5's break-glass, T7's electronic signatures and T8's second approvals all build on it.

TF-013's fallback of one-time codes by email or SMS needs S4's notifications; it becomes an exception with its home in S4. Assertions of MFA by an identity provider belong to T4.

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, .claude/rules/frontend.md, docs/STATUS.md,
docs/adr/0014, 0016, 0031, 0036, 0044 and 0046, and TF-011, TF-012, TF-013, TF-017, TF-019,
TF-026, TF-063 and TF-073 in docs/prd/foundation/technical-foundation-PRD.md. Then read
src/Kernel/Iron.Kernel.Identity (login, sessions, recovery, security events, the person's life
cycle), src/Kernel/Iron.Kernel.Api (the endpoint filters), src/Kernel/Iron.Kernel.Settings,
tools/Iron.Smoke, shell/e2e, and in the shell src/auth, the login and recovery pages and My
profile. Then read docs/prompts/S3.md: replace section T3 with docs/prompts/S3-T3.md, delete that
file, and commit the prompt alone first on a new branch slice/s3-t3 from main. Then follow section
T3: write a short plan into the session, and build without waiting for approval unless the "When to
stop" rule in CLAUDE.md applies. Done when: a person can enrol an authenticator app and passkeys,
receives recovery codes shown once, and signs in with a second factor; a tenant setting requires
MFA for everyone or for roles, and a person who must have it enrols before reaching any page; wrong
codes meet a cooling period; a lost device is recovered with a recovery code or by an
administrator's reset under T2's escalation rule; high-risk actions ask for a fresh
re-authentication (TF-248); the browser tests prove a passkey with a virtual authenticator; every
new test names what it proves; make verify passes, and make smoke TENANT=echo and make e2e
TENANT=echo pass. Finish with the report, the matrix's counts for TF-013 and TF-248, the brief's
six questions for the pages you changed, and screenshots of them in both schemes. Then stop.
```

### Instructions

1. **Factors.**
   - **Authenticator app (TOTP, RFC 6238):** 30-second steps, 6 digits, one step of clock tolerance either way, and a code accepted once only. Enrolment shows a QR code and the secret as text for manual entry, then asks for one code to confirm before the factor is saved.
   - **Passkeys (WebAuthn):** several per person, each with a name the person chooses; user verification required. A passkey is a full second factor.
   - **Recovery codes:** 10 codes, shown once at the first enrolment with copy, download and print; stored hashed; each works once; regenerating replaces them all.
   - The factors' secrets are encrypted at rest with a key from the unit's secret store (TF-073), never stored in plain text, never logged.
   - Use open-source libraries pinned exactly and at least two weeks old (ADR-0003): for example Fido2NetLib for WebAuthn on the server, the browser's own WebAuthn API (or a small MIT helper) in the shell, and a QR library. Record their licences.
2. **Sign-in with a second factor.**
   - After a correct password, a person with a factor sees a second step: a passkey, a code, or a recovery code. The password step alone creates no session; the half-done state lives at most 5 minutes.
   - **Wrong codes** (TF-013 AC2): after 3 wrong codes, a cooling period of 60 seconds, doubling with each further 3, up to 15 minutes. Ten wrong codes in a row lock the login as T2's lockout does. The answer never says which part was wrong in a way that helps an attacker.
   - **Passkey sign-in without a password** is a tenant setting, off by default. When on, a person may sign in with a passkey alone, since a passkey with user verification is already two factors.
3. **The policy** (TF-013 AC1), as tenant settings (A6):
   - MFA required for: nobody, roles (chosen by the tenant; default: the roles that hold a high-risk or critical permission), or everyone. Default: roles.
   - Allowed factors: authenticator app, passkeys, or both. Default: both.
   - A person who must have MFA and has no factor is taken to enrolment after the password step, before any page. There is no grace period by default; a tenant may set one of up to 14 days.
   - Service accounts keep their client credentials; MFA does not apply to tokens.
4. **A lost device** (TF-013 AC3).
   - Using a recovery code signs the person in, consumes the code, and asks them to enrol a new factor at once.
   - An administrator may reset a person's factors, under T2's escalation rule (only for someone whose permissions they hold), with step-up (item 5) and a reason.
   - The operator's `make recover-admin` also resets a tenant administrator's factors when asked, with the same audit in both planes.
   - Every enrolment, removal, reset and recovery code use is a security event (TF-019) and an audit event.
5. **Step-up re-authentication** (new requirement TF-248, written into the technical PRD with acceptance criteria in the usual format):
   - An endpoint can require a recent authentication: `RequireRecentAuthentication(minutes)`, default 5 minutes. If the session's last authentication is older, the API answers with a problem that the shell turns into a re-authentication dialog: the password and, when the person has one, the second factor. The original action then continues.
   - First uses: issuing a recovery link; resetting someone's factors; deactivating a person; granting a role with a high-risk or critical permission; changing the MFA policy itself.
   - T5's break-glass, T7's electronic signatures and T8's second approvals use the same mechanism.
   - Record it in the ADR together with the factors.
6. **The shell.**
   - The second-step page at sign-in; the enrolment flow, forced when required; the recovery codes screen.
   - My profile's Security tab: the factors (add, rename, remove), regenerate recovery codes, each behind step-up.
   - The user record: "Reset factors", shown only where `/me/access` and the escalation rule allow it.
   - The console's Settings page: the MFA policy.
   - The re-authentication dialog as a shared component.
   - Every string in the catalogue; the scan covers every new page and dialog in both schemes.
7. **Tests.** Each names its criteria. They cover: TOTP with clock tolerance and a replayed code; a passkey registered and used, in the browser tests with Chromium's virtual authenticator; recovery codes used once and regenerated; the cooling period and its doubling; the lock after ten; forced enrolment; the policy by role; the administrator's reset under the escalation rule; step-up when fresh and when stale; secrets encrypted at rest. The smoke gains a step that enrols an authenticator app for a person of its run, signs in with a computed code, and deactivates the person at the end.
8. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`.

Documentation: the next free ADR (factors and their storage, the policy's defaults, passkey sign-in as an option, the cooling period, recovery, step-up); TF-248 in the technical PRD; the Identity README; the runbook (resetting a tenant administrator's factors); STATUS. TF-013's email and SMS fallback is an exception with its home in S4, listed when S3 closes.

### Review checklist

- [ ] A password alone never creates a session for a person with a factor.
- [ ] Factor secrets are encrypted at rest and never logged.
- [ ] Recovery codes are shown once, stored hashed, and each works once.
- [ ] Forced enrolment comes before any page.
- [ ] Resetting someone's factors needs step-up, a reason, and the escalation rule.
- [ ] Step-up is one shared mechanism, ready for T5, T7 and T8.
- [ ] Passkeys are proven in a real browser with a virtual authenticator.

## T4. Single sign-on with OpenID Connect

Sharpened on 2026-10-21 after T2. TF-014: a tenant connects one or more OpenID Connect identity providers (its own Microsoft Entra ID, Google Workspace, Okta or another), marks people as SSO-only, and lets new employees be created on their first sign-in when the provider asserts an allowed domain. SAML (TF-015) and SCIM (TF-016) stay in S7.

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, .claude/rules/frontend.md, docs/STATUS.md,
docs/adr/0014, 0016, 0031, 0044, 0046 and the ADR of T3, and TF-010, TF-011, TF-013, TF-014,
TF-019, TF-033, TF-073 and TF-248 in docs/prd/foundation/technical-foundation-PRD.md. Then read
src/Kernel/Iron.Kernel.Identity (login, MFA, sessions, security events, the person's life cycle),
src/Kernel/Iron.Kernel.Authorization (assignments and the escalation rules),
src/Kernel/Iron.Kernel.Security (the secret store), infra/compose (the profiles and the memory they
use), shell/e2e, and in the shell the login page and the console. Then read docs/prompts/S3.md:
replace section T4 with docs/prompts/S3-T4.md, delete that file, and commit the prompt alone first
on a new branch slice/s3-t4 from main. Then follow section T4: write a short plan into the session,
and build without waiting for approval unless the "When to stop" rule in CLAUDE.md applies. Done
when: a tenant administrator connects a provider and tests it; a person signs in through it with
the authorization code flow and PKCE; a new employee of an allowed domain is created on first
sign-in with the default role and home unit; an SSO-only person is refused password sign-in with
"Use your company login"; an email outside the allowed domains is refused and audited; claims may
map to roles within the escalation rule; a provider's assertion of MFA is trusted or not by a
tenant setting; a test provider runs on the laptop and in the pipeline within its memory budget;
every new test names what it proves; make verify passes, and make smoke TENANT=echo and make e2e
TENANT=echo pass. Finish with the report, the matrix's counts for TF-014, the brief's six questions
for the pages you changed, and screenshots of them in both schemes. Then stop.
```

### Instructions

1. **The test provider (decide first, by measurement).** Choose a light OpenID Connect provider for the laptop, the integration tests and the pipeline. It must let a test set the claims it needs (email, `email_verified`, name, groups, `amr`), use under 300 MB of memory, be open source with a licence you record, and be maintained. Compare at least Dex (Go, Apache-2.0) and the `mock-oauth2-server` (MIT), measure each one's memory in the stack, and record the choice in the ADR. It joins Compose as its own profile, started by the browser tests and the integration stage, not by `make up`. The .NET integration tests start it with Testcontainers, as the other services are started.
2. **Providers, per tenant.**
   - Fields: a name shown on the sign-in page, the discovery URL, the client identifier, the client secret (kept in the store at `tenants/<slug>/sso/<provider>`, never in the database), allowed email domains, the claim mapping (email, name, groups), and per provider: just-in-time creation on or off, the default role, and the default home unit for people it creates.
   - A "Test connection" action fetches the discovery document and the keys, and says in words what works and what does not.
   - Presets fill the discovery URL pattern for Microsoft Entra ID, Google Workspace and Okta; any standard provider works without one.
   - Managing providers needs `identity.sso.manage`, rated critical, and step-up (TF-248). Every change is audited, without the secret.
3. **The flow.**
   - The authorization code flow with PKCE, `state` and `nonce`. The ID token is checked for issuer, audience, signature (through the provider's published keys, refreshed when a new key appears), expiry and issue time, with a small clock tolerance.
   - The sign-in page shows a button per provider. A person may also type their email: when its domain belongs to a provider, they are sent there. The answer for an unknown email is the same as for any other, so it reveals nothing (TF-011).
   - A provider's email is used for matching only when the provider marks it verified (`email_verified`), and its domain must be allowed (TF-014 AC3, refused and audited).
4. **People.**
   - **Just-in-time creation** (TF-014 AC1): a new person of an allowed domain is created with the provider's default role and home unit, and a session starts. A deactivated person is never re-created or reactivated by SSO: the sign-in is refused and audited.
   - **Linking:** an existing person whose verified email matches is linked to the provider on their first SSO sign-in. The link is a security event and an audit event.
   - **SSO-only** (TF-014 AC2): a person, or everyone linked to a provider, may be marked SSO-only. Password sign-in is then refused with "Use your company login", and recovery links do not apply. T5's break-glass account is the exception the tenant keeps.

## T6. Audit integrity, search, time, retention and legal hold

Sharpened on 2026-10-22 after T4. The audit trail has been append-only since S1 (TF-060), protected by database permissions. T6 makes tampering detectable even by someone who gets past those permissions, makes the trail searchable and exportable for its whole retention, makes every timestamp trustworthy, and gives records a defined life with legal holds. Requirements: TF-061, TF-064, TF-065, TF-066 and TF-069, building on TF-060.

Three decisions shape it:

- **Chain positions are assigned by sealing, not at insert.** Many transactions write audit events at once. Chaining each one inside its own transaction would serialise every write in the tenant, and a database sequence leaves gaps when a transaction rolls back, which the verification would report as tampering. So events are written as today, and a sealing job assigns them consecutive chain positions and hashes a few seconds later, in commit order. A gap in the chain then always means a deleted event.
- **The verifier is not the writer.** The unit seals its own events, but the anchors live in the control plane, and the daily verification is run by the fleet with a read-only database role. A unit that had been taken over could not fake its own verification.
- **The archive continues the chain.** Archived batches carry their hashes, so verification and search work across the online and the archived parts alike.

### Instructions

1. **The chain** (TF-061).
   - Each audit event gains: its chain position (consecutive per tenant from 1), the previous event's hash, its own hash, and the hash algorithm's version.

Sealing never changes an event's content; the sealing columns are the only ones the sealing role may set, once, and the database refuses any other update (TF-060 AC2 still holds).

5. **Archive and retention of audit** (TF-064).

The operator sets limits per class; a tenant chooses within them, and a value below the operator's minimum is refused (AC3).
   - A retention job archives a record past its retention, then deletes it, and writes an audit event (AC1).
   - Legal holds name records (one record, or every record linked to a master such as a supplier) or the whole tenant. A held record is skipped (AC2). Placing and releasing a hold needs `audit.legal_holds.manage`, critical, with a reason and step-up, and is audited.
   - Prove it on the data tests' sample module and on the kernel's own sessions.
8. **Operational logs** (TF-069).
   - The scrubbing rule of T2 extends to personal data: properties named like a name, an email, a phone or an address are masked, and so is any text that looks like an email (AC3). Logs carry identifiers only (AC1).
   - A test proves that deleting operational logs leaves every audit event in place (AC2), and the ADR states that no log tool can reach the audit store (AC4).
9. **The shell.** The audit search page with its filters, export and archive range; the History panel; a chain status page in the console (last verification, result, the anchors); legal holds; the retention settings; time zones in every date. Every string in the catalogue; the scan covers every new page in both schemes.
10. **Tests.** Each names its criteria, and every criterion of the six requirements is covered. Also: concurrent writes sealed into a consecutive chain; a modified row, a deleted row and a restore, each found by the verification; anchors refused for update; the canonical form recomputed by an independent implementation in the test; archived events found by search; pruning keeping the chain valid; a hold stopping deletion. The smoke gains a step that searches the audit trail for its own run's events.
11. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`, and one manual verification run with its record shown.

## T7. Change history and electronic signatures

Sharpened on 2026-10-23 after T6. The core of 21 CFR Part 11 and EU Annex 11: field-level change history for every business record (TF-062), electronic signatures bound to the exact version they sign (TF-063), and their manifestation on screen and on paper, with periodic audit-trail reviews (TF-219).

Four decisions shape it:

- **Change history is part of the audit trail, not beside it.** A field-level change is recorded as an audit event with its list of changed fields, so T6's hash chain protects it like every other event. Part 11 asks for a secure, computer-generated audit trail; a second, unchained store would be weaker.
- **A signature keeps a snapshot of what it signed.** At signing, the record's content is written in a documented canonical form, hashed, and stored with the signature. This is not a version table (the supplier management pack's decision 2 stands): only signed versions are kept, and only because a signature needs them. Later, the signature can be checked against that snapshot, and a changed record shows the signature as applying to the earlier version.
- **Signing follows Part 11's rule on components.** The first signature in a session asks for the login identifier and the password, and the second factor when the person has one. Later signatures in the same continuous session ask for the password (and the second factor if the tenant requires it). A person who signs in through a company login signs with a fresh sign-in at their provider (TF-248 AC6). An impersonator never signs (T5).
- **Kernel features use it first.** Access review decisions (A7) and audit-trail reviews are signed now; business documents use the same mechanism when their slices come.

## T8. Evidence for auditors, four-eyes on configuration, and the validation pack

## T9b. Keys, encryption and secrets

Sharpened on 2026-10-23 after T8. The second half of T9: encryption in transit and of chosen fields with tenant-specific keys (TF-074), versioned keys with scheduled and on-demand rotation (TF-075), and secrets that rotate without a restart and never leak (TF-073). It also takes T3's later item (the key that protects authenticator secrets must rotate too) and two of T9a's residuals (separate secrets for the control plane's API and the fleet, and the rotation of the sign-in check's key).

Three decisions shape it:

- **Keys are managed by a key service, not by the application.** On the laptop, OpenBao's transit engine holds versioned keys per tenant, encrypts and decrypts, rotates, and re-wraps values to a new version without exposing the key. In Azure, Key Vault takes the same role behind the same interface. The application never holds a data key in plain text longer than one operation.
- **Exact search through a keyed hash.** An encrypted field that must be found by its exact value (a tax identifier, a bank account) also stores an HMAC of its normalised value, with a tenant key of its own. A search hashes the input and compares hashes. The hash reveals nothing without the key, and the key rotates like the others.
- **Rotation never stops the service.** A rotated data key starts a re-encryption job; the old version keeps decrypting until the job finishes, then it is retired. A rotated signing key is published beside the old one, so tokens signed before the rotation stay valid until they expire.

## T10b. Security monitoring and incident response

Sharpened on 2026-10-24 after T8. The second half of T10: security alerts with thresholds (TF-079), incidents with their roles and post-incident reviews, the runbook with the duty to tell a tenant about a personal data breach within 72 hours, and the lost-span counter left from S1 (TF-130 AC4).

Two decisions shape it:

- **Alert rules are evaluated over the audit trail, not over metrics.** The audit trail already holds every authentication failure, lockout, denial, impersonation, break-glass use, export and configuration change, with the principal. Counting them per principal in metrics would create a label for every person, which monitoring systems handle badly. So a kernel rule engine, run by the unit's worker every minute, counts audit events in sliding windows, and raises alerts. Alerts are recorded in the tenant and in the control plane, and sent on to the operator's alerting.
- **A rule that cannot run is itself an alert.** A misconfigured or failing rule is reported as failing, never skipped silently (TF-079 AC4).

### Instructions

1. **Rules.**
   - A rule names: the audit event types it counts, how events are grouped (by principal, by address, by tenant), a threshold, a window, a severity, and a cool-down so one burst raises one alert.
   - Rules ship with the kernel, with defaults the operator can change and a tenant can make stricter, never looser:
     - permission denials: 100 by one principal in 10 minutes (AC1);
     - authentication failures and lockouts: by address and by login identifier;
     - impersonation started, break-glass requested or used, an emergency account's sign-in: each one, at once;
     - exports: any export of more than 10,000 records (AC3); the export also has its own audit event, as today;
     - configuration changes in critical areas (roles with critical permissions, single sign-on, keys, retention, legal holds, the MFA policy): each one, at once;
     - rate-limit refusals and CSP reports above a threshold (T9a).
   - The unit's worker evaluates the rules every minute over the audit events of the window.
   - A rule whose definition is invalid, or whose evaluation throws, is reported as failing: an alert of its own, with the reason (AC4).
2. **Alerts.**
   - An alert records the rule, the group (which principal or address), the count, the window, the severity, and links to the audit search that shows the events.
   - Alerts are recorded in the tenant's database, shown on a Security alerts page in the console with acknowledge and resolve (each audited), and copied to the control plane for the operator.
   - The operator's alerting: add Alertmanager to the laptop stack's telemetry profile, and send each alert to it, so paging works the same way it will in Azure. Choose and record how; keep its memory within the laptop's budget.
3. **Incidents and the runbook** (TF-079 AC2).
   - In the control plane: an operator declares an incident with a severity, the tenants affected, an incident lead and a summary. The incident keeps a timeline of entries, its communication log, and its close.
   - At close, a post-incident review is due within 10 days: what happened, why, what changes. An unrecorded review raises an escalation on day 10.
   - **Personal data breaches:** the incident records whether personal data is affected. When it is, the timeline shows the 72-hour deadline to notify each affected tenant, from the moment the breach became known, and the notice sent to each.
   - `docs/security/incident-response.md`: the severities with examples; the roles (incident lead, communications, scribe); how to communicate inside and to tenants, with templates; the 72-hour notice; evidence to keep (audit search links, chain verification records, logs); and the post-incident review.
   - Make targets: `make incident-declare`, `make incident-note`, `make incident-close`, and `make incident-review`.
4. **The lost-span counter** (TF-130 AC4). When the trace exporter is unavailable, requests still complete, spans are buffered up to a limit and then dropped, and a metric counts every dropped span. A test stops the collector, runs requests, and checks both. Remove the TF-130 AC4 exception from `docs/trace/exceptions.md`.
5. **The shell.** The console's Security alerts page (list, filters, acknowledge, resolve, the link to the audit search); the rules page, showing each rule's thresholds and its state (running or failing), with a tenant's stricter values editable within bounds. Every string in the catalogue; the scan covers both pages in both schemes.
6. **Tests.** Each names its criteria, and every criterion of TF-079 and TF-130 is covered. Also: one burst raising one alert under the cool-down; a tenant unable to loosen a rule; an alert's link finding its events; an incident's review escalated on day 10; the 72-hour deadline shown for a personal data breach; dropped spans counted while the collector is down. The smoke gains a step that produces 100 denials for a person of its run and finds the alert, then deactivates the person.
7. **On the laptop.** `make images`, `make up` with the telemetry profile (Alertmanager included), `make up-control`, `make update-unit` for acme, bravo and echo, `make smoke TENANT=echo`, `make e2e TENANT=echo`, and one incident declared, noted, closed and reviewed by hand.

Documentation: the next free ADR (rules over the audit trail and why not metrics; defaults and stricter-only tenant values; failing rules as alerts; Alertmanager; incidents and the 72-hour notice; dropped spans); the Audit and Telemetry READMEs; the incident runbook; the runbook's monitoring section; STATUS.
