# S3: trust and compliance

The instruction file for slice S3 (`docs/slices/S3-trust-and-compliance.md`, ADR-0023). One section per task. **How to use:** start a fresh Claude Code session in `~/foundation` inside WSL, with a clean working tree on `main` and no unmerged `slice/*` branch, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, and stops with a report. Bring the report and `git diff --stat main..slice/<task>` to the design session; the answer is one message: accept and merge, or stop and adjust. T1 is complete; T2 to T10 are outlines, sharpened in the design session before each starts.

S3 makes IronSaaS Foundation trustworthy for regulated customers: stronger sign-in (passwords, MFA, single sign-on), control over sessions, an audit trail nobody can alter unnoticed, field-level change history, electronic signatures with their manifestation, evidence for auditors, and the security practices behind them. Part 11 controls are active for every tenant from S3 (the technical PRD's D-16).

## T1. Traceability, and a check sequence that holds under load

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, .claude/rules/frontend.md, docs/STATUS.md (all of it),
docs/adr/0004, 0022, 0041 and 0043, docs/prd/README.md, TF-218 in
docs/prd/foundation/technical-foundation-PRD.md, docs/slices/S1-walking-skeleton.md,
docs/slices/S2-access-control-organisations-and-design.md and
docs/slices/S3-trust-and-compliance.md. Then read tests/ (Iron.Testing, the architecture tests, a
few test projects), shell/src/test, shell/vitest config, shell/e2e and the a11y config,
tools/Iron.Smoke, the prd-check script, the Makefile and .github/workflows. Then read
docs/prompts/S3.md: commit it alone first on a new branch slice/s3-t1 from main, and follow section
T1. Write a short plan into the session, and build without waiting for approval unless the "When to
stop" rule in CLAUDE.md applies. Done when: S3's slice plan has its task table; every test names the
requirement criteria or the decision it proves; make trace builds the matrix with each test's
result, and refuses an identifier that does not exist; every requirement of a done slice has a test
for each acceptance criterion or a listed exception; CI publishes the matrix; make verify runs every
check in order and passes three times in a row with the stack running; make prd-check, make test,
make shell-check, make shell-a11y and make format are clean. Finish with the report: the counts of
requirements and criteria covered, the exceptions, and the tests that prove no requirement and no
decision. Then stop.
```

### Instructions

1. **The slice plan.** Fill the task table of `docs/slices/S3-trust-and-compliance.md` from this file's table, with a State column. Fold every STATUS later item that belongs to S3 into the task it fits, and say which in the plan.
2. **Naming what a test proves.** Every test names at least one of:
   - a requirement criterion, written `TF-033 AC2` (or `REQ-012 AC1` for a suite's requirement), or a whole requirement `TF-033` when it proves all its criteria;
   - a decision, written `ADR-0029`, for tests that prove a rule of the build or the architecture rather than a requirement.

   The form, by test kind:
   - **.NET:** a custom trait attribute in `Iron.Testing`, `[Proves("TF-033 AC2")]`, usable several times, filterable (`--filter "proves=TF-033"`), with an analyzer or an architecture test that refuses a test method without one.
   - **Vitest and Playwright:** the test title ends with the bracketed list, for example `"a child-unit administrator sees only its users [TF-033 AC2]"`; a lint rule or a test refuses a title without one.
   - **The smoke:** each step names what it proves in its report line.
   - Record the forms in ADR-0044.
3. **The backfill.** Name what every existing test proves, from S1 and S2. Read each test against the requirement texts; do not guess from a test's name alone. A test that proves nothing the documents state is listed in the report for the design session, not tagged to fit.
4. **The matrix.** `make trace` reads the requirement documents and the tests' result files (TRX from `dotnet test`, JUnit from Vitest and Playwright, the smoke's report) and writes, into the build output (not committed):
   - per requirement and criterion: the tests that prove it, with pass or fail from the last run;
   - the requirements of each done slice (from the slice plans' requirement lists) without a test for every criterion;
   - tests naming an identifier that does not exist, which fails the command.

   A requirement of a done slice without a test for a criterion fails the command too, unless it is listed in `docs/trace/exceptions.md` with its reason and the date it was approved. Write the first exceptions list from the backfill's findings; the design session approves it at the review.
5. **CI.** The CI workflow produces the result files, runs `make trace`, and uploads the matrix as an artifact on every run; the release workflow keeps the matrix with the images it builds. TF-218's validation pack (T8) builds on this.
6. **A check sequence that holds under load.** The shell's page tests have timed out at 5 seconds when they ran straight after `make test` with the stack up (STATUS). Measure the slowest page tests under that load, find the cause, and choose the fix by the measurement: fewer workers when the machine is loaded, a longer default for page tests only, or a pause between suites. Record the choice in ADR-0044. Add `make verify`, which runs `make prd-check`, `make test`, `make shell-check`, `make shell-a11y`, the format check and `make trace` in that order. Done when it passes three times in a row with the stack running.
7. **Documentation.** ADR-0044 (the forms, the matrix, the exceptions list, the reliability choice); a section "Naming what a test proves" in the developer guide; a line in the definition of done ("every new test names the requirement criteria or the decision it proves"); a line in CLAUDE.md's rules; `.claude/rules/backend.md` and `frontend.md`; STATUS.

### Review checklist

- [ ] Every test names what it proves, and the build refuses one that does not.
- [ ] The matrix shows each criterion's tests with their results, and fails on an unknown identifier.
- [ ] Done slices are covered criterion by criterion, or their gaps are listed with reasons.
- [ ] CI publishes the matrix.
- [ ] `make verify` passed three times in a row with the stack running.

## T2. Passwords (outline)

TF-012 password policy, history and lockout (policy per tenant through settings; Argon2id stays; lockout with a back-off and an administrator unlock; the login answer stays the same for every failure, as TF-011 requires). TF-017 password recovery and change (a reset by email arrives with S4's notifications; until then an administrator issues a one-time reset link, shown once, as invitations are; change requires the current password). TF-019 account security events to the user (recorded now; delivered by email with S4). This also closes STATUS's later items about lost administrator passwords and test runs that leave people behind.

## T3. MFA and step-up re-authentication (outline)

TF-013: TOTP with recovery codes; WebAuthn passkeys as a second method if the task's measurement allows; MFA required by tenant policy, by role, or for high-risk permissions; step-up re-authentication within a short window for sensitive actions, which T7's electronic signatures and T5's break-glass reuse. Decision to take when sharpened: the methods and the default policy.

## T4. Single sign-on with OpenID Connect (outline)

TF-014: an identity provider per tenant (or per unit), sign-in by discovery, linking to existing principals, just-in-time creation within a rule, local passwords allowed or refused by policy, MFA left to the provider when it asserts it. Decision to take when sharpened: a light test provider on the laptop, within its memory budget.

## T5. Sessions, impersonation and break-glass (outline)

TF-022 the sessions console (a person's own sessions and an administrator's view, revoke one or all); TF-029 logout and revocation, including "sign out everywhere"; TF-025 impersonation with attribution (who may, the person's consent where required, a band on every page, both names in audit, time-boxed); TF-026 break-glass access (sealed credentials, step-up, alerts, review after use); TF-028 consent and terms acceptance (versions, acceptance per person, re-acceptance on change).

## T6. Audit integrity (outline)

TF-061 a hash chain over the audit log with a verification command and an alert on a break; TF-065 one trusted time source for every timestamp and its drift check; TF-064 audit search, export and retention; TF-066 data retention classes and legal hold; TF-069 operational logs kept apart from the audit trail, proven.

## T7. Change history and electronic signatures (outline)

TF-062 field-level change history with old and new values for every audited entity; TF-063 electronic signatures linked to a record version, with re-authentication, the meaning, and the signer's name and time; TF-219 signature manifestation on screen and in exports, and periodic audit-trail review with its own record. The S2 record template's history panel shows the change history.

## T8. Evidence and validation (outline)

TF-067 compliance evidence exports per framework and period; TF-068 a second approval for sensitive configuration changes (a maker and a checker, before the workflow engine exists); TF-218 the validation pack per release, built from T1's matrix and the release's results, with a traceability matrix, test evidence and release notes.

## T9. Hardening (outline)

TF-071 a review of input validation and output encoding across the API and the shell; TF-072 rate limits and anti-automation (per tenant, per principal and per address, login throttling); TF-070 the secure defaults re-checked; TF-073 and TF-075 key management and rotation (token signing keys with key identifiers, unit tokens, database passwords through the update job); TF-074 encryption in transit inside the platform where the laptop can show it, and at rest as the Azure deployment's requirement.

## T10. Secure development and monitoring (outline)

TF-076 vulnerability and dependency management beyond today's scans (an SBOM per image, licence checks, a policy for fix times); TF-077 the secure development lifecycle (threat models for the sign-in, the audit and the fleet, a security review line in the definition of done, static analysis); TF-079 security monitoring and incident response (alerts on lockouts, break-glass use, privilege grants and audit-chain breaks; an incident runbook).
