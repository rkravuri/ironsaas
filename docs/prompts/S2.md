# S2: access control, organisations and the design system

The instruction file for slice S2 (`docs/slices/S2-access-control-organisations-and-design.md`, ADR-0023). One section per task; the prompt at the top of a section is what goes into Claude Code. The standing rules are in `CLAUDE.md`.

---

## D1. Design foundation

### Prompt

```
Task D1 of slice S2: the design foundation. Read docs/prompts/S2.md section D1, CLAUDE.md,
ADR-0024 and docs/design/design-language.md, then build it. Done when: the gallery route shows
every token and component with zero WCAG 2.1 AA violations in the automated scan that runs in
CI; the login page and the layout use no colour by value; reduced motion is honoured; make test,
make shell-check and make format are clean. Report what you built, what you left out and why,
and the test counts.
```

### Instructions

Where: `shell/src/design/` (new), `shell/src/theme.ts`, `shell/src/shell/Layout.tsx`, `shell/src/auth/LoginPage.tsx`, `shell/src/gallery/` (new), `shell/e2e/`, `.github/workflows/ci.yml`, `shell/eslint.config.js`.

1. **Tokens** in `shell/src/design/tokens.ts`: ink and paper with light and dark values (no pure black or white), the accents with names and meanings (a primary accent, one identity accent per module with the module's name, and the four status colours), a six-step type scale with the reading family and the display family (display only at 24 px and above), the spacing scale, radii, and motion durations (150 and 250 ms) and easings. Export them as CSS variables on `:root` and under `[data-mantine-color-scheme="dark"]`, and as a typed object. Every pair used for text on a surface meets 4.5:1; write a small test that checks the contrast of the documented pairs.
2. **The Mantine theme** (`shell/src/theme.ts`) is built from the tokens: colours, fonts, headings, radius, spacing, component defaults (inputs with labels above, focus ring visible, buttons with one primary per page by convention). The grid theme (`src/components/data-grid/theme.ts`) reads the same variables.
3. **Density**: a `density` setting (comfortable, compact) in a small store (`src/design/density.ts`), applied as a data attribute on the root; the grid's row height and the record pages read it. Kept in `localStorage` as a per-viewer convenience.
4. **Reduced motion**: a `usePrefersReducedMotion` hook and a global rule that turns every transition into a cut when it is set.
5. **The gallery** at `/gallery`, present in development builds only (`import.meta.env.DEV`): every token (colour swatches with their contrast, type scale, spacing, radii), every Mantine component the shell uses in its themed form, the grid with sample rows, the error views, the login form, in both schemes and both densities. Each example has a heading and an accessible name.
6. **The accessibility scan**: Playwright with `@axe-core/playwright` on the gallery in both schemes, failing on any WCAG 2.1 AA violation; runnable with `npm run a11y` against `vite preview`, and a job in `ci.yml` (`shell-accessibility`) that builds the shell, serves the preview and runs the scan. Keep the existing `e2e` tests separate; they need the stack, the scan does not.
7. **The lint rule**: `no-restricted-syntax` in `eslint.config.js` that refuses hex, `rgb(`, `hsl(` and named colours in `style` props, `styled` objects and CSS modules under `src/modules/` and `src/components/` (except `src/design/` and `src/components/data-grid/theme.ts`). A test runs ESLint to prove it, as `src/lint.test.ts` does for the grid.
8. **Apply**: the login page and the layout use the tokens and the components only. Nothing else changes visibly yet; D2 brings the drawings.

Do not add illustrations, patterns or page templates here; they are D2 and D3. Do not change the API.

Tests: the contrast test; the lint test; `make shell-check`; the accessibility scan locally.

Documentation: `shell/README.md` gains the design folder and the gallery; `docs/guides/developer-guide.md` gets a short "Styling a page" paragraph pointing at the tokens and the lint rule; an ADR if a choice here is not already in ADR-0024 (for example the type families chosen and why).

### Review checklist

- [ ] The gallery shows both schemes and both densities, and the scan passes in CI.
- [ ] Contrast pairs documented and tested; no raw colour in a page; lint proves it.
- [ ] The login page and layout look the same or better and use only tokens.
- [ ] Reduced motion proven by a test or the gallery.
- [ ] ADR for the type families and any other choice.

## D2. The drawn world

### Prompt

```
Task D2 of slice S2: the drawn world. Read docs/prompts/S2.md section D2, CLAUDE.md, ADR-0024
and docs/design/design-language.md sections 3 and 4, then build it. Done when: acme and bravo
show different marks on their login pages; every empty and error state in the shell carries its
drawing; every drawing has an accessible name or is hidden; the gallery accessibility scan passes;
make shell-check and make format are clean. Report what you built and the test counts.
```

### Instructions

Where: `shell/src/design/patterns/` (new), `shell/src/design/illustrations/` (new), the login page, `src/shell/ErrorBoundary.tsx`, `src/components/data-grid/`, the gallery.

1. **The pattern generator** (`patterns/mandala.ts`): a pure function from parameters (symmetry 6, 8 or 12; rings 2 to 6; stroke; density; a seed) to SVG path data, and a `<Mandala>` component that draws it with the current ink and an accent at a given opacity, `aria-hidden`, honouring reduced motion for the draw-in animation. Deterministic: the same seed gives the same drawing; tests prove it.
2. **The tenant mark** (`patterns/TenantMark.tsx`): the mandala seeded from the tenant's hostname, shown on the login page (large, behind the form at 6 to 8 percent contrast, and small beside the title) and in the header corner at 24 px. The seed is the hostname so no configuration is needed; TF-173 adds tenant colours later.
3. **The illustrations** (`illustrations/`): one React component per drawing, SVG, the brief's stroke rules, taking `ink` and `accent` from the tokens, `role="img"` with an `aria-label` from the catalogue when it carries meaning and `aria-hidden` when it is decorative. The set: `NothingYet`, `NothingFound`, `NoAccess`, `AllDone` (empty states), `Lost` (404), `Broken` (unexpected error), `Forbidden` (403), `Welcome` (login), `Home` (the home page, used by D4), `Success`, `Loading` (a drawn loader). Each is original, in one hand, with the brief's subjects. Write them yourself; do not pull from a library or imitate a known style, character or brand.
4. **The illustration review checklist** in `docs/design/illustration-checklist.md`: one hand (stroke, caps, fills), original, accessible name, both schemes, reduced motion, the subject rules of brief section 3. Every drawing in the pull request is checked against it, and the list is referenced from `definition-of-done.md`.
5. **Apply**: the login page gets `Welcome` and the tenant mark; the error views get `Lost`, `Broken`, `Forbidden`; the grid's empty state gets `NothingYet` or `NothingFound` depending on whether a filter is active; the loading states get `Loading`. The gallery shows every drawing and pattern in both schemes.

Tests: determinism of the generator; the tenant mark differs for two hostnames; every illustration renders with an accessible name or hidden (a test that mounts each and checks the attribute); the scan.

Documentation: `docs/design/design-language.md` section 10 updated if a path changed; the checklist; the gallery.

### Review checklist

- [ ] The drawings pass the checklist and are in one hand; nothing looks like a known character or brand.
- [ ] The login pages of two tenants differ by their mark and nothing else.
- [ ] Patterns never sit behind text or data; contrast of text over them still 4.5:1.
- [ ] Reduced motion: no draw-in animation.

## D3. Templates, panels and forms

### Prompt

```
Task D3 of slice S2: page templates, panels and the form. Read docs/prompts/S2.md section D3,
CLAUDE.md, ADR-0024 and docs/design/design-language.md sections 2 and 8, then build it. Done when:
a server validation problem lands on its field; the Users page sits on the list template; the
grid's keyboard operation is proven in a browser test; the gallery shows every template and panel
with the scan passing; make shell-check and make format are clean.
```

### Instructions

Where: `shell/src/components/templates/` (new), `shell/src/components/` (panels), `shell/src/components/form/` (new), the Users page, the gallery, `shell/e2e/`.

1. **Templates**: `ListPage` (title, description, actions, filters bar, the grid, the empty state), `RecordPage` (the record header with status, actions and tabs; the panel area), `WizardPage` (steps, back and next, summary), `ConsolePage` (sections with descriptions, for settings-like pages), `DashboardPage` (a grid of cards with big numbers in the display family). Each follows "calm centre, living edges": the opener (title, one line, an optional spot drawing) is the moment; the body is the work.
2. **Panels**: `RecordHeader`, `ApprovalPanel` (a placeholder with the shape, S5 fills it), `AttachmentPanel` (list and upload through `IObjectStorage` paths), `HistoryPanel` (the audit events of a record), `CommentPanel` (placeholder), `EmptyState`, `LoadingState`, `ConfirmDialog`, `FormDialog`.
3. **The form** (`components/form/`): a `Form` built on Mantine's form with a Zod schema, labels above, inline validation after the first blur, one primary action, and `applyProblem(form, problem)` that maps an `ApiError`'s `errors` (field name to messages, snake_case from the API) onto the fields and shows the rest at the top with the correlation id. A test proves the mapping with a problem as `ValidationFilter` writes it.
4. **Apply**: the Users page on `ListPage`; a sample record page in the gallery with every panel.
5. **Keyboard**: a browser test on the Users grid: tab into the grid, arrow to a row, Enter or Space selects, a keyboard shortcut opens the row's action; and the density switch changes the row height.

Tests: the problem mapping; template rendering tests; the browser test; the scan.

Documentation: the developer guide's "A shell page with a grid" section becomes "A shell page" with the templates and the form; the gallery.

### Review checklist

- [ ] Every template judged by the brief's six questions in the pull request.
- [ ] The form's server error mapping works with the API's actual problem shape.
- [ ] The Users page is the same or better, on the template.

## A1. Organisation units

### Prompt

```
Task A1 of slice S2: organisation units. Read docs/prompts/S2.md section A1, CLAUDE.md, ADR-0012,
ADR-0013, the Authorization module, and TF-034 in docs/prd/technical-foundation-PRD.md, then build
it. Done when: a principal has a home unit; the tree page lists and moves units; a role assignment
scoped to a unit resolves for records owned by that unit and not for others; make test is green
with the new integration tests; make format is clean.
```

### Instructions

Where: `src/Iron.Authorization/` (entities, services, API), `src/Iron.Identity/` (home unit on the principal, through Contracts), `src/Iron.Data/` (the owning organisation on `BusinessRecord` already exists; use it), `shell/src/modules/console/` (new: the tenant console module with the units page).

1. **Entity** `OrganisationUnit` in `authz`: name, code, kind (legal entity, business unit, department, team), parent, path (materialised path or closure table; decide and record in an ADR with the performance reasoning for scope evaluation), status (active, inactive), `AuditedEntity`. The root unit is created by the seed with the tenant's display name.
2. **Principals** get a home unit (nullable until A1's seed sets the root for the administrator) and may be granted access to other units (A2 uses it); expose through `Iron.Authorization.Contracts` what Identity needs.
3. **API** under `/api/v1/organisation-units`: list (tree), create, rename, move, deactivate, with permissions `authz.units.read` and `authz.units.manage`; audit events for each change; the owning organisation of a record must be an active unit (a check in `Iron.Data` on save).
4. **Scope**: `IRoleAssignments` and `IPermissionEvaluator` learn a `Scope` (tenant, unit with or without children, record type and id) and `PermissionsOfAsync(principal, scope)`; the `RequirePermission` filter passes the record's unit when the endpoint declares how to find it (a small `RecordScope` marker that names the route value and the lookup). A2 completes the roles side; here the evaluator and its tests.
5. **Page**: the units tree in the console module on the `RecordPage` or a tree component on the `ListPage`, with create, rename, move and deactivate through the form dialog; the console module's manifest with its navigation.

Tests: integration tests for the tree, the move rules (no cycles), the scope resolution; API tests; shell tests for the page.

Documentation: module README; the developer guide gets "Scoping an endpoint to a record"; the ADR for the tree storage.
