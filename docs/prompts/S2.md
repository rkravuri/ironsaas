# S2: access control, organisations and the design system

**How to use.** One section per task. Start a fresh Claude Code session in `~/foundation` (inside WSL) with a clean working tree on `main`, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, and stops with a report. Bring the report, `git diff --stat main..slice/<task>` and the screenshots to the design session; the answer is one message to paste: accept and merge, or stop and adjust. If a session gets long, `/compact` between the build and the checks, or start a fresh session with a short note of where it stands. The standing rules are in `CLAUDE.md` (ADR-0023); everything below the line is written for Claude Code.

### The decision (write it as ADR-0029, "Three layers: kernel, business, products")

**Context.** S1 and the first S2 tasks built technical mechanisms. The Functional Foundation PRD mixes two different things: the shared business masters that every product needs, and the products themselves with their own documents and life cycles. Without a rule, business meaning drifts into technical modules (an organisation unit that knows what a legal entity is) and products start to own masters that other products need.

**Decision.**

1. Foundation code lives in three layers.
   - **Kernel** holds technical mechanisms that know nothing about any business domain: the vocabulary (results, errors, ids, tenant context, money, paging, principals, permissions), the shared libraries (data, API, telemetry, security), and the modules identity, authorization (with the organisation tree, scopes, roles, record policies and delegation of duties), audit, files, tenancy, fleet, and later entitlements, flags, settings, workflow and approvals engine, numbering service, notification delivery, forms engine, business calendar, tasks.
   - **Business** holds the shared business masters and the business configuration of kernel mechanisms: organisations and legal entities, purchasing groups, departments, people (designations, job grades, managers, business groups), items, commodities, categories, units of measure, chart of accounts, budgets, tax codes, HSN and GL codes, currencies and conversion rates, financial years and periods, payment and shipping terms, locations, projects as cost objects, the supplier master, content grouping, lookups, approval configurations and the delegation of authority matrices, number series, notification templates.
   - **Products** hold documents and processes with their own life cycles: supplier onboarding, purchase requests, purchase orders, advanced shipment notices, goods and service receipts, invoicing, sourcing (RFx), auctions, contracts, projects and tasks as a product, forms and surveys, expenses. The supplier portal is a surface, not a product: each product contributes its supplier views.
2. **The placement test.** It has no business meaning: Kernel. Two or more products would need to own it: Business. One product owns it: Products.
3. **Names.**

   | Layer | Project and root namespace | Folder | Schema |
   |---|---|---|---|
   | Kernel vocabulary | `Iron.Kernel`, one flat namespace | `src/Kernel/Iron.Kernel/` | none |
   | Kernel libraries | `Iron.Kernel.Data`, `.Api`, `.Telemetry`, `.Security` | `src/Kernel/Iron.Kernel.<Name>/` | none |
   | Kernel modules | `Iron.Kernel.<Module>` | `src/Kernel/Iron.Kernel.<Module>/` | `kernel_<module>` |
   | Business modules | `Iron.Business.<Module>` | `src/Business/Iron.Business.<Module>/` | `business_<module>` |
   | Products | `Iron.Products.<Product>` | `src/Products/Iron.Products.<Product>/` | `products_<product>` |
   | Hosts | `Iron.Host.<Surface>` | `src/Hosts/Iron.Host.<Surface>/` | none |
   | Tests | `<Project>.Tests` | `tests/<Layer>/<Project>.Tests/`; architecture and host tests stay at `tests/` | none |
   | Shell modules | | `shell/src/modules/{kernel,business,products}/<name>/` | none |

   The kernel vocabulary is one namespace so that no second segment under `Iron.Kernel` can ever be both a vocabulary area and a module (the S1 namespace `Iron.Core.Tenancy` would otherwise collide with the module `Iron.Kernel.Tenancy`). The schema keeps the module's existing short name: `kernel_identity`, `kernel_authz`, `kernel_audit`, `kernel_files`, `kernel_tenancy`, `kernel_fleet`.
4. **Dependencies go downward only**, and between modules only through a module's Contracts project: Products may use Business and Kernel; Business may use Kernel; Kernel uses only Kernel. Hosts compose any layer; tests and tools may reference what they test or drive. Every project declares `<IronLayer>` in its project file, one of `Kernel`, `Business`, `Products`, `Host`, `Test`, `Tool`; a missing or unknown value fails the build, and the architecture tests refuse an upward reference and a reference into another module's `Api`, `Services` or `Data`.
5. **Extension points point down.** When the kernel needs something only a business module can supply, the kernel declares an interface in its Contracts and the business module implements it; the kernel never references Business. The first one is the organisation kinds (A1).
6. **What keeps its name.** Permission names, audit event names, error codes, API routes, configuration sections, image names and secret paths are contracts with stored data, roles and clients; they name the module, not the layer, and do not change.
7. **Schemas start from a new baseline, once.** Each kernel module's migrations are replaced by a new `Initial` migration for its prefixed schema. This is allowed only because no database outside laptops and CI holds data today; from the first deployment outside a laptop, migrations are append-only again, as ADR-0008 says. The schema check refuses a module schema without its layer prefix.

**Consequences.** Every path in the guides changes once; ADRs before 0029 keep the names of their time, and this ADR's mapping table translates them. The Functional Foundation PRD will be split into a Business PRD and one PRD per product, in the design session, before any business or product slice. Laptops are reset once and their tenants provisioned again.

7. **The PRD.** TF-035 AC1 reads: "Given a supplier user requesting another supplier's order by identifier, When evaluated, Then it answers not found (ADR-0032)."

## A7. Delegation of duties and access reviews

Sharpened on 2026-10-19 after A6. Two kernel mechanisms of authorization: a person hands their duties to someone else for a period (TF-037), and an organisation regularly checks that the people in each unit still need their roles (TF-038). Delegation of authority (who may approve up to what amount) is a business configuration of the approvals engine and is not part of this task (ADR-0029).

Four decisions shape it:

- **Acting for someone is explicit.** A delegate chooses "act for" in the header, and while they do, their requests carry the delegator's rights for the delegated duties only. They do not get their own rights and the delegator's mixed together. Every action names both. This is clearer in an audit than a silent union of rights.
- **Duties are declared by modules**, like features and settings. The kernel declares "all" and one kernel duty for the proof. Approval, receiving and evaluation are declared by the slices that build them, and TF-037 AC1 (a workflow assigns the delegate too) belongs to S5.

   - A delegation is: delegator, delegate, duties, from and to (instants; the shell picks dates in the person's time zone), reason, created by, status.
   - A person creates their own delegations without a permission. An administrator creates one for someone else with `authz.delegations.manage` at that person's home unit.
   - The API refuses, each with its own error code:
     - a delegation to oneself;
     - a service account on either side;
     - an overlap (the same delegator and duty in overlapping periods);
     - a cycle of any length in an overlapping period (TF-037 AC2);
     - onward delegation: delegated rights cannot be delegated again.
   - A delegation can be ended early by the delegator, the delegate or an administrator. Every change is audited.
3. **Acting for.**
   - The session carries an "acting for" principal, set by `POST /api/v1/me/acting-for` (and cleared with `DELETE`) when an active delegation exists.
   - While it is set, permission checks use the delegator's permissions, at the delegator's scopes, limited to the delegated duties' permissions. Never more than the delegator holds now: if the delegator loses a role, the delegate loses it too.
   - When the delegation ends, the next request clears the acting-for and says so.
   - Tokens never act for anyone.
   - Every audit event written while acting carries both the actor and "on behalf of" (TF-037 AC3), and the audit list shows both.
   - `/me` answers the acting-for state and the person's active delegations both ways.
   - Record the rules in ADR-0037, including why acting is explicit, not a union of rights.
4. **Access reviews.**
   - A campaign has a name, its units (a unit with or without its children), a due date, an owner (the person who starts it), and a status (open or closed).
   - Starting it takes a snapshot of the items: for every assignment in those units, the principal, the role, the scope and the unit's path.
   - Reviewers are the principals holding `authz.reviews.decide` at an item's unit. A reviewer sees and decides only the items of their units (TF-038 AC1); anyone else is refused (TF-038 AC4).
   - A decision is confirm or revoke, with an optional comment. It is recorded append-only.
   - A revoke ends the assignment at once (TF-038 AC2), through A2's removal path, so the last-administrator guard still holds and is reported as the reason when it applies.
   - The campaign shows progress: decided, open, overdue.
   - Permissions: `authz.reviews.manage` to start and close campaigns, tenant-wide; `authz.reviews.decide` at a unit.
5. **Overdue and escalation** (TF-038 AC3).
   - `IReviewEscalation` in Authorization's Contracts names who is told about an overdue reviewer. The kernel default names the campaign's owner. A business module will name the reviewer's manager.
   - The fleet worker's daily pass, or the unit worker's, finds reviews 7 days overdue and records an escalation event with the target. Sending the message is S4; until then the event and the campaign page show it.
6. **The shell.**
   - The console gains Delegations (mine and, for administrators, others'), with create in a form dialog, a date range, duties as words, and a reason.
   - The header gains an "Acting for" control **only when the person holds an active delegation**, as ADR-0033 requires. It shows a calm band under the header while acting: whose rights, which duties, until when, and how to stop. The home page and every page keep working.
   - The console gains Access reviews: the campaigns list, and a campaign record page with the items to decide, filtered to the reviewer's units, with confirm and revoke per row and a confirm-all for a page of rows behind a confirmation.
   - My profile shows the person's delegations.
7. **Tests.**
   - Integration tests: each refusal with its code; acting with exactly the delegator's rights for the duties; the delegator losing a role during a delegation; expiry clearing the acting state; tokens refused; both identities in audit; campaign snapshot; reviewers limited to their units; a non-reviewer refused; revoke ending the assignment; the last-administrator guard in a review; overdue escalation with the default target, on a fake clock.
   - Shell tests: the control appears only with a delegation, the band, the review page's filtering.
   - A browser test against echo: a delegation of `identity.user_administration` to a child-unit user; that user acts for the administrator and sees the users the administrator may see, and the audit shows both names; a campaign on the child unit decided by its reviewer, with a revoke taking effect.
8. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, then `make smoke TENANT=echo` and `make e2e TENANT=echo`.

Documentation: ADR-0037; the Authorization README; a "Delegating and reviewing access" section in the developer guide, including how a module declares a duty; STATUS.

## A8. Cross-unit access and the unit lifecycle

Sharpened on 2026-10-19 after A7. A person often works for more than one unit: a group controller sees every subsidiary, a shared-services clerk works for three legal entities. This task makes that explicit and visible (TF-222): records shared with listed units, every cross-unit read of a private record audited, a switcher that chooses the unit you work for, and a consolidated mode for those allowed to see several. The lifecycle (TF-223) gains reactivation, a readiness checklist and merge. Splitting a unit waits (TF-223 is a Should, and split needs the business modules that own the records).

"Organisation" in the PRD is the kernel's unit (ADR-0029, ADR-0030). Numbering and templates follow the selected unit when their slices build them; today the settings and the owning unit of new records do.

### Instructions

Where: `src/Kernel/Iron.Kernel.Data` (sharing on business records, the policies), `src/Kernel/Iron.Kernel.Authorization` (units: reactivate, readiness, merge; the working unit), `src/Kernel/Iron.Kernel.Settings` (resolution by the working unit), `src/Kernel/Iron.Kernel.Identity` (the session's working unit, the users list), the audit, the shell's `auth/`, `shell/`, the console's units page, the Users page, the gallery, docs.

1. **Sharing a business record.**
   - A business record has a sharing mode: private (its unit, and those whose scope covers it), shared (also the units listed on the record), or tenant (every unit). The listed units live in a kernel table keyed by record type and id.
   - `UnitVisibility` and the policy engine (A3) follow the mode inside the query, so paging counts stay right.
   - Changing a record's sharing is an action the module's policy decides, and it is audited with the units before and after.
   - The shell gets one sharing control for record pages: the mode in words, and the listed units on the tree picker.
2. **The cross-unit read audit** (TF-222 AC2).
   - A read by id of a private or shared record whose owning unit is outside the reader's home unit and its subtree is audited as a read, with the reader, the record, the owning unit, and what allowed it (a scope, or a share).
   - A refused read by id is audited too, as not found. This closes A3's later item.
   - A list page that contains such records writes one audit event with their ids and count, not one per row.
   - Record the rule in ADR-0038, with why lists are audited per page.
3. **The working unit and the consolidated view** (TF-222 AC1, AC3).

   - New records take the working unit as their owning unit by default. Settings resolve for a person from the working unit, walking up, instead of the home unit.
   - Lists show the working unit's records, and its children's where the scope covers them.
   - A person whose assignments cover more than one unit through a parent with children may choose "All my units", the consolidated view, in which lists show everything their scopes cover.

   - Tokens have no working unit and see what their scopes cover.
4. **The unit lifecycle** (TF-223).

   - **Merge** unit B into unit A. First a preview that lists, by module, what will move: business records (through `IUnitRecordOwners`, which each module with records implements, the sample module in the tests), people whose home unit is B, assignments scoped to B (moved to A), B's settings (dropped where A has its own, listed as conflicts), B's shares (moved to A), and B's children (moved under A). Then a confirmed apply in one transaction, with an audit event that lists everything moved (TF-223 AC1). B ends deactivated and merged into A. Merging a unit into its own descendant, or the root, is refused.
   - **Move** keeps scoped roles and settings with the unit (TF-223 AC3). A1 moved assignments; prove settings too.
   - **Split** is a later item: it needs the business modules that own the records.
   - Permission: `authz.units.manage` at both units for a merge.
5. **Tests.**
   - Integration tests on the sample module: each sharing mode in lists and by id, with paging counts; the read audit for a scope and for a share; the refused read audited; the per-page list audit.
   - The working unit: setting it, new records defaulting to it, settings resolving from it, a unit the person may not choose refused, tokens unaffected.
   - The consolidated view for a parent-with-children assignment (TF-222 AC1).
   - Reactivate. The readiness checklist with a fixture contributor.
   - Merge: preview and apply, each kind of thing moved, conflicts listed, refusals for the descendant and the root, and the audit event listing all of it.
   - Move keeping settings.
   - Shell tests: the switcher appears only with more than one unit, the consolidated choice, the merge preview, the sharing control.
   - A browser test against echo: a person with assignments in two units switches between them and the Users page follows; an administrator previews and applies a merge of two test units.
6. **On the laptop.** `make images`, `make up-control`, `make update-unit` for acme, bravo and echo, then `make smoke TENANT=echo` and `make e2e TENANT=echo`.

Documentation: ADR-0038 (sharing modes, the read audit, the working unit and the consolidated view, merge through module contributions); the Data and Authorization READMEs; a "Working across units" section in the developer guide, including how a module implements `IUnitRecordOwners` and `IUnitReadiness`; STATUS.
