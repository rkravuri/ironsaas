# S2: access control, organisations and the design system

**How to use.** One section per task. Start a fresh Claude Code session in `~/foundation` (inside WSL) with a clean working tree on `main`, and paste the section's opening message. Claude Code commits the prompt first, writes a short plan into the session, builds on its branch without waiting, and stops with a report. Bring the report, `git diff --stat main..slice/<task>` and the screenshots to the design session; the answer is one message to paste: accept and merge, or stop and adjust. If a session gets long, `/compact` between the build and the checks, or start a fresh session with a short note of where it stands. The standing rules are in `CLAUDE.md` (ADR-0023); everything below the line is written for Claude Code.

### Opening message

```

first, write a short plan into the session, and build without waiting for approval unless the
"When to stop" rule in CLAUDE.md applies. Done when: the gallery route shows every token and
component with zero WCAG 2.1 AA violations in the automated scan that runs in CI; the login page
and the layout use no colour by value; reduced motion is honoured; make test, make shell-check,
make shell-a11y and make format are clean. Finish with the report, the test counts, the brief's
six questions for the login page, the layout and the gallery, and screenshots of the gallery in

```

### Instructions

Where: `shell/src/design/` (new), `shell/src/theme.ts`, `shell/src/shell/Layout.tsx`, `shell/src/auth/LoginPage.tsx`, `shell/src/gallery/` (new), `shell/e2e/`, `.github/workflows/ci.yml`, `shell/eslint.config.js`.

1. **Tokens** in `shell/src/design/tokens.ts`: ink and paper with light and dark values (no pure black or white), the accents with names and meanings (a primary accent, one identity accent per module with the module's name, and the four status colours), a six-step type scale with the reading family and the display family (display only at 24 px and above), the spacing scale, radii, and motion durations (150 and 250 ms) and easings. Export them as CSS variables on `:root` and under `[data-mantine-color-scheme="dark"]`, and as a typed object. Every pair used for text on a surface meets 4.5:1; write a small test that checks the contrast of the documented pairs.
2. **The Mantine theme** (`shell/src/theme.ts`) is built from the tokens: colours, fonts, headings, radius, spacing, component defaults (inputs with labels above, focus ring visible, buttons with one primary per page by convention). The grid theme (`src/components/data-grid/theme.ts`) reads the same variables.
3. **Density**: a `density` setting (comfortable, compact) in a small store (`src/design/density.ts`), applied as a data attribute on the root; the grid's row height and the record pages read it. Kept in `localStorage` as a per-viewer convenience.
4. **Reduced motion**: a `usePrefersReducedMotion` hook and a global rule that turns every transition into a cut when it is set.
5. **The gallery** at `/gallery`, present in development builds only (`import.meta.env.DEV`): every token (colour swatches with their contrast, type scale, spacing, radii), every Mantine component the shell uses in its themed form, the grid with sample rows, the error views, the login form, in both schemes and both densities. Each example has a heading and an accessible name.
6. **The accessibility scan**: Playwright with `@axe-core/playwright` on the gallery in both schemes, failing on any WCAG 2.1 AA violation; runnable with `npm run a11y` against `vite preview`, and a job in `ci.yml` (`shell-accessibility`) that builds the shell, serves the preview and runs the scan. Keep the existing `e2e` tests separate; they need the stack, the scan does not.
7. **The lint rule**: `no-restricted-syntax` in `eslint.config.js` that refuses hex, `rgb(`, `hsl(` and named colours in `style` props, `styled` objects and CSS modules under `src/modules/` and `src/components/` (except `src/design/` and `src/components/data-grid/theme.ts`). A test runs ESLint to prove it, as `src/lint.test.ts` does for the grid.
8. **Apply**: the login page and the layout use the tokens and the components only. Nothing else changes visibly yet; D2 brings the drawings.

Do not add illustrations, patterns or page templates here; they are D2 and D3. Do not change the API.

Tests: the contrast test; the lint test; `make shell-check`; the accessibility scan locally.

Documentation: `shell/README.md` gains the design folder and the gallery; `docs/guides/developer-guide.md` gets a short "Styling a page" paragraph pointing at the tokens and the lint rule; an ADR if a choice here is not already in ADR-0024 (for example the type families chosen and why).

### Review checklist

- [ ] The gallery shows both schemes and both densities, and the scan passes in CI.
- [ ] Contrast pairs documented and tested; no raw colour in a page; lint proves it.
- [ ] The login page and layout look the same or better and use only tokens.
- [ ] Reduced motion proven by a test or the gallery.
- [ ] ADR for the type families and any other choice.

### Agreed in the plan review (2026-10-18)

The plan Claude Code wrote is accepted with three additions: (1) no flash on a dark reload: `shell/public/scheme.js`, an external script referenced from `index.html`, sets `data-mantine-color-scheme` from `prefers-color-scheme` before React mounts (the CSP allows `'self'`, inline is forbidden), `defaultColorScheme="auto"` stays; (2) the scan saves `shell/test-results/gallery-<scheme>-<density>.png` for the four runs and the CI job uploads the screenshots and the report on every run; (3) the report lists the scan's first findings and how each was fixed. Decisions taken in the plan and kept: Source Sans 3 and Fraunces; the colour rule also refuses Mantine's palette names; OKLCH-generated scales on one lightness table; primaryShade 6 in both schemes; the gallery as a development build on port 4180.

## P1. The laptop store survives a restart, and an update heals a unit

Added on 2026-10-18 after the D3 session: the WSL distro restarted during the accessibility scan, OpenBao in development mode lost every secret, and every tenant unit crash-looped with 403 from the store. The S1 closing notes had listed this; it comes before A1 because the laptop cannot carry the access-control work on a store that forgets.

### Opening message

```
Read CLAUDE.md, .claude/rules/backend.md, docs/STATUS.md, docs/adr/0005 (the laptop platform),
docs/adr/0016 (secrets at start), docs/adr/0018 (provisioning steps) and docs/adr/0019 (the
Compose runtime), docs/guides/local-stack.md sections 4, 5, 9 and 10, infra/compose/compose.yaml,
infra/compose/scripts/init-env.sh, infra/compose/scripts/write-control-secret.sh, the Makefile,
src/Iron.Fleet/Services/Steps/ and tests/Iron.Fleet.Tests/ProvisioningTests.cs. Then read
docs/prompts/S2.md section P1 and follow it: branch slice/s2-p1 from main, commit the prompt alone
first, write a short plan into the session, and build without waiting for approval unless the
"When to stop" rule in CLAUDE.md applies. Done when: make down and make up keep every secret in
the store; a unit whose secrets were deleted from the store is healed by make update-unit; a
tenant provisioned fresh passes make smoke and make e2e against it; make test, make shell-check
and make format are clean; the runbook says how to recover. Finish with the report, the test
counts and the commands you ran on the stack. Then stop.
```

### Instructions

Where: `infra/compose/compose.yaml`, `infra/compose/openbao/` (new), `infra/compose/scripts/`, `Makefile`, `src/Iron.Fleet/Services/Steps/`, `tests/Iron.Fleet.Tests/`, `docs/guides/local-stack.md`, an ADR.

1. **OpenBao in server mode on the laptop.** A configuration file `infra/compose/openbao/openbao.hcl` with `storage "file"` on a named volume, a plain `tcp` listener on 8200, and auto-unseal. OpenBao's static-key seal (`seal "static"`, a 32-byte key in base64 from `.env`, generated by `init-env.sh` as `OPENBAO_UNSEAL_KEY`) is the first choice; if this OpenBao version does not have it, unseal by script at every start with a single key share kept in `.env`, and record the choice and the version checked in the ADR. The container's health check must accept the uninitialised and sealed states.
2. **Initialised once by `make up`.** A script `infra/compose/scripts/init-store.sh` runs after the container is healthy: if the store is not initialised, it initialises it (one recovery share), writes the root token into `.env` as `OPENBAO_ROOT_TOKEN` (replacing the development placeholder), and enables KV version 2 at `secret`; if it is initialised, it only checks that the token in `.env` works. `make reset` removes the store volume and the token line together, since they belong to each other. `make up-slim` and `make up-ci` get the same step.
3. **Development mode stays where it is right**: the Security and Fleet test fixtures keep `server -dev`; nothing in the tests changes.
4. **The update job heals.** `DatabaseStep`, `StorageStep` and `SecretsStep` join `JobKind.Update` (they are idempotent: a missing database secret means new passwords and `ALTER ROLE`, a missing storage secret means a new signed URL, a missing fleet secret means a new policy and token). The order of steps in an update is database, storage, secrets, migrate, seed, unit, verify. A Fleet test proves it: provision, delete every `tenants/<slug>/*` secret from the store, run an update, and the unit secret is back, the new app password opens the database, the new unit token reads the unit secret and nothing else.
5. **The smoke and the browser tests take a tenant**: `make smoke TENANT=x` and `make e2e TENANT=x` (default `smoke`); the e2e target reads the administrator's password from `tenants/<tenant>/smoke`. A tenant whose administrator password was lost with the store cannot serve the smoke until the reset flow of S3; the runbook says to use a fresh tenant.
6. **The runbook**: section 4 says the store persists and how `make up` initialises it; section 9 drops the development-mode limit; a troubleshooting row for "units restart with 403 from the store": `make up-control` (the control plane's secret) and `make update-unit TENANT=<slug>` for each unit. Prerequisites gain a `.wslconfig` recommendation (`memory` and `swap` sized so that the platform, the control plane, the units, the .NET tests and the browser scan fit; name the values that worked here), because the restart that caused this was most likely memory pressure.
7. **On this laptop, after the build**: `make up` (the store initialises), `make up-control`, `make update-unit TENANT=acme`, `make update-unit TENANT=bravo`, `make update-unit TENANT=smoke`, then a fresh tenant for the proof: `make provision TENANT=echo`, `make smoke TENANT=echo`, `make e2e TENANT=echo`. Report the commands and their outcome. If a unit cannot be healed, say which and why; do not delete tenants.

Do not change how units read their secret (ADR-0016), the fleet's secret paths (ADR-0018) or the test containers.

Tests: the Fleet healing test; the compose config check in CI still passes with the new file; `make test` 387 or more.

Documentation: the ADR (store persistence on the laptop, the seal choice, the healing update); the runbook; STATUS.

### Review checklist

- [ ] `make down && make up` twice in a row keeps a secret written in between.
- [ ] The healing update proven by the Fleet test and on acme.
- [ ] A fresh tenant passes smoke and e2e.
- [ ] `.env` holds the real root token; nothing else about it moved into git.
